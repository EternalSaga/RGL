## 1. 启动期资源基线（债-03 / 债-04）

### 1.1 显存账（债-03，2026-10-04 开账；测点 = `Resources::logMemoryStats` 自动打）

| 测点 | 读数 |
|---|---|
| `vma[startup]` | blockBytes **3300.88 MiB** / allocBytes **2926.15 MiB** / **461 allocations** |
| 逐内存类型闭合 | type0 2500.88 + type3 736.00 + type4 32.00 = **heap1 3268.88 ✓ 完全闭合** |
| run-to-run 浮动 | ≈ ±20 MiB |
| `vma[first_frame]` − `vma[startup]`（懒构造增量） | **IZB +46.51 MiB** · **EVSSM +42.69 MiB**（关掉对应门时各自 Δ=0.00 ⟹ 全归该模块） |

- 预算判断：本机 25.9 GiB 无压力，**12GB 独显会紧**——这条是 render graph aliasing 重开的触发条件
  承接者（总账 §2.7 注）。

- ⚠ **接进 FSR 后"逐类型求和与 heap 完全闭合"这个断言当场失效**（FFX 自带 VK 分配器不走 VMA）
  → `phase14_plan.md` §1.5。

### 2.1 首次开账读数（2026-10-04，债-01 / 债-02）——留作"缺 VVL 对照"的反例

`frame = 28.59` / `cpu.record = 26.79` / `gpu.frame = 10.89` ⟹ 当时判 **CPU-bound（余量 15.90ms）**。
构成：`cull` 41.6%（**全是 stall**）· 8 pass 57.1%（4 级阴影独占 37.7%）· 其余 1.3%。

- **插桩有效性**：`drawFrame` 未归因 **95.6% → 0.02%**（独立从 stats JSON 重算，**区间并集**口径）；
  profiler 关时交付逐位不变（sha256 全等）；观察者效应 **+0.20%**。
- **反推口径校验**：调研反推 26.7ms vs 实测 26.79ms = **+1.5%** ⟹ 反推口径是准的，
  **错的是它下面那条否决**（Phase 9 结论 2，用错 fence + 对 stall 无效的判据）。
- ⚠ **这组数缺 VVL 对照，"CPU-bound" 的结论因此只在开发环境成立**（2026-10-09 补 `no-vvl` 臂后
  翻案 → `cpu_perf_plan.md` §3.1）。同臂 10-09 复现：28.17 / 28.44 / 10.78 / 10.52，
  draws 6942 不变，vkcmd 21035→21036（来自 sync 修复批）。

### 2.2 级联轴成本表（债-20，2026-10-04 逐 shadow pass 实测）——**本表唯一载体**

`kActiveShadowCascades` 是**编译期常量**，改它要重编译并与 `kSceneShadowCascadeCount` / 图内 4 个
shadow pass / atlas 列数协同 ⟹ 当时不改代码，用"逐 pass 实测求和"给边际成本：

| 级联 | CPU 录制 (ms) | GPU 执行 (ms) | draws（**2026-10-12 逐级实测**） |
|---|---|---|---|
| shadow0 | **1.365** | **1.099** | **341** |
| shadow1 | 3.092 | 2.047 | **1591**（= 全部候选，一个不剔） |
| shadow2 | 3.038 | 1.882 | **1571** |
| shadow3 | 2.985 | 1.581 | **1524** |
| **4 级合计** | **10.480** | **6.609** | **5027** |

- 🔴 **本表 draws 列 2026-10-12 换过口径**：旧表 c1..3 的 ≈1676 是"三级均分"**推算**，且旧合计
  **5368 多算了 341**（实测四级之和 = 5027，差值恰为 341，而旧表 c0 那格注的正是"341 = IZB mask
  重放量"⟹ 很可能把 IZB 的 draws 当成 c0 的阴影 draws 加进去了）。**这条解释仍是推断，未确认**
  （也可能是 2026-10-04 机位不同）。实测方法 = 在 `emitShadowCasters` 内临时计数后复原；
  一个投影体每级最多一条 draw（`ShadowCandidate` 的 `groups` 是 draw 参数，不额外产生 draw）。

- ⚠ **CPU 列是"开着 VVL"的读数**：交付口径（VVL 关）下 4 级合计 CPU 只有 **1.14ms**，各级分布仍按
  本表比例。GPU 列不受影响：10-09 复测 6.59ms；债-87 修好 GPU 时间戳后 10-11 再测 4 级合计
  **6.28ms**（shadow0/1/2/3 = 0.832/1.959/1.901/1.591）⟹ 三个口径同量级互认。重测 = `just cpu`。
- **顺带解答一条悬案**：shadow0 的 CPU 只有其余三级的 **1/3**、draws 只有 **1/4.9**——因为
  **cascade 0 的视锥切片最近最小 ⟹ 投影体最少**，GPU 侧同向。**不是 viewport 子矩形分块的副作用**
  （那条怀疑被实测否掉）。
- **减级联的可用估计**：4→3 省 ≈3.0ms CPU / 1.6ms GPU；4→2 省 ≈6.0ms CPU / 3.5ms GPU。
- ⚠ **两个口径限制**：① 减级联会**改变 split 边界**（`splits[c]` 依赖 `kActiveShadowCascades`）
  ⟹ 留下的级联覆盖更远、投影体更多 ⟹ **实际节省小于线性求和**；② 本表是"现行 4 级配置下各级的
  实测成本"，不是"1 级 / 2 级配置下的总成本"。**要真数得改常量重编**（= 总账批次 N3b，要用户放行）。
- 减级联直接顶 2026-09-29 画质拍板 ⟹ **是画质决策不是纯性能决策**。
- **债-82 的定价缺口已补（2026-10-12）**：逐级投影体数全部实测（见上表），c1..3 = 1591/1571/1524
  **每帧全量重画**，GPU 侧 c1..3 合计 **5.45ms = 阴影 6.28ms 的 87%** ⟹ 时序摊销的分母就是这块。
  同时这次实测**否掉了"簇粒度剔除进阴影段"**（可证上界 0.31ms = 5%，口径见
  `docs/mdi_plan.md` §7.4）——阴影的两条真杠杆是**时序摊销（少画几遍）**与**远级联 LOD（换粗级
  几何）**，不是剔更多。

## 3. 画质类结案数据

### 3.1 SSAO 噪点量化（债-00，2026-10-04；判据 = `imgqa ao-noise`，advisory）

- AO 场确实噪：契约区抖动 **1.310 LSB ≈ 1 量化步长**；但**交付 8bit 面颗粒仅 0.203 LSB < 1**
  = 被量化吞掉。
- 可见形态 = **屏幕锚定的相机移动爬行**（亚像素位移 **5.53×**），不是静止闪烁。
- 机制指纹指向**导数重建**：掠射面 σ **5.14×**，正对相机的面 σ 恰为 0。
- **裁决：不为它拆 tonemap 契约**（`ao.strength=0` 逐位旁路基线不动）。总账债-00 里
  "AO 噪点已量化结案：别再当噪点闪烁的嫌疑"就是这条。
- ⚠ 但"AO 不是"≠"已找到用户报的噪点"——真身另案（TAA 自身交付时域不稳定，随 Phase 13 冻结
  于 2026-10-09 下线，去 `git log -p docs/还债总账.md`）。
- 权威载体 = `phase13_plan.md` §3；施加点最终搬进 TAA 之前的翻案与实测（4.26pp → 0.11pp）
  → `taa_history_space_plan.md` §5.1c。

### 3.2 Wayland 分数缩放把画面放大成糊（债-37，2026-10-04 当日修复）——**唯一现存完整版**

原详细记录在被删除的 `git:调试历史` 里；工作树里另一处引用 = `phase14_plan.md` §1.9（批 14.3 落地
事实）里那句"债-37 的三条连带**无回退**"，指的就是下面的 ①②③。

- **根因**：建窗缺 `SDL_WINDOW_HIGH_PIXEL_DENSITY` ⟹ SDL 仍把 `wp_viewport.set_destination` 设成
  **逻辑尺寸** ⟹ 缓冲 = 逻辑尺寸、被合成器放大 1.75 上屏（= "糊"）。
- **协议级证据**（自写 SDL3 探针 + `WAYLAND_DEBUG=1` 读报文）：`preferred_scale(210)` = 1.75、
  `set_destination(800,600)` 两档都发、缓冲 800×600 vs **1400×1050**。加 flag 后实测
  `Swapchain extent: 1400x1050 … ratio 1.75x1.75, windowScale=1.750` = **精确 1:1**。
- **三条连带**（只加 flag 会坏 UI）：① imgui 坐标系钉成**帧缓冲像素**；② 字号 + 样式 ×scale；
  ③ 鼠标与**点选** ×scale。
- **读数**：文字锐度梯度 **+48%**；UI 物理尺寸精确复原 = `imgui.ini` 面板 `Size` 从 `384,259`
  （逻辑单位）→ `673,453`（像素单位）= **恰 ×1.75**；后端 `io.DisplaySize` 800×600 / FBS 1.750
  → 1400×1050 / FBS 1.000。
- **代价** = 渲染像素 **×3.06**（GPU 侧）。**升级后要删一次 `build/rgl/imgui.ini`**（单位口径变了）。
- **XWayland 实测是更差的路**（HPD 无效）⟹ 这条退路被实测否掉。
- **被推翻的两条旧裁决**：① `vkswapchain.cppm` 的"SDL 从不按分数缩放给缓冲 / 从不写 viewport"，
  其论证用 `nm --defined-only libSDL3.a`——**方法学错误**：SDL 直接 `wl_proxy_marshal`，协议生成
  函数不参与链接，`--defined-only` 查不到是必然；② `FontScaleDpi` "只烘焙不改布局"的假设——
  实测 UI 整体变大、锐度仅 +4%，作废。

### 3.3 mip 链零滤波 ⟹ 平面墙白散斑（债-137，2026-10-18 修复；本机 AMD Radeon 8060S / RADV STRIX_HALO）

### 3.4 GGX 预滤波火点 ⟹ 湿面白散斑（债-138，2026-10-18 修复；本机 AMD Radeon 8060S / RADV STRIX_HALO）

**根因一句话**：`env_prefilter.comp.slang` 每个输出纹素只用 256 个 GGX 样本，而**每个样本都读
mip0 锐利源**。交付 env（`san_giuseppe_bridge_4k.hdr`）最亮纹素 82637、中值 0.266 = **30 万:1**，
太阳只占约 110/8.4M 个纹素 ⟹ 256 样本命中它的概率 ≈ 1e-2/纹素：绝大多数纹素估出 0，极少数估出
82637/256 ≈ 323。**预滤波图因此不是「太阳的模糊像」而是孤立单纹素尖峰**，渲染端湿石
roughness 0.05–0.35 逐像素反射方向扫过尖峰 ⟹ 交付图白点。（修法推导就地 → 该文件头注释。）

**机位** = 用户给的参考机位（`camera.cppm` F1 打印的 `[camera_saved]`，fps 姿态写进
camera.lua 由加载器反推 yaw/pitch）：position `{-0.088202, 0.047000, 0.080680}`
target `{-0.059753, -0.071044, -0.134595}` fov 45。湿材质占画面 22.4% 的那一档。

**判据口径** = 项目既有 `speck`（单帧 L≥200 且 4 邻域中位 ≤60 的像素数，`normalmap.slang`
2026-10-05 那两轮定的口径）+ 一条**尺度无关**对照「孤立比 >6 = 亮度超 4 邻域中值 6 倍」
（防"画面整体变暗所以 speck 掉"这种假降）。窗 = 湿鹅卵石 300×200 @ x150 y430。

**四条量具自身的缺陷**（每条都让某一版读数作废，全部记进脚本注释防移植到 C++ 时带过去）：

1. **不做位置焊接 ⟹ 全部读数作废**。源数据 de-indexed（逐面顶点）⟹ 相邻三角同位置不同下标，
   按下标跑并查集把一块实心平板切成 664 个"分量"。首跑 bistro 因此读出 282,242 个分量 /

   值）⟹ 数 1c 八档全等、对门槛完全不敏感。

面积 1–26 px；**其中 21/22 块内部同时有变暗和变亮**（只有 1 块 3px 全变暗）。一块"新出现的影子"
会把一片连续区域整体压暗，方向混合的 3–26px 碎斑 = **既有影边的亚纹素重摆**（钉进去的簇改了
shadow map 的深度最小值 → PCF 抽点换位置），不是"某枚花箱从无影变成有影"。
按到全量几何参照（D=−1）的距离算：D=5 14,937 → 14,810 px、D=7 19,489 → 19,370 px，
**找回 0.61–0.85% 的损失**；而钉住的簇 = 179/27,487 L0 簇 = **0.65%**。
⟹ **找回量 ≈ 钉住份额，一比一**。如果 must-L0 那 196 个分量真的"特殊"（它们的影子比同体积随机
簇段更容易丢），找回量应当显著**超过**钉住份额；实测没有。

**这就是任务书要的两类归因**：LOD 造成的阴影损失**不是集中在 must-L0 分量上，而是弥散在全部被
简化的几何上**。二值形态钉住 0.65% 的簇只能按比例换回 0.65% 的影子——不是"钉得不够多"（那是
多段排序的账，数 7 已按代价否掉），是**这个切法选中的集合与丢失的集合几乎不相关**。

**几何账交叉核对（±20% 那条纪律）**：纯三角数比预测不了——按 144,448→94,087 应得 0.954ms，
实测 1.299ms（**差 +36%，在 ±20% 外**）。先查了量具：两 VVL 档互差 <0.05ms、带宽 0.004ms、
draws 数 7009/7044 与闭式对得上 ⟹ 量具没问题。换两参数模型 `t = f + k·三角` 用 arm0/arm3 定出
f ≈ 0.99ms、k ≈ 2.9–3.3 ns/三角，回代 arm1/arm2 **四臂全部拟合到 ±3%**。
⟹ 阴影段 GPU 时间里**约 2/3 是与三角数无关的固定项**（四趟 pass 的调度/清除/光栅建立 + 命令组织），
这同时解释了两件事：为什么"三角数比不算数"，以及为什么 +35 draws 的代价（+0.026ms）会被淹没。

**变异自证（两条，都做到"画面逐位回落到对照臂"这个强度）**：
① `collectShadowCasters` 里 `pinnedCount` 人为置 0 → D=7 门开截图与 arm3 **逐位相同**
  （sha `effa57c6…` 两边一致）；② `kPinMinTexels` 改 1e9 → 启动日志活跃 0/0/0/0，D=7 门开 == arm3、
  D=5 门开 == 出厂锚，且 arm2 的 draws 从 7044 掉回 7009、Σc1..c3 与 arm3 差 −0.002ms（带内）。
⟹ 画面与 GPU 的差异**确实**由钉段贡献，不是噪声；也反过来说明：这 128 px 就是本批的全部画面收益。

**门关两锚逐位复现**：出厂 `3801ad63…` / 门关 `23e029e2…`（P3 改动全部在默认关的门后 + 两条
纯重构接缝：`shadowTexelSize` 收口保持表达式逐字同、`worldScaleOf` 收口保持同操作数同序）。

配置面 = `tools/smoke.py shot --frames 400 --timeout 120 --set ...`。

**矩阵读数（每格 6 轮，单轮不算证据）**

🔴 **proxy 钉段不是因**（A/E 都关着照样挂；主 agent 早先"臂 B 过了、臂 A 挂了"那个反直觉方向

**内核侧签名**（每次挂都落在同一形态）

🔴 **复位一路失败到 MODE2 这一层是关键信息**：CP 是**卡死**而不是"活多"。正常的大 dispatch

**device_fault 取证 = 负读数（本批主要产出）**

探测侧一切正常：`Device device_fault: backend=khr reportMasked=false maxFaultCount=1`
（vulkaninfo 也对得上：`deviceFault=true`、`deviceFaultReportMasked=true`、
`deviceFaultVendorBinary=false`、`maxDeviceFaultCount=1`）。

**8 次 hang 的抓取结果逐条相同**（原文）：

```

（不是没查到；后端=VK_KHR_device_fault（可任意时刻查询 + masked 上报））。
```

masked 半边单独跑（臂 E + `diagnostics:fault_poll=true`，3 轮）：
`device fault 轮询账: 调用 401 次，抓到 masked fault 0 次`（401 = 400 帧 + 收尾一次，
证明轮询**真的在跑**而不是被静默跳过；其中一轮确实在第 93 帧挂了，挂前已轮 93 次，零条）。

⟹ **结论：RADV（Mesa 26.2.4 / STRIX_HALO）的 device_fault 对"CP 挂起"这一类不产出任何数据。**
它 advertise 扩展、feature 位全 true、命令调用成功返回，但报告恒空。

🔴 **而"报告恒空"只把嫌疑从"驱动可见的 GPUVM 越界"收窄到"驱动不报的那类"，它没有排除越界**：
随后拿到的 devcoredump 里内核层明写 `[gfxhub] Page fault observed` + fault 地址恰 = 0x0
⟹ fault 存在，只是没进驱动的 fault ring。本模块的日志文案已据此从「本次是纯 hang 无 fault」
改成「**驱动可见面**无 fault（≠ 无 fault）」（判据 = `tests/test_device_fault.cppm` 的
「『驱动可见面没有』须与『无 fault』和『没查成』都可分」用例）。上面那段引文是当时的日志原文，
保留是因为它是读数，不代表它当时的措辞仍成立。
⚠ devcoredump = root 0600、`sudo -n` 无免密 ⟹ **这条取证通路依赖人工**（本批由主 agent 手输
密码才拿到）。写在这里是为了让"下次自己拿不到"这件事不出声。

**诊断通路自身的开销（实测，不是"看着差不多"）**

帧墙钟量不动它（VVL 下 CPU-bound，同臂 run-to-run 带 ≈ 1.09ms，而待测量是 µs 级），
所以用 profiler 逐 zone 直接量：

| 指标 | 读数 |
|---|---|
| `cpu:faultPoll`（每帧一次 `vkGetDeviceFaultReportsKHR(timeout=0)`） | **0.002–0.003 ms/帧** |
| 同一次跑里的参照 `cpu:fenceWait` | 0.033 ms |
| 同一次跑里的参照 `cpu:acquire` | 0.128 ms |

⟹ 轮询成本 ≈ 一次 acquire 的 1/50，占 16ms 帧的 0.015%。门关时连 Vulkan 调用都不发。
量具 = `tools/cpu_baseline.py` 新增的 `fault-poll` 臂（臂表是真相源，读数不抄进文档正文）。

**审计：容量不等式方向是对的（没找到反例，但也没排除）**

闭式（已落成单测 `test_mdi_shadow_emit` 的「容量闭式」用例）：

```
需求 demand = (S + P) × C          S = 可切候选数（meshletPipeline 与 meshletMdiPipeline 均有效）
容量 capacity = sliceRows          P = 其中带钉段者（N10 P3 起每带钉段候选多占一行）
                                   C = kActiveShadowCascades − 1（c0 恒旧路径）
需证 demand ≤ capacity：
  S ≤ A_lod = |{s : lod[s].count > 0}|   （switchable ⟹ 该槽选级非空）
  P ≤ A_pin = |{s : proxy[s].count > 0}| （pinnedCount 直接搬自 proxy 表）
  两条都成立的前提 = objectSlot 由 `NextObjectSlot.next++` 单调分配 ⟹ 每候选独占一槽
边界两侧各半实测：容量给到刚好 (S+P)×C 不回落；少一行必须整体回落（"宁可越界也要画"是唯一
不可接受的形态，用例钉住）。
```

另外三条也核过：行数组 `reserve` 恰等于需求（`rowsPerCascade × C`）⟹ 取 span 之后的 insert
不会 realloc，且 `seg.rows.data() == rows.data() + seg.firstRow` 已有断言兜；段区间首尾相接
不重叠；`upload` 被拒 = throw（不会静默提交陈旧行表）。

**最优假设（未证实，写清楚它是假设）**：GPU 读到本帧未写过的行 ⟹ `groupCountX` /
`meshGroupCount` 是任意值 ⟹ `DispatchMesh` 一个天文数 ⟹ **无 fault、纯卡死**（与取证结果吻合）。
审计没找到它能成立的路径，但"没找到反例"不等于"排除"。剩余嫌疑按优先级：
① ring×2 的写安全前提（注释声明"`beginFrame` 的 fence wait 已完成才写本槽"，**未独立取证**）；
② RADV 侧对 MDI + amplification/task shader 组合的实现（本引擎是它少见的重度用户）。

### 4.10 债-140 第二网：ASan/UBSan + VVL GPU-AV（2026-10-20，用户点名试 ASan）

两网都打在**臂 E 配方**上（`mdi_shadow=true` + `shadow_proxy=false` + `shadow_lod=7`，400 帧），
串行、跑前 `pgrep -cx rgl` 为 0。基线对照 = §4.9 的矩阵（同配方 5/6 挂）。

**ASan 构建本体（首次引入，走正门）**

`RGL_ASAN=ON` cache 选项（根 `CMakeLists.txt`）+ `just asan-on` / `just asan-off` 两枚配方。
🔴 为什么必须是 cache 选项而不是手传 flags：sanitizer 要**同时**进编译与链接、且对 C++20 modules
的 BMI 生成一致。手传最容易漏的是 `rlstd` / `logger` 两个独立库——**编得过、链得过，但那两个 TU
根本没插桩**，产出的"干净"报告什么都没测。本批逐库核对过（`nm -C | grep -c __asan`）：

| 库 | `__asan` 符号数 | 库 | `__asan` 符号数 |
|---|---|---|---|
| librlgfx.a | 1882 | librlscene.a | 1295 |
| librlframe.a | 1760 | librlbase.a | 1446 |
| librllogger.a | 70 | librlstd.a | 4 |

vcpkg 依赖是非插桩预编译（接受，ASan 允许混编），所以运行期必须 `detect_leaks=0`。
C++20 modules + clang + ASan **没有撞 BMI 问题**，一次通过，无需给 GMF 特殊处理。

**UBSan 立刻抓到一条真 UB（在本引擎的测试里，不是假阳）**

```
    which is declared to never be null
    #0 RGL::(anonymous namespace)::buildProduct(...) test_meshlet_hand.cppm:209:3
```

= `std::memcpy(tris + triOff, c.locals.data(), c.locals.size())` 在 `c.locals` 为空时传
`nullptr`。触发者正是本文件的「triCount = 0 的簇」用例——**它造的就是空簇**。按 C 标准
`memcpy` 的两个指针实参即使 `n=0` 也必须是可解引用的地址；今天不出事只因为 glibc 对 `n=0`
直接返回。已加 `if (!c.locals.empty())` 守卫。修前 `just test` 在 UBSan 下 abort（rc=134），
修后 **663 条全绿、净化器零报告**。

🔴 **判读边界（不许越界的地方）**：8 轮零报告只能写"**这张网没抓到**"，**不能**写"排除 UAF"。
理由是结构性的：本例全部嫌疑对象——descriptor heap 的**槽内容**、`meshlet_shadow_args/ring`

**ASan 的插桩面根本不覆盖**（它管的是 CPU 侧 heap/stack/global 的访问）。
它能在本次跑里看见的只有 C++ 侧的 vector/new/malloc，而审计已核过那条链（§4.9 容量闭式）。

**GPU-AV：先要把它"真的打开"这件事解决掉**

第一版直接开 VVL 的 `gpuav_enable`，结果是**引擎非零退出**，日志里：

```
vkCreateShadersEXT(): pCreateInfos[0] Internal Error, GPU-AV is being disabled. Details:
Unable to instrument shader using VkIndirectExecutionSetEXT validly, things might work, but
likely will not because of GPU-AV's usage of VK_DESCRIPTOR_TYPE_STORAGE_BUFFER_DYNAMIC
(If you don't need VK_SHADER_CREATE_INDIRECT_BINDABLE_BIT_EXT, turn it off).
```

⟹ **本引擎的 shader object 带着 `VK_SHADER_CREATE_INDIRECT_BINDABLE_BIT_EXT`（DGC execution set
的硬要求，VUID-11032/11154），而 GPU-AV 装不了带该 bit 的 shader object，会自行关闭 GPU-AV。**
这条的危险不在"跑不起来"，而在**它关完之后 VVL 其余面照常干净**——"我开了 GPU-AV"与"我从没开过"
在日志上几乎同形。处置 = 新增 `diagnostics.gpuav_compat`（默认 false）摘掉那枚 bit；
`gate_lint` 对 `gpuav_compat × dgc_static` 同开出 warn（那是拿诊断开关去破一条硬 VU）。

**装桩证据（先于任何"没抓到"的结论）**：开 `gpuav_debug_print_instrumentation_info` 后每轮
**2380 条装桩记录**，逐 pass 分布（984 个 shader 的合计）：

| pass | 装桩分布 | 含义 |
|---|---|---|
| `DescriptorHeapPass` | 3×312 · 8×444 · 7×134 · 17×1（0 仅 35 个） | **描述符堆索引校验在跑** |
| `MeshShading` | 1×345 · 5×132 · 4×2（0 有 505 个） | **mesh/task 侧确实在装桩** |
| `LogErrorPass` | 1×952（全覆盖） | 报错通路在 |
| `BufferDeviceAddressPass` | **0×984** | 本引擎 shader 不用 BDA（走 descriptor heap） |
| `SharedMemoryDataRacePass` | **0×984** | 无 workgroup shared 访问可查 |

**GPU-AV 矩阵：装桩可证的 6 轮 0 挂；合计 12 轮 1 挂**

⚠ 先把口径摆正（这条差点被我写成一个更大的数）：**第一批 6 轮的"装桩"没有取证**——脚本当时漏传
`gpuav_debug_print_instrumentation_info`，所以那 6 轮只能算"跑了，但 GPU-AV 是否真在干活未证明"
（而 GPU-AV 恰恰有一种"看着开了其实被禁用"的失效形态，未证明 = 不能当证据用）。
**第二批 6 轮装桩可证**（每轮 2380 条装桩记录），结果 **0 挂、零 GPU-AV 报错**。
合计 12 轮 1 挂，唯一那次挂在第一批里。

第一批挂的那 1 轮（r6）内核侧确认是**同一个 hang**（`ring gfx_0.0.0 timeout` + MODE2），
但它的死相是先撞到 VVL 自己的 `vkQueueSubmit(): Internal Error / Failed to submit per pre
submission command buffer`（设备已 lost 后 GPU-AV 补交自己的记账 CB 失败）——
🔴 **那一轮本模块的 device_fault 抓取一次都没出**（`抓取=0`）：VVL 抢在引擎的 device-lost
分支之前把进程带走了。这是**我自己这张网的覆盖面缺口**，记下来：GPU-AV 下想拿 fault 读数不可靠。

🔴 **最有信息量的反而是那个"挂率掉了 8 倍"**：无净化器 ~67% → ASan 50% → **GPU-AV 合计 8%（1/12，
且装桩可证的那 6 轮一次没挂）**。GPU-AV 给每帧加了大量 GPU 侧校验工作，而**GPU 侧变慢会压制本
hang** ⟹ 这不像"命令流里写死了一条坏命令"（那种无论多慢都会执行到），更像 **CPU 提交与 GPU 执行
之间的竞态**。⚠ 同一条读数也**反过来削弱**"GPU-AV 干净"的分量：装桩可证的 6 轮里它一次都没看到
案发现场，样本量太小，只能说"没抓到"。

**GPU-AV 判读边界**：它的 descriptor 校验查的是**索引越界**（shader 有没有访问超出绑定范围的
描述符），**不查"某个描述符槽里存的地址是 0"**。所以"GPU-AV 干净"**不排除**"binding 34 的
描述符内容为 null"这条主假设——那条恰好是两网都结构性看不见的东西。

**两网合计对债-140 假设面的净影响**

1. CPU 侧内存错误（UAF / 越界 / 空 memcpy 之类）**没有**被排除，但**没有得到任何支持**，
   且嫌疑对象在 ASan 视野外；
2. GPU-AV 排除了"shader 越界索引描述符堆"这一类；
3. **新增一条正向线索**：GPU 侧降速压制竞态 ⟹ 优先级重排到「ring×2 写安全前提」与
   「提交/GPU 执行的相位」，压过"命令内容本身是坏的"；
4. **下一步该做的不是再撒网，而是那条针对性的、便宜的、确定性的检查**：启动后（及若干帧后）
   把 binding 34 那个 heap 槽的**内容**读回来，与 `ring.deviceAddress` 逐字节对账——
   它直接判"描述符地址是不是 0"，两网都替代不了它。

### 4.11 债-140 第三击：heap 槽内容审计 + ring×2 串行化对照 + vendor dump 通路（2026-140 本批）

三击都打在 devcoredump 那条 **fault @ VA 0x0** 上。前两网（§4.10）结构性看不见嫌疑对象，
本批补的是**能看见的那次观测** + **能把假设判死的两个对照**。

**① 描述符堆槽内容审计（`diagnostics.heap_slot_audit`，默认 false）**

`writeSlotDescriptor()` 原先只在构造期写一次、之后无人复核。现在构造期写完**立刻**把槽内容
拍成快照，每帧在 MDI upload 之前读回逐字节对账（`MeshletShadowArgsService::auditAndLog`）。
主判据是"**与启动快照逐字节相同**"而不是"等于 BDA"——描述符内存布局是驱动私有的，
拿"槽前 8 字节 == BDA"当判据 = 造一条换台机器就红的假判据。

构造期的装桩行（本机实测，含基准快照全 32 字节）：

```
heap slot audit: 已启用 —— 槽 8258，基准快照 32 字节
[30 23 53 03 01 80 00 00 40 86 03 00 ac 6f 01 30 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00]
期望 BDA=0xffff800103532330
```

🔴 **这条读数顺手纠正了一个会让人误判的细节**：槽里存的是 `0x0000800103532330`，
而 BDA 是 `0xffff800103532330` ⟹ **AMD 把高 16 位掩掉了**（GPU VA 是 48 位规范形式）。
所以"地址在不在槽里"这一项必须同时拿**掩码形态**去比，否则它在唯一实测过的驱动上恒 false
= 装了一盏永远不亮的灯（变异测试 Ⓓ 就是钉这个）。

**审计读数（臂 E 配方 × 8 轮，穿过真实的挂）**

| 轮 | 结果 | 挂时帧号 | 审了 | 不符 | 内核 |
|---|---|---|---|---|---|
| 1,2,5,8 | ✅过 ×4 | — | 401 ×4 | 0 | — |
| 3 | ❌挂 | 309 | 310 | 0 | `gfx_0.0.0` Δ3 |
| 4 | ❌挂 | 46 | 47 | 0 | `comp_1.1.1` Δ0 |
| 6 | ❌挂 | 46 | 47 | 0 | `gfx_0.0.0` Δ3 |
| 7 | ❌挂 | 46 | 47 | 0 | `comp_1.3.1` Δ0 |

⟹ **合计 2055 帧，不符 0 次，无基准 0 次**；其中 **451 帧来自那 4 个挂掉的轮次**，
一路审到死掉的那一帧前一拍。

🔴 **结论的准确形状**：这只排除了"**CPU 在录制期看到的那个槽里是 0 / 是陈旧值**"这一条，
**没有**排除 fault@0 本身，因为审计有一个自知的边界——**它审的是服务认为自己那枚槽
（`argHeapSlot`），不是 shader 条目实际烘进去的那枚**。两者按构造同源，但"同源"这件事
本批没有独立取证。剩下的形态因此收窄成三条：① 条目烘的 mapping 指向别的槽（CPU 侧可查，
下一步就做这条）；② GPU 侧读到的与 CPU 写的不同（页表/驱动，CPU 侧不可见）；③ 空指针
根本不在 binding 34。

⚠ 另有一条**观测到的规律**值得记：8 轮里 3 轮挂在**第 46 帧**（其余分布在 246/309 与通过）。
46 不是截图帧也不是任何配置里的数，像是某个周期性事件被挂概率放大——本批样本不足以定论。

**审计自身开销（实测，且实测推翻了我自己的预判）**

| 版本 | `cpu:heapSlotAudit` | 说明 |
|---|---|---|
| 初版（无条件拼 hex + 扫地址） | **0.045 ms/帧** | 预判"读一次 host 映射几乎免费"是**错的** |
| hex 改冷路径 | 0.027 ms/帧 | |
| hex + 地址扫描都改冷路径 | **0.012 ms/帧** | 占 16ms 帧的 0.07% |

成本**按次线性**（同一次跑里把审计调两遍 → 0.058 ms/帧，实测），所以不是计时假象。
量具 = `tools/cpu_baseline.py` 新增的 `mdi-base` / `heap-audit` 两臂（必须成对：审计只在
行表 buffer 已创建时才有对象，拿出厂默认当对照量出来是 0，而那是"没跑"不是"便宜"）。

**② ring×2 写安全对照实验（临时代码，已 revert）**

在 upload 之前插 `vkDevice.waitIdle()` 排空**整个设备**（含另一帧槽上 N-1 的全部提交）
⟹ 从那里到 memcpy 之间 GPU 不可能有任何在途读。臂 E × 6 轮：**3/6 挂**（帧号 279/197/379），
与基线（臂 E 5/6 ≈ 64%、上批 ASan 4/8 = 50%）**无可分辨差异**。

⟹ **"ring×2 的写安全前提被违反"这条假设没有得到支持**——把 GPU 完全排空之后照挂。
⚠ 混杂因素照实说：串行化同时改变了提交节奏，所以这条读数是"该前提**单独**不足以解释"，
不是"围栏机制被证明正确"。实验代码与实验前备份**逐字节相同**（`cmp` 核过），未进构建。

**③ vendor crash dump 通路补全（`vkGetDeviceFaultDebugInfoKHR`）**

探测位 `deviceFaultVendorBinaryKhr` / `deviceFaultVendorBinaryExt` 进 features 生成链；
启用请求挂 `deviceFault` 同处，策略是"**支持即请求**"（它只允许驱动多吐一份二进制 dump，
不改任何提交语义，所以不需要像 `reportMasked` 那样门控）。device-lost 抓取里加两段式
（第一段 `pVendorBinaryData=nullptr` 取 size → 第二段按 size 取回），size>0 落盘到
`build/rgl/faultdumps/rgl-fault-<帧号>.bin`，其余各态**恒出声**。

本机负读数原文（3 次挂逐条相同）：

```
device fault: vendor crash dump 取不到：驱动**没 advertise** deviceFaultVendorBinary feature
（我们无从请求）。这是驱动的覆盖面，不是本引擎的接线问题——要这份数据得换驱动/换卡
（NVIDIA 侧对应 Aftermath）
```

🔴 **这条通路是"先跑一次才写对"的**：第一版只分 `featureOff` / `empty` 两态，本机第一次实跑
就把"RADV 根本没 advertise 该 feature"报成了"**我们**没启用——去查自己的探测接线"，
方向完全错。据此补出第四态 `unsupported`，判序改成**先判责任方**（驱动没 advertise →
我们没启用 → 驱动没给），四种措辞两两不同由单测钉住。

**本批顺手抓到并修掉的一个自身缺陷**

两笔执行账（fault 轮询账 / heap 槽审计账）原先只挂在 main 的退出收口里，而 device lost 时
**那条路执行不到**（收尾 `waitIdle` 抛 `vk::SystemError`，异常展开跳过它）⟹ 挂的轮次一律报
"审了 0 帧"，于是"审了 2055 帧零不符"这个数会**系统性地排除掉正在调查的那些轮**。
现在抓取点与退出收口两处都调、各自去重（`printed` 标志），挂的轮次如实报出 310/47/47/47。
**这是"崩溃路径上的观测代码必须放在异常展开之前"这条教训的第三次应验**（前两次：
device_fault 抓取点、`reportDeviceFaultPollSummary`）。

**三击之后，债-140 的假设面**

| 假设 | 本批判定 |
|---|---|
| ring×2 写安全前提被违反 | **不支持**（②：全排空后 3/6 照挂） |
| CPU 侧看到行表描述符槽是 0/陈旧 | **不支持**（①：2055 帧零不符，含挂前 451 帧） |
| 条目烘的 mapping 指向非预期槽号 | **未测**（①的边界；CPU 侧可查，下一步） |
| GPU 侧读到的与 CPU 写的不同 / RADV 对 MDI+amplification 的实现 | **升为首位**（前两条形被排除后剩下的） |
| vendor crash dump 能给出线索 | **本机无读数**（驱动不 advertise；通路已备给 NVIDIA 那台） |
