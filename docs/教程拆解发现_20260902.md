## ① GGX 分母 `+1e-7` 削掉光滑表面的高光峰值【优先级：高，真 bug】✅ 已修复（相对化 `1e-7·a2`，两条 frag 同步）

**位置**：`shaders/model_pbr.frag.slang:37`、`shaders/model_pbr_ibl.frag.slang:42`

```
D = a2 / (3.14159265 * d * d + 1e-7)     // a2 = r⁴，roughness clamp 下限 0.04
```

**问题**：NdotH=1 时真实分母 π·a2² 极小（r=0.04 → 2.06e-11），被绝对 epsilon 1e-7 淹没约 5000 倍：

| roughness | 理想峰值 1/(π·a2) | 引擎实际 | 保留率 |
|---|---|---|---|
| 0.04 | 124340 | 25.6 | **0.02%** |
| 0.1 | 3183 | 761 | 23.9% |
| 0.2 | 199 | 196.5 | 98.8% |

**症状**：r<0.12 全在雷区；且 D(1) 对 roughness **非单调**（r=0.04 峰值反而低于 r=0.1）——
越光滑高光越暗，抛光金属变天鹅绒。

**复现**：`python3 ~/program/modern_vulkan_tutorial/verify/test_ggx.py`（末段量化了保留率与非单调）。

**修复方向**（二选一）：
- epsilon 相对化：`a2 / (π*d*d + 1e-7*a2)`（r=0.04 时分母回到真实量级）；
- 或 roughness clamp 下限提到 ~0.12（掩盖问题，不推荐）。

## ② `model.mesh.slang` 的 `max(uint, 0)` 是无效防御【优先级：中，潜伏雷】✅ 已修复（条件式前置）

**位置**：`shaders/model.mesh.slang:28`

```
uint remaining = max(drawArgs.totalTriangles - firstTriangle, 0u);
```

**问题**：uint 减法先回绕（firstTriangle > totalTriangles 时得到巨大值），`max` 救不回来
→ triangleCount = min(10, huge) = 10 → 越界读字节。

**现状**：当前不可触发（CPU 侧 `ceil(total/10)` 恒正确），但 groupCount 一旦算错
（资产改动 / Phase 7 device_generated_commands 的 indirect 路径），症状是**静默读垃圾**而非空组。
"看起来安全"的防御写法最危险。

**修复**：条件式前置，杜绝无符号回绕：
```
uint remaining = (firstTriangle >= drawArgs.totalTriangles) ? 0u
               : drawArgs.totalTriangles - firstTriangle;
```

## ③ env 契约检查过宽 + 与文档漂移【优先级：中，DX/正确性】✅ 已修复（styleMap 精确匹配 + 报错列出实际引用风格）

**位置**：`main.cpp:149-157`；文档口径在 `AGENTS.md`（"引用 pbr_ibl 风格无 env 启动报错"）

**实际逻辑**：管线表里**出现** `name == "model_pbr_ibl"` 或 `fragSpv.contains("model_pbr_ibl")`
即报错——**不管有没有风格真正引用它**。

**踩坑实录**：教程截图配置 `styles.pbr = "model_pbr"` 但 pipelines 表保留了 ibl 条目 → 启动失败，
错误信息 "model_pbr_ibl style requires scene.lua 'environment'" 把排查方向带偏
（配置看起来完全合法）。

**两个子问题**：
1. 检查对象错了：应只遍历 `styleMap` 的值（真正"引用"），不看管线表条目；
2. `contains()` 子串匹配脆弱（未来命名 `model_pbr_ibl_v2` 会误伤）。

**修复**：判定收敛为 `for (auto& [style, spec] : styleMap) if (spec == "model_pbr_ibl") ...`
（或按管线规格名精确匹配），错误信息补一句"当前 styles 实际引用：…"。

## ④ `model_pbr` 的 ambient 项没扣 metallic【优先级：低，能量一致性】✅ 已修复（`ambient * albedo * (1-metallic)`）

**位置**：`shaders/model_pbr.frag.slang:46`

```
color = light.ambient * albedo + ...              // pbr：漏了 (1-metallic)
ambient = envDiffuse*albedo*(1-metallic) + ...    // pbr_ibl：这边是对的
```

**问题**：同一引擎两条路线对 ambient 的 metallic 语义不一致；纯金属表面在 pbr 路线下
仍吃到带 albedo 色的环境漫反射（物理上金属无彩色漫反射）。
两风格截图对比时会被误读成光照算法差异。

**修复**：`light.ambient * albedo * (1.0 - metallic)`，与 `model_pbr_ibl` 对齐。

## ⑤ 两个 "intensity" 语义不对称【优先级：低，文档陷阱】✅ 已修复（取文档化方案：env.slang/scene.slang 头注释 + AGENTS.md 各一句；env 颜色在 GPU 侧无法 CPU 预乘，差异为本质性）

- 定向光：`light.color` 在 **CPU 端预乘** intensity 后写入 sceneData@24；
- 环境光：`env.intensity` 在 **shader 端**乘（model_pbr_ibl.frag 末行）。

字段同名、作用点不同，调光时极易只改一边导致两路线亮度不可比。
**修复方向**：统一为 CPU 预乘（env 参数写 intensity 后的值），或至少在
scene.slang/env.slang 头注释与 AGENTS.md 各写一句。
