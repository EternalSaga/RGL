# 债-140 跨驱动取证与上游素材：MDI 阴影段概率性 CP 挂起（fault @ VA 0x0）

> **状态：现行**（2026-10-21）。本文两半：§1–§7 = RADV 侧取证素材（原 `/tmp` 版收编入库，
> 提交上游前从这里定稿）；§8 = **三驱动测试协议**（ANV / NVIDIA 那台机器照它跑）。

> 读数在总账债-140 行）——剩下的分叉只有"驱动特定 vs 引擎通用"，§8 就是审这个的。

## 2. 最小复现

一个渲染器，每帧做这件事（其余全部关闭）：

- **mesh shader 阴影管线**，簇化（cluster）几何，走 **`vkCmdDrawMeshTasksIndirectEXT`**；
- 间接参数表 = 一张 **persistent-mapped** 的 `VkBuffer`
  （usage = `INDIRECT_BUFFER | STORAGE_BUFFER`，VMA `CPU_TO_GPU` +
  `HOST_ACCESS_SEQUENTIAL_WRITE` + `MAPPED_BIT`），CPU 每帧 `memcpy` 写入本帧的行 +
  `vmaFlushAllocation`；
- 同一张 buffer **同时**被 shader 当 storage buffer 读（binding 34，描述符 range = 整张容量），
  寻址方式 = `row = rowBase(push_constant) + SV_DrawIndex`；
- 行表按 2 个帧槽轮转（frames-in-flight = 2）；
- 级联阴影 + mesh shader amplification（`×2`）。

触发条件（已用 5 臂矩阵定案）：**MDI 开 且 阴影簇路径有活干**（把 LOD 深度设成"不产簇"则一次不挂）。
**与 shadow proxy 功能无关**（见 §6 的跨提交 A/B）。

```bash
# 引擎侧配方（本项目）
python3 tools/smoke.py shot --frames 400 --timeout 300 \
  --set meshlet.mdi_shadow=true --set meshlet.shadow_proxy=false --set meshlet.shadow_lod=7
```

## 3. 症状

- **概率性**：约 50–75% 的 400 帧跑挂一次（各批读数见 §6）。挂的帧号散布在 20–390。
- 内核：
  ```
  amdgpu: ring gfx_0.0.0 timeout, signaled seq=N, emitted seq=N+3
  amdgpu: Starting gfx_0.0.0 ring reset
  amdgpu: MES failed to respond to msg=RESET
  amdgpu: failed to reset legacy queue
  amdgpu: reset via MES failed and try pipe reset -110
  amdgpu: Ring gfx_0.0.0 reset failed
  amdgpu: GPU reset begin!
  amdgpu: MODE2 reset
  amdgpu: GPU reset succeeded, trying to resume
  ```
  ⟹ **ring 级复位失败、升级到 MODE2 全量复位**。CP 是卡死而不是"活多"：正常的大 dispatch
  会被抢占或跑完，不会让 MES 连 RESET 都不响应。
- **`VK_KHR_device_fault` 报告为空**（8 次挂全空），开着 `deviceFaultReportMasked` 每帧轮询
  也一条 masked fault 抓不到 ⟹ device_fault 对"CP 挂起"这一类不产出数据。
  ⚠ 但**"报告为空 ≠ 无 fault"**：devcoredump 明确抓到 page fault（§4）。
- `deviceFaultVendorBinary` **本机驱动未 advertise** ⟹ `vkGetDeviceFaultDebugInfoKHR` 无从取
  （四态判据已实现，NVIDIA 侧可走 Aftermath 同族路）。

## 5. 应用侧已排除的（每条都有 ≥6 轮实测或全量对账）

**CPU 侧在崩溃时刻的状态是可证明正确的**——这是本素材的核心，也是"为什么怀疑驱动侧"的理由：

| 排除项 | 手段 | 读数 |
|---|---|---|
| CPU 侧内存错误 | **ASan + UBSan 全量插桩**（vcpkg 依赖不插桩，`detect_leaks=0`） | 8 轮 4 挂，**0 条 sanitizer 报告** |
| 描述符索引越界 / OOB 访问 | **VVL GPU-AV**（须先摘 `VK_SHADER_CREATE_INDIRECT_BINDABLE_BIT_EXT`，否则 GPU-AV 对本引擎**静默自我关闭**；装桩证据 = 每轮 2380 条 instrumentation 记录） | 装桩确认 6 轮，**0 条 GPU-AV 错误** |
| 行表描述符槽内容错 | 自写审计：每帧把槽内容读回与构造期快照逐字节对账 | **4265 帧零不符**（含 4 个挂掉轮次的 606 帧，审到死前一拍） |
| 管线条目烘错槽号（Ⓐ） | 烘时抄一份 mapping，启动期对账"烘入 heapOffset/descriptorSize == 服务写入的槽号" | **恒等**；改烘的一侧可复现点名（非恒真） |
| **条目用到的全部 8 枚描述符是否为空** | device-lost 时 dump 8 枚槽的原始字节 | **全部非零、基址均为合法 VA**（本批新增，见 §7） |
| ring×2 写安全前提（在途读） | upload 前 `vkDeviceWaitIdle()` 排空**整个设备** | 仍 **3/6 挂** |
| 行表内存类型 / 缓存属性 | VMA `CPU_TO_GPU` → `CPU_COPY`（WC → write-back cached） | 仍 **4/6 挂** |
| 复用密度 | 强制两帧共用同一格（ring×1，故意违反写安全前提） | 仍 **4/6 挂**（不升） |
| 应用层 buffer 越界写 | ASan + VVL + 采集期/录制期两道容量核对 | 无 |

**唯一有效的变量是"快慢"**：无网络 ~64% → ASan 50% → GPU-AV 装桩 0/6。
**任何拖慢 GPU 侧或加验证的东西都让挂率下降** ⟹ 指向 CPU 提交与 GPU 执行之间的相位竞态，
而不是一条写死的坏命令（坏命令不受速度影响）。

## 6. 跨提交 A/B：不是本项目某条功能线引入的

| 版本 | 日期 | 配方 | 挂率 | 形态 |
|---|---|---|---|---|
| ★M-1b `96887ba`（行表刚接上真 MDI） | 10-13 | mdi=1 D=7 | **6/6** | **确定性，恒在第 2 帧，不升 MODE2** |
| ★M-3T-b `53b3982`（行寻址仍在 mesh 侧） | 10-1x | mdi=1 D=7 | **3/6** | 概率性，帧 54/197/208 |
| **pre-N10 `4a3a2d7`**（shadow proxy 线之前） | 10-20 | mdi=1 D=7 | **6/8** | 概率性，帧 20–366，**fault@0 逐位相同** |
| HEAD `86b51c8` | 10-20 | 同 | 4/8、4/8 | 同上 |

⟹ ① **概率性 + fault@0 + MODE2 这一形态早于 shadow proxy 线一周存在**，与该项目功能线无关；
② ★M-3T-a（task 化）把"必挂在第 2 帧"改成了"概率挂"，是一次**部分缓解**，残留即本案；
③ 行寻址从 mesh 挪进 task（★M-3T-c）**不是**扳机（★M-3T-b 已概率性挂）。

## 7. 本批新增的取证能力（可复用于上游复现）

- **device-lost 时 dump 条目全部 heap 槽内容**（描述符堆是 host 可见映射，device lost 后
  CPU 仍读得到）。实测输出示例（8 枚全非零）：
  ```
  binding 28 槽 8244 [00 0a cf e0 01 80 00 00 00 01 00 00 ac 6f 01 30 …]
  binding 23 槽 8248 [00 03 c4 e0 01 80 00 00 40 00 04 00 ac 6f 01 30 …]
  binding 33 槽 8251 [00 0f cf e0 01 80 00 00 10 00 01 00 ac 6f 01 30 …]
  binding 17 槽 8252 [00 00 60 1f 01 80 00 00 70 17 40 08 ac 6f 01 30 …]
  binding 18 槽 8253 [10 9d 0f 07 01 80 00 00 70 4d 29 00 ac 6f 01 30 …]
  binding 19 槽 8254 [70 11 f2 1c 01 80 00 00 f0 69 fe 00 ac 6f 01 30 …]
  binding 20 槽 8255 [00 00 c0 27 01 80 00 00 30 73 8f 01 ac 6f 01 30 …]
  binding 34 槽 8258 [30 23 53 03 01 80 00 00 f0 7e 03 00 ac 6f 01 30 …]
  ```
  前 8 字节 = 描述符基址（**AMD 把 BDA 的高 16 位掩掉了**：`0xffff800103532330` →
  `30 23 53 03 01 80 00 00`，48 位规范 VA）；binding 34 那枚与引擎自报的
  `BDA=0xffff800103532330` 对上。
- **`RADV_DEBUG` 可用值（本机库里的字符串）**：`allbos`（BO→VA 区间）、`hang`
  （库内自带警告"costly and should only be used for debugging"）、`nocompute`（已弃用）。
  ⚠ 本机是 **release 构建的 Mesa**，`RADV_DEBUG=allbos` 未产生可见输出（该打印在 debug 构建里）
  ⟹ **要拿 CS 流需要 debug/trace 构建的 Mesa**，这是给上游提 issue 时值得点明的前置。

## 8. 请上游回答的问题

1. `vkCmdDrawMeshTasksIndirectEXT` + `VK_EXT_descriptor_heap` + mesh amplification 组合下，
   CP 对 **indirect args 所在内存**是否有额外缓存/预取语义，使得"同一块 persistent-mapped

   devcoredump 有 `[gfxhub] Page fault observed`，而 `vkGetDeviceFaultReportsKHR` 返回空。）

## 8. 三驱动测试协议（ANV / NVIDIA 机器，2026-10-21 用户拍板）

**目的**：排除"这确实是 RADV 驱动 bug"——同一份引擎代码在三家驱动上的挂率与故障签名对比。
**判据先行**（跑之前写死，防事后解释）：

| 读数形态 | 结论 | 下一步 |
|---|---|---|
| ANV 也概率挂（≥1/6）且内核有 GPU fault 日志 | **引擎侧通用 bug**（三家共享的命令流/同步形态有缺口） | 回 AMD 做 `96887ba..ad64059` 二分（worktree 已留） |
| 只有 RADV 挂，ANV/NV 各 6/6 过 | **RADV 特定**（或引擎某个形态只有它不容错） | 上游 Mesa issue（本文 §1–§7 就是素材）+ 出厂 `mdi_shadow=false` 维持 |
| NVIDIA 挂且 checkpoint 数据可用 | **直接锁定肇事 draw/binding** | 按 checkpoint 指认的形态回读引擎代码 |
| 全部 6/6 过但 AMD 复跑仍挂 | 环境差异掩盖（负载/内存压力/电源状态） | 记录差异面，不算"排除" |

### 8.1 通用配方（三机同一条）

```bash
# 构建（worktree 复用要显式 -G Ninja，默认 Makefiles 在 generate 期拒 modules）
just config && just build
# 复现臂（每臂 ≥6 轮，串行，跑前 pgrep -cx rgl 清残留）
python3 tools/smoke.py shot --frames 400 --timeout 300 \
  --set meshlet.mdi_shadow=true --set meshlet.shadow_proxy=false --set meshlet.shadow_lod=7
# 对照臂（同机自证"不是整机问题"）：--set meshlet.mdi_shadow=false 跑 6 轮，必须 0/6
```

每轮记录：挂/过、`vkQueueSubmit` 报 DEVICE_LOST 的帧号（**口径：这是 CPU 察觉时刻，是下界
不是案发时刻**——CP 超时判定 1–2s ≈ 上百帧）、驱动侧日志（下面逐驱动）、引擎
`shadow proxy`/`device fault` 行（device_fault 通路已入库，各驱动支持度不同，负读数也要记）。

### 8.2 逐驱动的取证面

**ANV（Intel）**：`dmesg -w | grep -iE "i915|xe|page.fault|GPU hang"`——i915/xe 的 GPU fault
会打进内核日志（含 fault 地址与 ring，形态类似 amdgpu 的 `[gfxhub] Page fault observed`）；
`sudo cat /sys/class/drm/card*/device/devcoredump/data` 若节点存在同样先拷走（易失！）。
ANV 是否 advertise `VK_EXT_device_fault` 用 `vulkaninfo | grep -i fault` 当场记。

**NVIDIA**：崩溃签名不在 dmesg 而在 **Xid**——`journalctl -k | grep -i xid`（典型 13/31/
69/79）；`nvidia-smi -q | grep -A3 "Xid"`。NVIDIA 侧对位工具是 **`VK_NV_device_diagnostic_
checkpoints`**（在 MDI draw 前后各插一枚 checkpoint，device-lost 后取回"最后到达的 checkpoint"
= 直接指认肇事 draw）与 Aftermath（闭源 SDK，`GF_SDK`，能拿 GPU crash dump）。**checkpoints
优先**——它是公开扩展、引擎侧接线小；Aftermath 等 checkpoints 不够用再上。若 NV 侧要临时
加 checkpoint 接线，挂 `diagnostics` 门默认 false，别裸进提交路径。
