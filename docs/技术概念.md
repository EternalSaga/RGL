# 技术概念与设计决策

> **状态**：现行（核心 Vulkan 模式与设计决策的权威记录；代码演进后在此更新）

## 核心 Vulkan 模式

### Synchronization2
所有屏障均使用 `pipelineBarrier2` + `vk::DependencyInfo`，不再使用旧的 `pipelineBarrier` API。

### Dynamic Rendering（动态渲染）
不使用 Render Pass，通过 `beginRendering` + `RenderingInfo` 直接开始/结束渲染。无需创建 RenderPass 对象，简化了渲染流程。

### ShaderObject（着色器对象）
不再创建 Pipeline，直接通过 `bindShadersEXT` + dynamic state 绑定着色器。省去了 PipelineLayout 和传统 Pipeline 创建流程。

### Push Data
通过 `vkCmdPushDataEXT` 推送 `DrawArgs` 数据到着色器。与 descriptor heap 独立，在 shader 中通过 `[[vk::push_constant]]` 访问。push data 区域大小 ≥256 字节。

### DescriptorHeap
`VmaDescriptorHeap` 管理单个 GPU-visible buffer。Descriptors 通过 `vkWriteResourceDescriptorsEXT` 写入 heap slots（slot 运行时动态分配 = `reservedSlots() + offset`，offset 由反射生成：cube vertex=0 / index=4（`types_generated`），模型顶点 base=8+i（`model_types_generated`，每 primitive 一个））。`vkCmdBindResourceHeapEXT` 在渲染前绑定 heap。

### 渲染图（RenderGraph，Phase 6）
帧拓扑从"drawFrame 硬编码三段 + 手写 barrier"升级为**声明 → 编译 → 执行**三层：

1. **声明**（`configs/render_graph.lua`，sol2 沙箱，缺文件回落默认三段图）：
   `attachments`（kind=swapchain/depth/offscreen）+ `passes`（outputs/inputs 带 usage、
   load/store/clear、state/drawSource 名字字符串）。纯数据，零 Vulkan handle 零每帧回调。
2. **编译**（`render_graph::compileRenderGraph`，启动期 fail-fast）：结构校验
   （读先于写/同 pass 读写冲突/DontCare 后仍被使用/usage 与 kind 匹配/blit 拓扑/
   swapchain 必须被写）+ **barrier 自动推导**——每个 attachment 一条"上次 usage"游标，
   跨 pass 转换按查表物化：

   | usage | layout | stage | access |
   |---|---|---|---|
   | colorWrite | ColorAttachmentOptimal | ColorAttachmentOutput | ColorAttachmentWrite |
   | depthWrite | DepthStencilAttachmentOptimal | EarlyFragmentTests | DepthRead\|DepthWrite |
   | sampleRead | ShaderReadOnlyOptimal | AllGraphics | ShaderRead |
   | transferRead | TransferSrcOptimal | Transfer | TransferRead |
   | transferWrite | TransferDstOptimal | Transfer | TransferWrite |

   **帧首规则**：swapchain/depth = oldLayout `eUndefined` + src TopOfPipe/eNone（内容按
   loadOp 重建，与图化前实践逐位一致）；offscreen 持久图 = 执行器跨帧追踪的真实布局
   （帧间已由 fence 同步，src 仍 TopOfPipe）。**跨 render pass 实例 LOAD 的执行依赖** =
   同布局也发 identity barrier（写→写；读→读跳过——写后的首条 read barrier 传递覆盖
   后续所有读者）。帧末 present 转换 src 由 swapchain 最后 usage 派生，submit
   waitStage = 命令流首个 swapchain barrier 的 dstStage（直渲图 ColorAttachmentOutput、
   blit 上屏图 Transfer——旧手工特判被机制接管）。
3. **执行**（`Renderer::drawFrame` 盲循环）：逐 pass `emitBarriers`（物化 +
   `attachmentLayouts` 追踪推进）→ `beginRendering`（逐 pass 附件）→
   `applyDynamicState(pass.state)` → 段内逐 draw（`pass.drawSource`→FrameDrawList
   段边界）→ `endRendering`；blit pass = transferRead→transferWrite 整幅拷贝。
   **图的边界**：heap host-write barrier、scene staging copy、heap 绑定、acquire/present
   信号量与双 fence 帧槽 = 数据通路/时序基础设施，不入图。

设计定位：Frostbite 第一代全自动图只保留核心一条（自动 barrier），aliasing/pass
fusion/多线程录制不做——与 GDC 2022 "The Future of Render Layers"（API-tight）收敛
方向一致。验收 = 图化后截图与旧硬编码路径 **BIT-IDENTICAL**（headless swapchain 回读
sha256 对账，基线 71e50427）；`renderGraphSelfCheck()`（无 GPU）main 启动期常跑。

## 着色器缓冲访问

### ByteAddressBuffer（唯一推荐方式）
Descriptor heap 模式下，shader 侧缓冲访问只使用 `ByteAddressBuffer`：

| 数据类型 | 访问方式 | 原因 |
|---|---|---|
| 每绘制小数据（MVP、光源数等） | **Push Data** | ≤256B，零 descriptor 开销，最快 |
| 其他缓冲数据（顶点、索引、变换等） | **ByteAddressBuffer** | 手动控制字节偏移，始终匹配 C++ `sizeof` |

### 为什么不用 StructuredBuffer
HLSL `StructuredBuffer<T>` 强制元素 stride ≥16 字节对齐，与 C++ `sizeof(T)` 不一致，导致静默数据损坏。`ByteAddressBuffer` 由开发者控制字节偏移，始终与 C++ 布局匹配。

### 为什么不用 UBO/SSBO
ByteAddressBuffer 已覆盖所有使用场景。UBO 在某些硬件上的缓存优化优势在实际中可以忽略。

## 设计决策

### GPU 评分：`pickPhysicalDevice`

评分权重：`coreCount * 1000 + vramGB * 10 + discrete(+500) / integrated(+200)`

流处理器数量是性能的决定性指标，其次是显存，最后是 GPU 类型。这避免了高端核显被误排到弱独显之后（例如高端 iGPU 搭配入门级亮机卡）。

### Present Mode：仅 `eImmediate`

直接返回 `eImmediate`，不可用则抛异常。

在 Wayland 下，compositor 已管理 triple-buffering 和帧同步。`eImmediate` 是正确选择，无需回退。

### Swapchain 图像数量：Wayland 不加 1

Wayland compositor（如 KWin）自身维护 triple-buffer。额外 +1 会变为 quadruple-buffer，增加不必要延迟。X11 仍 +1 以保持向后兼容。

### Viewport Y 轴翻转

`viewport(0, height, width, -height, 0, 1)` 反转 Y 轴。

Vulkan NDC 的 Y 轴向上，窗口/屏幕坐标向下。翻转后视图与预期坐标系一致。

### 双 Fence：inFlight + present

使用两套 fence（`inFlightFences_` + `presentFences_`），而非单 fence。

**问题：** 在 triple-buffer swapchain（KWin）下，单 fence 附加于 `queueSubmit` 无法追踪异步的 `presentKHR`。fence 信号时 present 可能仍在等待，导致 semaphore 重用违规（VUID-00067）。

**方案：** 利用 `VK_KHR_swapchain_maintenance1`：
- `inFlightFences_` — 附加于 `queueSubmit`，追踪 command buffer 完成
- `presentFences_` — 通过 `SwapchainPresentFenceInfoEXT` 附加于 `presentInfo.pNext`，追踪 present 完成

`drawFrame()` 开始时同时等待并重置两个 fence，确保 semaphore 和 command buffer 在 submit 和 present 均完成后才安全重用。

### PresentFenceInfoKHR

使用 `vk::SwapchainPresentFenceInfoEXT`（`SwapchainPresentFenceInfoKHR` 的 typedef 别名）于 `presentInfo.pNext`。

现代同步方式，利用 `VK_KHR_swapchain_maintenance1` 实现更干净的 present 端 fence 追踪。EXT 和 KHR 的 sType 值相同。

### DrawArgs 布局规则

Slang 对 `[[vk::push_constant]]` 结构体应用 std140 风格的 UBO 对齐。若 `uint32_t` 前有 `uint64_t`，后者会被 padding 到 8 字节对齐。C++ 和 Slang 布局必须逐字段一致，否则触发 `vkCmdPushDataEXT was never called for range [X, Y)` 验证错误。

### Matrix 布局

Slang 面向 Vulkan/SPIR-V 时 `float4x4` 默认为 column-major，与 `glm::mat4` 一致。`mul(M, v)` 严格计算 `M×v`（列向量）。**两端内存布局相同，直接透传，切勿 `glm::transpose()`**。

### colorToDrawBarrier 的 `oldLayout = eUndefined`

Swapchain image 第1帧 layout 为 `Undefined`（刚创建），帧2+ 为 `PresentSrcKHR`。`eUndefined` 作为 `oldLayout` 在 spec 中**唯一正确**——它覆盖两种状态，无需分支判断。

### Push Data 无需显式 mapping

`[[vk::push_constant]]` 在 descriptor heap 模式下不需要显式 mapping。Spec 3.4.1 明确说明 push constants 以旧方式访问，只是不再需要构建 pipeline layout。
