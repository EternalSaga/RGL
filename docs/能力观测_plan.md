# 渲染能力观测单源化计划

> **状态：批 1、批 2、批 3、批 4 已落地**（2026-10-19 用户拍板四条，结论见 §7；批 4 的三条待定也已在落地时裁决，见 §7 末与「批 4 落地记录」）。批 2 落地时新增一条拍板：**FSR 判据的出口 = `/state` 增 `fsr` 兄弟段**——FSR 是图外 compute，`capabilities` 段按 §3.1 只装编译图事实，塞不进去（「velocity 附件在图」推不出「FSR context 构造了」，设备轴 shader16 降级档就是反例）。§3.5 那句「RT / FSR / TAA / render-scale 判据改成读 `/state.capabilities`」按此执行：RT / TAA / render-scale 读 `capabilities` + `render` 段，FSR 四条读 `fsr` 段（申报侧 gateOpen/temporalConfig × 生效侧 usable/temporalEffective/尺寸/jitter）。
> 一句话：把「引擎当前具备哪些渲染能力」从**被正则捞的日志文案**收成**一个运行期可查询的结构化出口**，
> 并且**消费者同批改过去**——消费者不同批，这条计划就该像债-129 S1b 一样被砍掉。
>
> 由来：`docs/rpc_单源_plan.md` 讨论 RPC 错误面时，用户定的原则「RPC 是外部观测工具，错误只准是真正的
> 网络错误与可信的内部崩溃，**渲染能力一概不得用错误回包表示**」，与「能力本来就有，但可能是散落的，
> 如果可能，是需要统一一下的，需要出计划的」。本计划就是把那两句话变成可执行的东西。
>
> **追加（同日）**：用户进一步要求"提供一个尝试"——动态修改渲染图选项的 add / del，「能不能成不重要，
> 但是预留……add 和 del 失败正好说明渲染图动态能力不足」。本计划因此从"观测"扩到"试探"（§3.6 / §3.7），
> 它同时给这件事定了价：今天运行期能撤的东西，实测**只有被 `adoptPass` 登记过的 highlight 一个**。

## 1. 问题（每条都是本会话实测，不是推断）

1. **能力事实今天存在三个地方，而这三处不是同一份数据**：
   - 编译产物本体 `CompiledRenderGraph`（`attachments` + `passes`）——真正决定这一帧画什么的那份；
   - **声明** `RgGraphDesc`——`Renderer::graphStatus()` 算 `/state` 的 pass 列表时读的是 `desc().passes`，
     不是编译产物；
   - `CompiledGraphResult` 上的一组 `*Decorated` 布尔（taa / velocity / aoApply / ssr）——「某个门有没有
     落图」的平行记账。
   三份各自正确，但**没有任何一处能回答"现在图里到底有什么"**。
2. **外部唯一能拿到能力事实的通道 = 抓引擎日志文案**。`tools/smoke.py` 用十几条正则从启动日志里捞
   velocity / ssr / ssr_trace / taa 的 RT 行、render scale、FSR context、fsr temporal/jitter 的生效证据；
   这些日志行住在 `rgl/render_graph_rtslot.cppm`（逐 RT 一行 info）。
3. **这条通道的脆弱性，两侧都自己写在注释和报错文案里**（不是本计划的新发现）：
   - C++ 侧：`main_scene.cppm` 自陈「文本格式被 smoke.py 的正则钉住」；`main_impl.cppm` 自陈「日志是判据
     的一部分……改了文案那条判据会当场报」；`offgraph_contract_impl.cppm` 甚至规定某条日志**必须在 warn
     档**，因为 info 到不了 smoke 抓的 stdout——**连日志级别都是隐式契约**。
   - 工具侧：smoke.py 多条 `fail()` 文案把「启动日志文案改了」直接列为失败原因之一。
4. **图编译本身不打名字**：唯一的编译日志是 `RenderGraph: {} attachments / {} passes compiled`——**只有
   数量**。`render_graph_impl.cppm` / `render_graph_builtin.cppm` 全文零 logger。
5. **RT「建没建」这个事实问不出全貌**：`RenderTargetCache` 的已建集合是 private，公开面只有按名问的
   `find` / `heapSlot`，**没有任何枚举接口**（实测 `names()` / `size()` / 迭代器零命中）⟹ 想知道"今天到底
   建了哪几张"只能拿一份名单去逐个试——而那份名单正是能力本身。
6. **`/state` 的 `graph` 段五个字段全是 pass 侧，零 attachment**（实测回包构造代码）。

**为什么这是债而不是"能用就行"**：抓日志的判据在文案改动时会**静默失效**——它不会报错，只会因为
"没匹配到"而走进"该能力没开"的分支。债-130 记的就是这一族：smoke.py 的判据一度"能红这件事本身没有
判据"，后来靠 78 条合成用例补上，且教训是**变异必须双向**。也就是说，我们已经在为这条通道付测试成本，
而它本来可以是读一个 JSON。

## 2. 目标与非目标

**目标**：一处产生、一处出口、消费者只认出口。

**非目标**（每条带"什么发现会推翻它"）：

- **不做构建期生成物**（不进 `rgl/generated/`，不走 `just reflect`）。理由：能力是**运行期**事实——
  同一份二进制，`ssr.enabled` 开与不开，图里就没有 `ssr_trace`；构建期产物会**说谎**。
  ⚠ 失效条件：若将来出现"图形态在构建期就完全定死"的档（例如烘焙专用构建），这条对该档不适用。
- **不做"引擎内部错误统一通道"**。用户已裁：引擎没有统一内部通道**是设计不是缺陷**，现有 log + 异常
  体系足够观察真正的错误；本计划只补"能力"这一类可观测事实，不给错误新开一处记录。
- **不在 RPC 里用错误回包表达渲染能力**（用户原则）。本计划是它的正面做法：能力走**观测**，不走错误。
- **不动渲染、不改图编译算法、不改布局链**。批 1-3 是纯观测面 + 消费者迁移；批 4 的探针**在尝试成功的
  那一刻会真的改运行期图**——那正是被测对象，但它不改图编译算法，只走既有的安全点重编译入口。

## 3. 设计

### 3.1 单一来源 = 编译产物本体，不新建第二份事实

能力出口的内容**一律从 `CompiledRenderGraph` 现算**：附件名/种类/格式/尺寸来自 `attachments`，pass
名/类型/状态/执行序来自 `passes`（**不是 `desc()`**），"RT 建没建"来自 `RenderTargetCache` 的实际状态。

🔴 `CompiledGraphResult` 的那组 `*Decorated` 布尔**不进**能力出口——它是装饰过程的副产物，一旦出口
抄它，就把"两处记录"变成了"三处"。装饰有没有落图，答案应当能从图里算出来；算不出来的那部分才需要
单独讨论（见 §7 第三条）。

### 3.2 出口 = `/state` 增一段 `capabilities`

形状（字段名待定稿，语义先钉）：

- `attachments`：逐条 `{name, kind, format, width, height, rtBuilt}`——`rtBuilt` 就是"这张 RT 今天
  实际建了没有"，把 §1.5 那个问不出全貌的事实变成一次查询。
- `passes`：逐条 `{name, kind, state, order}`，**顺序 = 编译产物的执行序**。
- 顶层 `frame`：能力快照属于哪一帧（运行期图可被 `/pass` 热插拔，没有帧号就无法复现）。

为什么挂 `/state` 而不是新端点：少一个端点、复用既有超时档、且"能力"与"状态"本来就是同一次快照的两
部分（推荐意见，待拍板 §7.1）。

### 3.3 需要补的内部能力（本计划唯一的新代码面）

`RenderTargetCache` 需要一个**按图 slot 枚举**的问法（"这个附件的 RT 在不在"），而不是新增一份名单。
注意方向：**不要**给缓存加 `names()` 返回它自己的表——那会把"缓存里有什么"当成能力真相；要的是
"遍历图的附件，逐个问缓存建没建"，能力名单的唯一来源仍是图。

### 3.4 出口的形状进 RPC schema（复用刚落地的那套）

`rgl/rpc_schema.lua` 的 `response` 段 + 共享 `shapes` 已经就位（`docs/rpc_单源_plan.md` 批 3），
`capabilities` 直接登记进去 ⟹ 自动获得：三份生成物、六面对账、实机回包对拍。**不为此另立管线。**

### 3.5 🔴 消费者同批改完（这条决定本计划该不该做）

先例摆在那儿：**债-129 S1b 因"当期零消费者"被取消**。所以迁移不是收尾工作，是准入条件：

- `tools/smoke.py` 的 RT / FSR / TAA / render-scale 判据从"正则捞日志"改成"读 `/state.capabilities`"；
  判据本体（正向必须齐、反向必须不出现、尺寸必须等于渲染网格的某个函数）**一条不减**，只换数据来源。
- smoke.py 的 `--selftest` 合成夹具跟着从"日志文本"换成"JSON 回包"，并按债-130 的教训做**双向变异**
  （删判据要红、弱化判据也要红）。
- 日志行**保留**（人读日志是对的），但**不再是契约**：删掉 C++ 侧那几条"文本格式被 smoke.py 的正则钉住"
  的注释——消费者迁走后它们会变成误导（读者会以为还有东西钉着）。
- `tools/cpu_baseline.py` 里捞 render scale 的那处同步换。

### 3.6 动态能力探针：`POST /decorate`（用户 2026-10-19 追加，本计划由此从"观测"扩到"试探"）

用户原话的要点：「提供一个尝试就是动态修改渲染图选项，add 和 del……**能不能成不重要，但是预留**……
add 和 del 失败正好说明渲染图动态能力不足」。

**形状**：`POST /decorate {feature, op}`，`op ∈ {add, del}`，`feature` = 可装饰特征名。回包**恒 200**，
内容是一次尝试的**结果事实**：

- `done`：这次尝试做成了没有；
- `refusedAt`：**固定词表**里的失败环节（量尺本体，见下）；
- `reason`：一句人话；
- 外加改动成功后的能力快照差异（哪些附件 / pass 因此出现或消失）。

🔴 **拒绝不是错误**。这是用户原则「渲染能力不得用错误回包表示」的正面执行：请求合法、引擎**试了**、
没成——这是能力事实，走正常回包。与 §4 那条 404 的分工必须写清，否则两条决定看起来互相矛盾：

| 情形 | 回什么 | 为什么 |
|---|---|---|
| 请求**点名**一个不存在的东西（`/shot attachment=zzz`） | **404** | 引用解析失败，属协议层（与未知路由同族），引擎没有"尝试"可言 |
| 请求**发起一次变更尝试**（`/decorate`） | **200 + 结果** | 请求完全合法，成与不成都是运行期事实，不是客户端的错 |

**`refusedAt` 词表就是这次探针的刻度**——没有它，"失败"是一坨无法归档的字符串。按实测现状，词表至少
要能区分这几档（每条都有现成的拒绝点做锚，不是臆造）：

- `not-adopted`：该装饰没被登记成可撤。现状实测：`adoptPass` 只有 highlight 装饰用过，四个
  `*Decorated` 特征**全部不在册**，而 `retirePass` 对不在册的名字是明确报错的 ⟹ **今天所有
  `del <特征>` 都会死在这格**。
- `attachment-append-only`：附件撤不掉。这是一条**明确不许动的约束**，理由 = FrameCapturer /
  PickingService 构造期缓存 slot；`declarePass` 自己的注释也写着运行期只能**增**附件。⟹ 即使 pass
  摘掉，附件也摘不掉，只会留孤儿 RT。
- `rt-alloc` / `entry-wiring`：RT 领建与装配条目 / 色输入优先级链的接线不在运行期能力内（`add` 方向的
  预期死点——附件那关它能过，后面这关过不去）。
- `gate-off`：配置门本身关着（与"图形态不支持"是两件事，必须分开，否则读数无法归因）。
- `trial-compile`：试编译拒了（`withdrawPass` / `declarePass` / `redeclarePass` 各有试编译，这是最硬的一道
  正确性闸门；它响说明意图本身不合法，不是能力不足）。

**预期读数（写在这里，跑出来不符就是新发现）**：`del` 全灭在 `not-adopted`；`add` 能过附件关、死在
`rt-alloc` 或 `entry-wiring`。若某条真做成了，说明动态能力比注释声称的强——那也是有效读数。
⚠ 批 4 实跑的结论：`del` 半边符合预期；`add` 半边**两条都不符**——词表最终三档（删了三档），
`add` 死得比预期更早（gate-off），而 `rt-alloc` 实测根本不是墙。逐条 → 「批 4 落地记录」。

### 3.7 🔴 探针必须有消费者，否则它就是又一个休眠端点

"预留"这个词在本项目是有前科的：债-129 S1b 的图事实查询面因"当期零消费者"被取消；RPC 单源也定了
"没有消费点的字段不进 schema"。一个**没人调的 `/decorate` 端点**正是同一形态。

所以本计划给探针指定的消费者是**它自己存在的理由**：一条把 **add / del × 全部特征** 的矩阵跑一遍、把
`refusedAt` 逐条落成读数的探针运行，输出进 QA 的追加式台账（与 `qa/log/` 同族）。这样"预留"的语义是
**已量过的能力边界**，不是**待实现功能的空位**。

⚠ 这条同时划出本计划**不做**的事：不承诺把 add / del 做成。做成它需要（至少）把四个装饰也走 plan +
`adoptPass` 登记、并解决附件 slot 缓存才能松掉 append-only 那条约束——那是另一件事，探针的读数正好给
它定价。要不要立这条债，等探针跑完再说（§7 第 4 条）。

## 4. 顺带收口的 RPC 错误面（依赖 §3，故同计划不同批）

用户原则的直接推论，逐条处置：

| 现状 | 归类 | 处置 |
|---|---|---|
| 400 形状/类型/范围/必填/互斥/未声明键；404 未知路由；405；503；504 帧边界超时 | 网络与协议 | **保留** |
| 409 三个"在途占用"（含 llm 截图模式占着捕获通道） | 协议（会话状态） | **保留** |
| `/shotburst` 的 `attachment` 静态白名单 `swapchain \| taa_out` | **能力伪装成协议** | **删**——它把运行期的图与门写死成请求校验，会拒绝掉引擎本可以服务的请求 |
| `/shot` 点名一个图里不存在的附件 → 400 | 能力被当成请求错误 | 改 **404**（"你点名的东西不存在"是引用解析，与未知路由同族）——已拍板 §7.2 |
| 500 写盘失败等杂项内部故障 | 既不是网络也不是协议 | **未决**——撤掉它会让"图没写成"回成功，正是批 2 刚治过的"200 但什么都没改"；理由与两个出路见下方落地记录 |

🔴 **不许回退的不变量**（本会话刚修的缺陷）：捕获请求**要么兑现要么明确作废，永不悬挂**。之前正是
"未命中就每帧重试"把 `/shot` 端点打死到进程重启。错误面怎么重设计，都不能把悬挂放回来。

### 批 3 落地记录（2026-10-19）

**做了**：

- 删掉 `/shotburst` 的 `attachment` 静态白名单（schema 里的 `oneOf` 一处）。删完实测发现**白名单不止
  一处**：`/shotburst` 仍回 400，因为跑的是 `just reflect` 之前编好的二进制——重编后才 404。这条记下来
  是因为它是个通用陷阱：**改 schema 不重编，判据会拿旧表跑**。
- `/shot`、`/shotburst` 点名不存在的回读源 → **404**。类别由产生失败的层给（`CaptureFailureKind`
  = `unresolved` / `invalidArgument`），RPC 层只做一次纯映射 `rpcStatusForCaptureFailure`，
  **不解析原因字符串猜状态码**。gbuf 通道号越界仍是 400（词表是协议的一部分，越界 = 参数不合法）。
- 两条行为锚换主体不换判据：`test_rpc_contract` 的 oneOf 那条改挂 `/camera mode`（它守的是"这条校验
  分支在跑"，不是"某字段必须有白名单"）；`test_burst_protocol` 的反向九条 ⟹ 八条，就地写明为什么走、
  判据搬去了哪（`rpc_endpoints_live` 的 404 两条），别让后来人以为是谁手滑删的。
- 实机对拍补两条：`/shotburst` 点名不存在 ⟹ 404 且**与 `/shot` 同口径**；此后 `/shotburst` 仍可用
  （端点没被一次拼错打死）。

**没做，且故意不做**：表里"500 写盘失败从 RPC 撤"这条**没动**。撤掉它 ⟹ 图没写成而回包说成功，
正是批 2 刚治过的那个"200 但什么都没改"。要么保留一个诚实的失败码（细节去引擎日志看，RPC 不诊断），
要么给"没做成"设计一个非错误的正常回包形态——这是契约决定，需要用户拍一句，不自行选边。
（原表把它指向"待拍板 §7.3"是错的，§7.3 现在是 `*Decorated` 那条；本条已就地改记为未决。）

**判据**：`rpcStatusForCaptureFailure` 两 case 对调 ⟹ 2 断言红；两 case 塌成同一个码 ⟹ 2 断言红
（后一条专门防"把能力事实与请求错误混为一谈"，即用户原则禁止的那个混法）。

  回包整个没拿到而日志行全在 ⟹ 红；`capabilities` 段缺失 ⟹ 红；`attachments` 改名 ⟹ 红）。
  实机变异四条全部验红：① 门关不拢 + RT 行文案改拼写 → 迁移前静默 PASS、迁移后 FAIL（对照组：
  只漏门不改文案，旧判据也红——归因坐实到文案）；② 门开而能力段不报 ssr_trace → 正向红（旧判据
  同变异下反而 PASS——来源说谎只有吃 JSON 才抓得住）；③ 门关而能力段注入 ssr_trace → 反向红；
  ④ 回包删掉整个 capabilities 段 → FAIL 不回落（`--ssr` 档日志行在场也不救）。

### 批 2 的三条硬规则（2026-10-19 定，来自"迁移会不会把同一个病搬过去"）

先记着**为什么**要迁：判据段 12 条正则的失效方向**不对称**——正向（门开必须有行）不中会 `fail()`，
反向（门关必须无行）不中则条件为假、**静默通过**。而反向那条是"门开 = 门关逐位相同"这条**不许破的约束**的
**唯一**防线（代码自陈：门关不拢时截图也可能相同，画面判据抓不住，只有日志能抓）。⟹ 文案一改，
逐位不变比对的前提静默死掉而全套测试全绿。旧的 78 条合成用例也抓不到：夹具是**手抄的日志行**（连
`render_graph_rtslot.cppm:195` 前缀都抄了，而文件自己声明那些行号是格式占位、不随源码同步）
⟹ 解析器是拿文案的冻结副本在测，不是跟生产者测。

JSON 的优势具体只有一条：**正则不中 ⟹ None ⟹ 与"该能力不存在"塌成同一个值；JSON 少键 ⟹ 直接响**。
是结构性的，不是风格性的。也正因为它只是结构性的，写错照样能把病搬回来：

1. **能力路径上禁用 `.get(key, default)`**。`caps.get("attachments", [])` 一写，"字段改名"就又塌回
   "没有附件"——同一个 bug 换个写法。缺就是错。
2. **必须有一条合成用例：回包里整个 `capabilities` 段不存在 ⟹ 判据红**。这是新判据的**反向半边**，
   旧夹具形态天生表达不了它（它只能表达"这行文案在/不在"）。没有这条，批 2 只是把脏法换了个名字。
3. **RPC 没起来 / 拿不到能力段 ⟹ smoke 直接 FAIL，绝不回落去捞日志**。回落 = 两个来源，而其中一个
   会悄悄赢，比今天更糟。同理不给 smoke 加"能力段读不到就当没这个能力"的宽容路径。

⚠ 迁移会新增失败模式（smoke 从"起引擎、拿日志、判"变成要开 rpc 门、在引擎活着时连进去）。这些是
**会响**的失败，按规则 3 一律 FAIL 出声即可；不要为了绕开它们而放宽上面三条。
- **批 3**：错误面收口（§4 表）+ `docs/技术概念.md` §RPC 指向能力段。
- **批 4**（已落地 2026-10-19，落地记录见下）：`/decorate` 探针（§3.6）+ 矩阵读数落台账（§3.7）。排最后：它要靠批 1 的能力段来确认"尝试前后
  图变成什么样"，否则 `done` 无从验证。

把「没实现」读成「不可能」并据此冻结值得做的方向，这种事项目里真发生过。这句话同时刻在三处：
量具输出（`ADD_CAVEAT`）、台账每行的 `caveat` 字段、本段。

⚠ **但这条 caveat 自己也有作用域，别读宽**（主 agent 复核时补）：阳性对照证明的是**改图机制**这一半
是通用的（申报单 → 安全点复合事务 → 试编译 → 重编译 → 逐 slot 表结转 → RT 每帧自动 ensure，
没有一环是 highlight 独享），它**没有**证明**特征接线**那一半也走得通——highlight 是个不碰色输入
优先级链、不接 FSR、不加管线条目与堆槽的简单 pass。所以「没接线，不是路走不了」这句话：
对「图能不能被运行期改」是高置信，对「ssr 真接起来走不走得通」目前**只是外推**。
要把这半也变成实测，需要的正是探针本来要量的那个东西——一个真去接线的实现。

**没做，且故意不做**：不承诺把 add 做成（§3.7 划下的边界）；§7.2 的「当场立债」**没立**——
按本计划倾向只落台账，等真有需求再拿这份读数去定价。
