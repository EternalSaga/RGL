````text
Title: [RADV][gfx1151] Mesh shader entry consuming SV_DrawIndex (no task shader) ->
       deterministic GPUVM fault at a fixed VA on frame 2 (22/22 rounds); single-variable
       probes localize it to the builtin itself, not the value

## Summary

On an AMD Radeon 8060S iGPU (Strix Halo, gfx1151, RADV STRIX_HALO), a **mesh shader entry
that reads `DrawIndex` (SPIR-V `BuiltIn DrawIndex` / `gl_DrawID`-equivalent) without a task
shader** produces a **100% deterministic GPUVM fault**: same frame (frame 2), same faulting
virtual address, same status word, every single time — 22/22 rounds on Mesa 26.2.4 across
two source revisions of our renderer. The fault is fully reported by RADV on stderr
(retry-type fault, so the IH path works — unlike our separate probabilistic issue, see the
companion report).

Three single-variable probes pin the causal variable to **the presence of the builtin in the
mesh entry's SPIR-V interface**:

- removing the read (the compiler then strips the builtin from the interface) makes the
  fault vanish completely (0/6);
- restoring the read brings it back (2/2);
- keeping the read but clamping the derived address into a provably in-range window does
  **not** help (2/2) — the value the shader computes from DrawIndex is irrelevant.

We also found what looks like a deliberate workaround in the driver for the *task-shader*
variant of this exact system value (`src/amd/vulkan/radv_pipeline_graphics.c`, Mesa 26.2.4,
~line 2610):

```c
/* Lower mesh shader draw ID to zero prevent app bugs from triggering undefined behaviour. */
if (i == MESA_SHADER_MESH && stages[i].info.ms.has_task &&
    BITSET_TEST(stages[i].nir->info.system_values_read, SYSTEM_VALUE_DRAW_ID))
        radv_nir_lower_draw_id_to_zero(stages[i].nir);
```

The **no-task** case is not covered by that path — and that is exactly the configuration
that faults. Per the spec (interfaces, DrawIndex):

> "When task or mesh shaders are used, only the first active stage will have proper access
> to the variable. The value read by other stages is poison."

With a task shader present, mesh reading DrawIndex is indeed poison — the zero-lowering
matches the spec. But with **no task shader, the mesh stage *is* the first active stage**:
proper access is mandated, and DrawIndex is well-defined (zero-based index of the draw
within the `vkCmdDrawMeshTasksIndirectEXT` sequence, drawCount = 1530). That mandated path
is what faults, 22/22.

## The workload (per frame)

- one `vkCmdDrawMeshTasksIndirectEXT` (drawCount=1530, stride=24) for a clustered mesh-shader

  (binding 34) and read from the **mesh** shader as `row = rowBase(push) + DrawIndex`;
- plus regular direct `vkCmdDrawMeshTasksEXT` draws for the main view.

## Observed fault (deterministic, frame 2)

Engine stderr (RADV's own report, printed every single hang, 22/22):

```
radv: GPUVM fault detected at address 0xbc074a7d3000.
GCVM_L2_PROTECTION_FAULT_STATUS: 0x701431
     CLIENT_ID: (SQC (data)) 0xa
     MORE_FAULTS: 1
     WALKER_ERROR: 0
     PERMISSION_FAULTS: 3
     MAPPING_ERROR: 0
     RW: 0
```

Kernel side: `ring gfx_0.0.0 timeout` → **ring reset succeeds** (no MODE2 escalation — this
is a much gentler citizen than our probabilistic case). The address is page-aligned,
non-zero; MAPPING_ERROR=0 + PERMISSION_FAULTS=3 reads as "PTE exists, permission violation"
— the classic shape of touching a freed/rebound BO. The fault is attributed to the app's
own context (RADV read and printed the fault status for its own graphics VMID).

## Single-variable probe matrix (Mesa 26.2.4, commit `96887ba` of our renderer)

| variant | `BuiltIn DrawIndex` in mesh SPV (spirv-dis count) | value flows into the row address | result |
|---|---|---|---|
| unmodified | 1 | yes | **6/6 hang, frame 2**, fault printed 6/6 |

| reverted (control) | 1 | yes | **2/2 hang, frame 2** |

The one-line probe patch (entire diff — everything else, including dispatch shape, row
table contents and push constants, is untouched):

```diff
--- a/rgl/shaders/shadow_meshlet.mesh.slang
+++ b/rgl/shaders/shadow_meshlet.mesh.slang
@@ -165,7 +165,7 @@ void main(
-    const uint rowBytes = (shadowMeshletDrawArgs.objectIndex + drawID) * kMdiShadowRowStrideBytes;
+    const uint rowBytes = (shadowMeshletDrawArgs.objectIndex + 0u) * kMdiShadowRowStrideBytes;
```

(Semantics are intentionally wrong with the constant — every group reads row 0 — but the
dispatch shape is identical and that is what makes the fault observable as a single
variable. The clamped variant keeps semantics-adjacent addressing fully inside the buffer.)

## A second, independent Mesa bug found while testing the obvious workaround

The zero-lowering workaround (`radv_pipeline_graphics.c:2610`) is gated on `has_task`. We
removed that gate (one-line change, self-built 26.2.4 debug) to see whether it masks the
no-task case — **Mesa itself SIGSEGVs at pipeline compile time**: crash inside
`radv_nir_lower_draw_id_to_zero` (`exec_list_push_head` with `list=0x20`), 6/6 on our
no-task mesh pipeline, backtrace available. So the workaround pass is dead code that
crashes the moment it is applied to the one shape that needs it. (Full backtrace + the
one-line patch: on request.)

## History: on Mesa 26.2.3 the same single variable failed *differently*

On 2026-10-13, on Mesa 26.2.3, our original single-variable matrix (9 arms, same build,
only the mesh SPV varying) showed:

- mesh entry declares+reads `DrawIndex` → **all subsequent direct `vkCmdDrawMeshTasksEXT`
  draws in the same submission produce zero pixels** (a whole building vanishes from the
  main view: 34.27% of pixels, one 315k-px connected component);
- clamping the row index (`min(..., 4772)`) does **not** prevent it;
- not declaring the builtin → clean;
- declaring it in a **task** shader instead (mesh reads the value from the task payload) →
  clean, and still clean today.

So across the two driver versions the same legal construct shows two different failures
(silent poisoning of later mesh draws / deterministic VM fault), while the task-shader
route works in both. Moving the DrawIndex read into the task shader (mesh receives it via
task payload) is our current workaround — verified clean today. Caveat when reading the
symptom change: on 2026-10-13 the kernel was 7.2.9; kernel and Mesa were upgraded together
on 2026-10-15, so "poisoning → fault" cannot be attributed to Mesa alone.

## Questions

1. Is `DrawIndex` in a **mesh entry without a task shader** implemented and tested on the
   hardware meshlet path (GC 11.5.1: `PKT3_DISPATCH_MESH_INDIRECT_MULTI`,
   `SPI_SHADER_GS_MESHLET_*`) at all? The `has_task`-only zero-lowering suggests the
   no-task plumbing may simply never have been exercised.
2. We traced the Mesa-side supply chain and it looks correct: draw_id is lowered to a user
   SGPR (`AC_UD_VS_BASE_VERTEX_START_INSTANCE`), Mesa initialises it before dispatch
   (`set_sh_reg(reg, 0)`, `DRAW_INDEX_ENABLE=1`, `DI_SRC_SEL_AUTO_INDEX`), and our address
   arithmetic shows the faulting VA is **unreachable** from our row-table base + 32-bit
   offsets — i.e. the bad value appears to be produced by the hardware DrawIndex
   auto-increment path itself. How is DI auto-increment driven for
   `DISPATCH_MESH_INDIRECT_MULTI` on GC 11.5.1, and can that path itself fault?
3. Should the zero-lowering workaround be extended to the no-task case? We tried — the
   pass itself crashes (section above). And probe 2 shows clamping the *value* does not
   prevent the fault, so the value is not the (only) mechanism: the builtin merely being
   present in the mesh interface is enough.
4. Is the 26.2.3 symptom (later mesh draws silently producing no pixels) known to share a
   root with this?
````

````text
Title: [RADV/gfx1151] Probabilistic GPUVM fault at VA 0x0 + CP wedge (MES stops responding,
       full MODE2 reset required) from a clustered mesh-shader shadow pass using
       vkCmdDrawMeshTasksIndirectEXT + task shaders — with an exhaustive app-side exclusion

## TL;DR

A private Vulkan renderer (bindless, ShaderObject + descriptor heap, mesh-shader cluster
pipeline) hangs the GPU **probabilistically (~50–75% of 400-frame runs)** on Strix Halo /
RADV 26.2.4 with a `[gfxhub] page fault at 0x0` and a CP that needs a full MODE2 reset.
We have excluded, with measurements (below): CPU-side memory errors, validation layers,
descriptor contents, kernel version, firmware, the driver's **submission surface** (debug
Mesa build + 10 byte-identical vendor fault dumps), the **row-table data contents**
(per-frame blackbox + in-shader self-checks), and the "read never-written memory" family
(poison-filling, 11 independent fault dumps still fault at exactly 0x0).

On the *same* workload we can deterministically observe **two spec violations** (tables
below): one tied to `DrawIndex` in a mesh entry (detailed in a separate report), and one
**mesh workgroups executing with `WorkgroupId.x` beyond the `EmitMeshTasksEXT` X dimension**
— proven with three probes to be a dispatch-side defect, not an application data bug. Both
point into the task→mesh plumbing on the hardware meshlet dispatch path (GC 11.5.1:
`PKT3_DISPATCH_MESH_INDIRECT_MULTI`, `SPI_SHADER_GS_MESHLET_*`).

## Workload shape (minimal reproduction spec)

Per frame, with everything else off:

- clustered mesh-shader shadow pass dispatched via **`vkCmdDrawMeshTasksIndirectEXT`**
  (drawCount ≈ 1530, stride 24; each 24-B row = `VkDrawMeshTasksIndirectCommandEXT` +
  objectIndex + clusterStart + meshGroupCount);
- the indirect args buffer is **persistent-mapped** (`INDIRECT_BUFFER | STORAGE_BUFFER`,
  VMA `CPU_TO_GPU`, `HOST_ACCESS_SEQUENTIAL_WRITE | MAPPED`), CPU `memcpy` +
  `vmaFlushAllocation` every frame, ring-of-2 by frame slot;
- the **same buffer** is read by the task shader as a storage buffer (descriptor heap slot,
  range = whole buffer), addressing `row = rowBase(push_constant) + SV_DrawIndex` in the
  **task** stage; the task dispatches `EmitMeshTasksEXT(meshGroupCount,1,1,payload)`;
- mesh entry reads the cluster tables (4 `ByteAddressBuffer`s via descriptor heap) and the
  per-object cluster-range table;
- plus regular direct `vkCmdDrawMeshTasksEXT` draws (main view) in the same submission.

Reproduction (our engine; standalone reproducer available on request):

```bash
python3 tools/smoke.py shot --frames 400 --timeout 300 \
  --set meshlet.mdi_shadow=true --set meshlet.shadow_proxy=false --set meshlet.shadow_lod=7
```

**Two necessary conditions** (5-arm matrix, 6 rounds per arm): MDI on **and** the cluster
shadow path actually having work. Turning either off: `mdi_shadow=false` → 0/6; LOD depth
that produces no clusters → 0/6. Both on → 3/6 to 5/6.

## Failure signature

Hangs at frames 20–390 (uniform-ish spread — not "runs fine then dies", it is a race).
Kernel:

On 7.2.10 (the common case):

```
amdgpu: ring gfx_0.0.0 timeout, signaled seq=N, emitted seq=N+k   (k <= 3 across events)
amdgpu: MES failed to respond to msg=RESET
amdgpu: failed to reset legacy queue
amdgpu: reset via MES failed and try pipe reset -110
amdgpu: Ring gfx_0.0.0 reset failed
amdgpu: GPU reset begin!  /  MODE2 reset  /  GPU reset succeeded
```

On 7.2.9 the same workload reaches the same MODE2 by a different detection path — **no
`ring timeout` line at all**: the fault goes straight to `GPU reset begin! Source: 1` →
MODE2 (one boot, one hit, 33 s after boot). Both kernels end at MODE2; please don't read
only one signature as "the" symptom.

devcoredump (11 independent kernel blobs — pairwise md5-distinct, which rules out re-copies
of the kernel's ~5-minute stale-dump window we once tripped over):
**every one** shows `[gfxhub] Page fault observed` /
`Faulty page starting at address: 0x0000000000000000`. Notes:

- the *ring* named in the timeout varies across identical rounds (`gfx_0.0.0`, `comp_1.3.0`,
  `comp_1.3.1`, `comp_1.1.1`) — we read that as "which watchdog notices first", not fault
  attribution; the Rptr in two decodable blobs lands in 32/32-NOP padding (CP already
  drained — the faulting wave is hanging a shader engine, not a bad packet);
- `RADV_DEBUG=allbos` BO ranges: lowest VA `0x800000000000` — **0x0 is inside no mapping**:
  a true null read, not "valid base + wild offset";
- `Protection fault status register: 0x0` in the blob means "not readable" (CNTL=0), not
  "no fault" — verified with a 200 Hz SRBM harvester across the whole fault→MODE2 window
  (latches never set before dump; they reset first).

## Why `VK_KHR_device_fault` reports nothing (mechanism chain, worth documenting)

The fault is a **non-retry** protection fault (null page can never build a PTE) → the
hardware kills the wave **without raising an IH**. Consequences, all verified here:
`vkGetDeviceFaultReportsKHR` empty (8/8 hangs; its data source is the fault IH), no kernel
dmesg fault line, `amdgpu.vm_fault_stop=1` is a no-op (its path requires the IH handler),
the kernel's `entry->client_id` never exists, and latched UTCL2/GCVM registers are cleared
by dump time. **Driver-side observability for this fault class is structurally zero on
gfx11** — that is a design property, not an anomaly of our case; it is why this report had
to come with an exclusion matrix instead of a fault trace.

| **driver submission surface** | self-built **debug Mesa** (asserts live) + `RADV_DEBUG=hang` | 10 vendor fault dumps (12 md5-distinct on disk) byte-identical decoded: 3 MDI dispatches, `DATA_ADDR` = args BDA, `COUNT=1530`, `STRIDE=24`, strictly in range, args BO alive; zero asserts over 10 hangs ⟹ address/count/stride/range/BO/descriptor all correct — **the fault is produced at shader runtime, not in the CS** |
| **row-table data contents** | per-frame ndjson blackbox (COUNT vs rows-written, per-segment digests) + in-shader printf self-checks at the task entry (5 predicates) | across 10 rounds: row bytes identical between hung and clean rounds (3 digests = 3 cascades), zero predicate violations — **the data the shader reads is correct** |
| "read never-written memory" family | poison-fill (0xDEADBEEF+off) of descriptor-heap user slots + args ring + cull chain, install-proved every round | 30 rounds, 7 new blobs — **fault address stays exactly 0x0, poison never appears** (whole-investigation cumulative: 11 independent blobs, all at 0x0) |

Speed dependence (the one variable that moves the rate): no network ~64% → ASan build ~50%
→ GPU-AV instrumented **0/6**. Anything that slows the GPU or adds validation *reduces* the
hang rate ⟹ a CPU-submit/GPU-execute phase race, not a poisoned command (a bad command
would not care about speed).

## Two spec violations observed on this same workload

**(1) Mesh entry consuming `DrawIndex` (no task shader) → deterministic fault.**
22/22 rounds, fixed VA `0xbc074a7d3000`, `GCVM_L2_PROTECTION_FAULT_STATUS=0x701431`
(PERMISSION=3, MAPPING_ERROR=0, RW=read, CLIENT_ID=0xa SQC-data), ring-only reset, fully
printed by RADV. Single-variable probes: removing the read (builtin stripped from the SPV
interface) → 0/6; restoring → 2/2; keeping the read but clamping the derived address
in-range → 2/2 (value irrelevant). Details + patch in the companion report.

**(2) Mesh workgroups running beyond the task's `EmitMeshTasksEXT` X.**
The task reads `meshGroupCount` from the (correct) row and calls `EmitMeshTasksEXT(mgc,1,1)`;
the mesh entry then occasionally runs with `groupID.x ≥ mgc` — 60 self-check hits over 35
400-frame rounds (`bits=4`, e.g. row `obj=588 cstart=0 mgc=2 range_count=1` with `slot=2/3`
observed; the hit objects drift from round to round, so it is not a static data defect).
Three probes pin it to the dispatch itself:

| probe | reading |
|---|---|
| CPU-side audit of the actual row bytes before upload (always-on, 64-bit) | silent across all rounds — rows are correct |
| task-stage printf of the row it latched | 565/565 dispatches read `mgc=2` (= exactly what the CPU wrote) |
| mesh-stage self-check | for that same row: `slot=2/3` with `mgc=2`; across all 60 hits the observed `slot` values run 2–16 — the over-shoot amount is not fixed |

and `spirv-dis` confirms `OpEmitMeshTasksEXT %mgc %1 %1` with `%mgc` loaded from the row.
Per `interfaces.adoc` (WorkgroupId) + SPV_EXT_mesh_shader, mesh `WorkgroupId` is bounded by
the dispatching parameters — this workload violates that bound, reading the *neighbouring
object's* cluster entries (legal memory, wrong geometry). We now clamp in the mesh entry
(image-side mitigation), which is why the rate question below matters more than the image.

## Questions

1. Does the CP (or the descriptor-heap path) have any **caching / prefetch semantics for
   indirect args memory** that could make "persistent-mapped buffer, memcpy+flush every
   frame, also bound as a storage buffer" read stale or half-written data under MDI?
2. Given the submission surface is provably correct (above): **where can a 0 base come
   from at shader runtime** on the hardware meshlet path (GC 11.5.1) — descriptor heap GPU-side
   caching? MES queue state after a previous reset? The task→mesh ring-buffer plumbing?
3. Is there **any observability surface for non-retry faults** beyond the devcoredump
   (which only gives the address)? A way to get the client id without a kernel patch?
4. Is `MES failed to respond to msg=RESET` → MODE2 on gfx1151 a **known-broken reset
   path**? Until it is fixed, what is the recommended way to return to a comparable GPU
   state between test rounds (we currently wait for `GPU reset succeeded` + 15 s)?
5. Is the upper bound of mesh `WorkgroupId` (violation (2)) enforced anywhere in the
   task→mesh launch on RDNA3.5, or is it assumed from hardware that does not exist on this
   generation?

## What we can / cannot provide

  engine logs of ~60 rounds; the always-on row audit + shader self-check sources (or the
````

````text
Title: Strix Halo (ASUS TX Air, Radeon 8060S): minute-level recipe for the Variant 2
       "silent hard hang" — writing `profile_peak` killed the machine 2/2 within minutes

(Framework community #82310 follow-up; root-cause-wise this belongs to the SMU command
serialization race AMD confirmed in drm/amd kernel#5171 — filing the recipe where the fix
is landing.)

We run a Vulkan renderer stress matrix on a Strix Halo box and, while preparing an RGP/SQTT
session, stumbled into a **deterministic-feeling, minute-level recipe** for the silent hard
hang that the Framework wiki describes as taking "hours to days" in the field.

## Machine

- ASUS TX Air FA401EA, AMD Radeon 8060S Graphics (RADV STRIX_HALO, gfx1151, PCI 1002:1586)
- kernel 7.2.10 (Gentoo custom build), Mesa 26.2.4 — both `profile_peak` kills happened on
  this kernel; we have not tested the recipe on other kernels
- `softlockup_panic=1` set; pstore/efivars persistent; journald persistent

## Recipe (2 attempts, 2 kills)

```bash
echo profile_peak | sudo tee /sys/class/drm/card0/device/power_dpm_force_performance_level
# then run any sustained GPU workload (ours: a ~120-frame headless Vulkan render pass;
# NOTE: we have NOT tested profile_peak + idle — the GPU load may or may not be required)
```

- Attempt 1 (2026-10-21 15:57): wrote `profile_peak`, ran the engine (120 frames, **no
  tracing involved at all** — the render completed and exited normally). **1–3 minutes
  later the whole machine silently froze.** No way out but a power cycle.
- Attempt 2 (16:3x): `profile_peak` + an SQTT trace session (256 MB buffer) — froze
  silently **during** the run.

## What "silent" means here (this is the informative part)

- journal's last entry = our own `sudo` write to the sysfs file moments earlier; then
  **23 minutes of absolute kernel silence** — no ring timeout, no GPU recovery message,
  no OOPS, no RCU stall;
- `softlockup_panic=1` did **not** fire (so not even the CPU-lockup watchdog path was
  reached — consistent with a bus/SMM-level dead, not a spinning kernel);
- `pstore` empty after the forced reboot (nothing ever panicked — the machine was simply
  unable to die politely).

## Control

Same machine, same day, **hundreds** of GPU-load rounds without touching
`power_dpm_force_performance_level` (left at `auto`): zero silent hangs. (We do have a
*separate*, recoverable Variant-1-class hang from `vkCmdDrawMeshTasksIndirectEXT` + task
shaders — different animal, filed separately, ring-reset-recoverable.)

n=2 with a same-day same-machine control of that size is not a statistics lecture — but it
turns "hours to days, unreproducible" into "minutes, on demand", which should be worth
something to whoever chases the SMU serialization race in #5171.

Side note for anyone else with this SoC: this also means **RGP/SQTT profiling is a landmine
here** — `ac_check_profile_state()` requires a `profile_*` DPM state to arm SQTT, so on this
machine every RGP attempt is a roll of the same dice. (Separately: RADV SQTT on gfx1151
produces a zero-payload trace even when it survives — happy to file that as its own thing.)

## What we can / cannot provide

- Can: exact versions, journal excerpts around both events (the silence itself is the
  artifact), the sysfs state, and — if useful for the fix validation — **more controlled
  reproductions** (each costs a forced power cycle, so please schedule with us); kernel
  parameter / debug-build A/B runs on request.
- Cannot: a core dump of the freeze — there is nothing to dump; by design the machine
  never reaches any error path.
````
