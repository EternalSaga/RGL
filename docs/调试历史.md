## 灰屏问题修复时间线

### 阶段一：Descriptor Heap 基础搭建

1. **替换 BDA 指针运算** — 最初使用 BDA pointer arithmetic，后改为 `[[vk::binding(N, 0)]] StructuredBuffer<T>`，最终改为 `ByteAddressBuffer`（修复 #13）。StructuredBuffer 的 stride 对齐导致静默数据损坏。

2. **创建真实 descriptor heap** — 使用 `VK_BUFFER_USAGE_DESCRIPTOR_HEAP_BIT_EXT`（`vkresources.cppm:96-114`）。

3. **写入 descriptors** — 通过 `vkWriteResourceDescriptorsEXT` 写入 heap slots 8（vertex）和 12（index），避开 heap 起始保留区域。（当时为固定编号，现已动态化为 `reservedSlots() + offset`）

4. **修复 vk-hpp wrapper 类型** — `writeResourceDescriptorsEXT` 需要 `vk::ResourceDescriptorInfoEXT` / `vk::HostAddressRangeEXT`（而非原始 `Vk*` 类型）。

5. **对齐 heapOffset 和 heapArrayStride** — 对齐到 4（`bufferDescriptorAlignment` 的倍数）。

6. **添加 Host→GPU 内存屏障** — `HostWrite` → `ShaderRead`，在 heap 绑定前插入。

7. **修复屏障位置** — `VK_PIPELINE_STAGE_2_HOST_BIT` 不能在 dynamic render pass 内使用。将 barrier + `vkCmdBindResourceHeapEXT` + `vkCmdPushDataEXT` 移至 `vkCmdBeginRendering` 之前。

### 阶段二：修复灰屏（2026-06-24）

8. **修复 heapOffset/heapArrayStride 字节不匹配**（`shader.cppm`）
   `VK_DESCRIPTOR_MAPPING_SOURCE_HEAP_WITH_CONSTANT_OFFSET_EXT` 期望的 `heapOffset` 和 `heapArrayStride` 是**字节**而非 slot 索引。
   修正：`heapOffset = 8` → `8 * descriptorSize`，`heapArrayStride = 4` → `descriptorSize`。
   **效果：** 灰屏解决，渲染输出出现。

9. **修复 MVP 矩阵**（`vkrenderer.cppm:58`）
   修正：`drawArgs_.mvp = glm::mat4(1.0f)` → `proj * view * model`。立方体开始旋转。

10. **修复 StructuredBuffer stride 不匹配**（主修复）
    HLSL `StructuredBuffer<T>` 要求元素 stride ≥16 字节对齐。C++ `Vertex` 为 24 字节（2×float3），GPU 读取 stride 32 字节 → `vertexBuffer[1]` 从 offset 32 读取，但实际数据在 offset 24 → **完全错误的顶点数据** → 几何畸变。
    临时修复：C++ `Vertex` 添加 `float _padding[2]` 填充到 32 字节。

11. **修复索引缓冲类型**（`types.slang:24`）
    `StructuredBuffer<uint>`（16字节 stride）→ `ByteAddressBuffer`，通过 `.Load(offset * 4)` 正确读取 4 字节 `uint32_t` 索引。

12. **修复 colorToDrawBarrier**（`vkrenderer.cppm:143`）
    `srcStageMask` 从 `eColorAttachmentOutput` 改为 `eTopOfPipe`（无前序访问需要同步；acquire semaphore 处理帧间同步）。

13. **彻底替换 StructuredBuffer → ByteAddressBuffer**（`shaders/types.slang:20-24`, `cube.mesh.slang:13-19`, `cube.cppm:10-14`）
    `StructuredBuffer` 的 stride 对齐是根本原因。C++ `Vertex`（24字节）与 GPU stride（32字节）不一致 → 仅 `vertexBuffer[0]` 正确，顶点 1-7 读取错位垃圾数据 → 几何畸变 + 颜色丢失。
    添加 `_padding[2]` 是临时方案 — 数据仍只有 24 字节，padding 包含垃圾值。
    **正确修复：** `ByteAddressBuffer` + 手动 `.Load3(offset)` + 字节偏移计算（`ti * 24`），精确匹配 C++ `sizeof(Vertex)`。移除 C++ `Vertex` 中的 `_padding[2]`。

### 最终状态（已验证工作正常）

- Descriptors 正确写入 heap slots 8（vertex）和 12（index），通过字节对齐的 `heapOffset` 映射
- MVP 矩阵计算后通过 `vkCmdPushDataEXT` 推送
- **顶点和索引缓冲均使用 `ByteAddressBuffer`** — vertex 通过 `.Load3(offset)` 在 `ti * 24` 处访问，index 通过 `.Load(offset * 4)` 访问。C++ `Vertex` 24 字节（无 padding）
- colorToDrawBarrier `srcStageMask` 修正为 `eTopOfPipe`
- **结果：** 立方体正确渲染，旋转正常，8 个不同顶点颜色（每顶点一色：红、绿、蓝、黄、品红、青、白、黑）

## 已解决的争议

### ~~Matrix 布局~~
Slang 面向 Vulkan/SPIR-V 时 `float4x4` 默认 column-major，与 `glm::mat4` 一致。**实验证明：添加 `glm::transpose()` 输出严重畸变** — 立方体塌陷为扁平方块。两端内存布局相同，直接透传。

### ~~Push Data Mapping~~
`[[vk::push_constant]]` 在 descriptor heap 模式下不需要显式 mapping。Spec 明确说明无需构建 pipeline layout。

### ~~StructuredBuffer vs ByteAddressBuffer~~
**Slang 面向 Vulkan 时绝不用 `StructuredBuffer<T>` 处理顶点/索引数据。** `StructuredBuffer` 强制 ≥16 字节 stride 对齐，与 C++ `sizeof` 静默偏离 → 数据损坏。**始终使用 `ByteAddressBuffer` + 手动 `.Load(offset)` — 字节偏移由你控制，始终匹配 C++ `sizeof`。** `scalarBlockLayout` 不影响 StructuredBuffer stride，只影响 UBO 布局规则。

## 维护性改进

### ~~VMA 裸指针生命周期~~（2026-08-01）

**问题：** `VmaBuffer`/`VmaImage` 存储原始 `VmaAllocator*` 指针。AGENTS.md 已记录为已知问题 — 仅在 allocator 生命周期长于所有分配时安全。若 allocator 提前析构，后续 `vmaDestroyBuffer`/`vmaDestroyImage` 调用将读悬空指针 → UB。

**方案：** 引入 `SharedAllocator = std::shared_ptr<AllocatorControlBlock>` 共享所有权。

- `AllocatorControlBlock` 包装 `VmaAllocator` 句柄
- `VmaAllocatorRAII` 在构造函数中创建 `shared_ptr`（带 `vmaDestroyAllocator` 自定义删除器）
- 所有 `createBufferWithAddress`/`createImage`/`createDescriptorHeap` 方法将 `allocatorBlock` 的副本传递给子对象
- `VmaBuffer`/`VmaImage` 析构时通过 `allocatorBlock->handle` 访问，保证 allocator 在最后一个对象析构前始终有效
- `rlstd.cppm` 添加 `using std::shared_ptr;` 以供模块间使用

**效果：** 消除了 AGENTS.md 中的已知问题 2.2。无论析构顺序如何，allocator 仅在最后一个 VMA 对象析构时才被销毁。

- `tools/generator.cppm` 新增 `renderTemplate()` — 泛化的代码生成函数
- `tools/reflection_tool.cpp` 新增 `render` 子命令
- CMake custom command: `reflection_tool render --json features_config.json → features_generated.cppm`
- `features.cppm` 缩减为 67 行，仅保留 `checkDeviceExtensions()` / `getDeviceExtensions()`，通过 `export import features_generated;` 重新导出

**效果：** `features.cppm` 从 217 行 → 67 行。添加新 feature 只需在 JSON 中新增一行。

### ~~WriteDescriptor 静默失败~~（2026-08-01）

**问题：** `vkresources.cppm` 中的 `writeDescriptors()` 在 `getSlotCpuAddress` 失败时静默 `return`，不向调用者报告错误。构造函数无法感知 descriptor 写入失败，导致渲染错误时几无提示（灰屏）。

**方案：** 将 `if (!result) return;` 改为 `throw std::runtime_error(result.error().describe())`，与 `recreateDepthImage` 等方法保持一致的错误处理模式。构造函数通过 `main.cpp` 的 `try-catch` 统一处理异常。

### ~~Trackball 相机"鬼畜旋转"~~（2026-08-22）

**问题：** Phase 1 引入 trackball 相机后，用户反馈"稍微拖动几个像素 cube 就消失"，随后是"疯狂鬼畜旋转"。

**排查（3 轮）：**

1. **误判 Wayland 巨型增量** — 最初以为是 Wayland 合并 pointer 事件下发超大 delta，加了 ±100px/帧 clamp。症状从"瞬间消失"变为"快速消失"，方向对但没到根。
2. **发现相机模型错误** — 用户指出"trackball 下相机应该绕 cube 转圈"。检查实现：cameraSystem 是**原地转朝向**（position 钉死，yaw/pitch 旋转），任何旋转都让目标立刻出视野轴。重写为真轨道：旋转 `position - target` 偏移向量（yaw 绕世界 Y、pitch 绕相机右轴），再由新位置反推 yaw/pitch 保持朝向 target，object 恒居屏中心。
3. **日志定位真根因（SDL3 API 误用）** — 限幅触发的 debug 日志显示"巨大 delta"形态异常：`(260, 367) → (255, 370)` 逐帧缓慢漂移 —— 这是**指针在窗口内的绝对位置**，不是增量。查 `SDL3/SDL_events.h:461-464`：SDL3 的 `event.motion.x/y` 是**窗口内绝对坐标**，相对增量在 **`xrel/yrel`**（SDL2 时代 x/y 即绝对坐标的习惯让人误以为 x/y 是 delta）。把 `event.motion.x/y` 当增量累加 → 相机每帧按"指针位置"旋转 ≈73°/帧 → 鬼畜。改用 `xrel/yrel` 后修复。

**教训：**

- **SDL3 鼠标事件：增量用 `motion.xrel/yrel`，`motion.x/y` 是窗口内绝对坐标，永远不要当 delta 用。**
- 相机"目标消失"类 bug 先查**相机模型**（原地转 vs 绕 target 公转），再查输入数据；日志里的 delta 形态（恒定巨大 + 缓慢漂移 = 绝对位置）是重要线索。
- 输入增量 clamp（±100px/帧，`camera.cppm`）保留作尖峰保险，与根因无关但防真异常。

## 2026-09-02：编译提速二期——2m2s → 31.1s，以及"为什么惊讶"

`just profile-fast`（clean 后全量）时间线：**137.8s**（一期起点）→ 122.0s（一期：GMF 收敛 +
依赖图解耦，commit `1a6ffce`）→ 112.2s（二期 A：11 模块接口/实现单元拆分）→ **44.5s**
（二期 B：rlvk 具名模块，`3736251`）→ **31.1s**（反射管线解耦，`4a1a661`）。
user CPU 4m33s → 1m57s（-57%）——**全项目每个模块重复解析 vulkan.hpp 就是最大的那件事**。

**惊讶记录**：B（rlvk）预估 -8~12s，实测 **-68s**，当场 WOW。复盘为什么模型错：

1. **把 3.1s/TU 当成了 B 的全部收益**。3.1s 只是纯文本解析（vkerror 对照实验的量）；hpp 在
   每个 TU 里还附带：模板隐式实例化、以及 **WriteAST 连带序列化**——模块接口导出实体凡引用
   vk:: 类型，该类型所在的 hpp 上下文被一并拖进 BMI。rlvk 后引用变 BMI ID 直连，两头都省。
2. **收益不在并行区而在串行链上复利**。链首四节点实测各降 ~6-10s：vkinstance 7.4→1.2、
   vkdevice 10.0→1.3、vkswapchain 10.5→1.4、vkresources 13.2→2.6，合计 -34s 全落在关键路径
   （墙钟 ≈ 关键链长；并行区再省也不掉墙钟）。预估时按"15 TU × 3s 均摊"，没建模"hpp 成本
   集中在链首串行节点"这一分布事实。
3. 教训：**估编译收益要按关键路径算，不按 CPU 总量算；测"头成本"要用真实消费 TU 的
   -ftime-trace（Frontend + WriteAST 两项），别拿单文件对照实验外推。**

A（接口/实现拆分）本身只值 -7s（函数体移出 BMI 的收益被新实现的 entt 头解析吃回去一半）——
它是必要铺垫（接口面收窄后 B 的 WriteAST 复利才成立），不是主角。

**二期坑档（append-only）**：

- **clang 不给 partition implementation unit 隐式 import 主接口**（[cpp.import.module] 标准
  文本两实现都该有，GCC 有、clang 无）——`module xxx:impl;` 第一行必须显式 `import xxx;`，
  症状"类名 undeclared"。
- **CMake 4.3 拒绝 FILE_SET 里的纯实现单元**（`module xxx;` "does not provide a module
  interface unit or partition"）→ 用 partition（`module xxx:impl;`）形态。
- GMF 掏空暴露 **rlstd 历史洞**：此前每 TU 靠 vulkan.hpp 传递 include 兜底 STL 自由运算符与
  全局名（`uint32_t`、`it != end`、`ifstream`、`getenv`…）；BMI 只带类本体，namespace 作用域
  自由运算符（含 `__gnu_cxx` 迭代器比较）不序列化 → 全部补进 rlstd 导出（教训已写进 AGENTS
  规范：rlstd 必须是"完整可用面"的唯一来源）。
- **vulkan.hpp 的 namespace 作用域 Flags 位运算符**（`operator&|^~`）同理必须逐个
  `export using` 进 rlvk，否则 `a | b` 无候选；`operator&=/|=` 在 vk 不存在（Flags 成员函数）。
- **本机 CMake 4.3.4 的 `file(TIMESTAMP)` 对任何存在文件恒返回空串**（Gentoo 构建异常，实测
  三路径全空）——新鲜度判定改用输入 **SHA1 清单**（`cmake/ReflectionManifest.cmake`），
  顺带比 mtime 语义更强（touch 噪声不误报、改动零漏报）。
- add_custom_target/command 的 `-DPAIRS=...` 命令行参数会被 CMake 按 `|`/`,`/`;` 拆分转义，
  复杂参数一律经 `file(GENERATE)` 落地成 .cmake 文件再 `-D*_FILE` 传入。
- 反射工具链的 custom command 若 DEPENDS 含工具 exe，clean 后 exe 缺失 → 命令必判过期 →
  产物重写 → 下游全量重编（14s 串行前缀的根因）；解法 = 产物提交 + 显式 `just reflect` +
  哈希守卫，工具链 `EXCLUDE_FROM_ALL`。

## 2026-09-02：edS3 depthClip "VVL 误报"实为真违规（深挖推翻，已修复）

**旧结论（错）**：`vkCmdSetDepthClipEnableEXT` 每帧报 VVL `VUID-…-depthClipEnable-07451`

   ——查的就是旧扩展 feature；上面 09423 才查 `extendedDynamicState3DepthClipEnable`（两 VUID
   分管两 feature）。`device_features.cpp` 两字段分别解析自两 sType。v1.4.359/main 检查未变。
3. **vulkaninfo**：RADV `VK_EXT_depth_clip_enable: revision 1`、`depthClipEnable = true`（能开，app 漏开）。

**根因**：两个 feature 名都含 "depthClipEnable" 子串，此前只 grep 到自己启用的 edS3

**修复**：`features_config.json` optional 加 `depthClipBase`（探测 `VK_EXT_depth_clip_enable`）
→ `vkdevice.cppm` 条件链接其 feature struct + `features.cppm` 同启扩展 + `rlvk` 补 `vk::PhysicalDeviceDepthClipEnableFeaturesEXT`。
注：`depthClipDynamic` 门（vkrenderer）实际仍按单探测位 `optionalFeatures.depthClipEnable`（edS3）——"门 = eds3 && base"仅见于提交信息/调研 §12.3 勘误，代码未落地；RADV 两扩展同暴露故行为正确，严格兑现"缺一即不调"需把门改为 `depthClipEnable && depthClipBase`（未做）。
**验证**：headless 冒烟 `was not enabled` 报错归零（此前每帧刷屏），且 `VK_EXT_depth_clip_enable`
出现在启用列表——命令仍实调、0 报错源于底座补齐而非退化成 no-op。

**教训**：VVL feature 类报错，先精确锚定 VUID 引用的**那个 sType/字段**（查 spec 锚点或 VVL
`enabled_features.X` 的 X 名），别被相似命名带偏——"某个含该子串的 struct 在链里 = TRUE" ≠
"被检查的那个 feature 启用了"。同名/近名 feature（edS3 的 extendedDynamicState3DepthClipEnable
vs 旧扩展的 depthClipEnable）是本次误诊的全部原因。

## 2026-09-08：截图回归基线跨日漂移（±1 LSB）——BIT-IDENTICAL 比对法修正

**现象**：重构清理批次 1（纯行为保持改动）验证时，新二进制 forward/deferred 截图与前一晚二进制
截图差 ~1000 像素（白树 dither 叶缘，±1/±2 LSB）。

**隔离实验**（同环境当日）：① 同一二进制连跑两次 = 位级一致（运行确定）；② `git stash` 回
HEAD 源码全量重建 vs commit-1 改动源码全量重建 = **位级一致**（改动零像素影响，实锤）；③ 两者
与前一晚二进制产物 = ±1 噪声（同源码重建也复现）。驱动（libvulkan_radeon 8/28）与工具链未更新、
`MESA_SHADER_CACHE_DISABLE` 无影响。

**结论**：噪声源 = **增量构建残留 .o vs 全量重建 codegen 微差**（C++20 modules 下 clang 内联/FMA
决策对 BMI 重建状态敏感，CPU 侧 mvp ±1ulp 放大于高频纹理边缘）。非代码 bug、非驱动 bug。

**规约修正**：BIT-IDENTICAL 验收以**同会话双构建比对**为准（stash 基线构建 vs 改动构建）；
跨日/跨构建形态比对只作目检参考，出现 ±1 LSB 叶缘级噪声不判回归。

## 2026-09-10：三驱动排查——NVIDIA DGC 黑屏根因 + DrawArgs 彻底 bindless 化（存疑未闭环）

**背景**：Phase 7b 批次 5 的 DGC 路径（`vkCmdExecuteGeneratedCommandsEXT`）此前只在 RADV 编译绿但**从未运行时实测**（RADV graphics 侧 graphicsIndirect=false → 走读回重放）。三驱动排查首次在 NVIDIA（RTX 5090 / 610.57.04 / GB202）跑通 DGC，立即黑屏。

**排查链**（Aftermath GPU crash dump + 逐层 bisect，全部证据在案）：
1. **VVL 首层违规**（应用侧真 bug，已修）：PUSH_DATA updateRange.stageFlags 须 `VK_SHADER_STAGE_ALL`（11333）；DRAW_MESH_TASKS token 须 mesh+task 双 feature 启用（11126，故 features_config 加 `taskShader`）；execution set `pInitialShaders` 须 shaderCount>0 且各元素 stage 唯一（11023，改"初始=首条目 frag+mesh + 建后 update 全 2N 槽"）；preprocess/序列/计数 buffer 补 PREPROCESS_BUFFER/INDIRECT_BUFFER/DEVICE_ADDRESS usage（bit-31 usage 走 flags2 pNext）。
2. **定性崩溃性质**：开 `VK_NV_device_diagnostics_config`（flags=15）后 Aftermath dump 显示 `Device state: Reset / Engine reset`，无 PageFaultInfo、无 active shader，最后一个 automatic checkpoint = `NotStarted`，CPU 栈落在 `Renderer::drawFrame`。结合内核 `Xid 109 CTX SWITCH TIMEOUT` = **GPU 在 DGC 命令生成阶段挂死被 watchdog 复位**，非内存错误、非 shader 死循环（shader 从未跑起）。
3. **规模定位**（bisect env 剥离，以"是否 DeviceLost"为自动判据）：单序列 DGC **像素级渲染完全正确**（截图验证）→ 基础契约全对；去 PUSH_DATA token（仅 EXECUTION_SET+DRAW）全 1591 序列**活**；含 push token 的任意组合**崩**。
4. **尺寸相关性**（初步结论，**存疑见下**）：固定 1591 序列下 push 字节数阈值 83/84；固定 100B 下序列数阈值 ~112/120。→ 推断"总 push 字节 ≈ size×count"超某内部上限即挂死。

**处置**：顺着项目 bindless 原则把 **DrawArgs 彻底瘦身至仅 `objectIndex`（4B push）**——mvp → scene data per-object MVP 表（`readObjectMvp`）、baseColor/roughnessMetallic/totalTriangles/vertexOffset → per-object 材质/几何表（`readObjectDraw`），均按 objectIndex 索引、CPU 每帧写同一份值（位级与旧 push 路径一致，无 shader 端矩阵乘法）。顺带踩坑：Slang `float4x4(c0,c1,c2,c3)` 构造按**行**填（HLSL 语义），列主序内存读成转置 → 建筑炸形（地面近似对称侥幸正常），改用 `ObjectMatrix`+列组合 `clipPos` 规避。结果：NV 全量 1591 序列 DGC 不崩、渲染正确；RADV replay 画面与基线一致。

**⚠️ 根因存疑（用户明确保留意见，未闭环）**：`push 字节数 × 序列数` 这个阈值规律**太邪门**——NV 是 DGC（EXT 由 NV 主导 promote）的最初推手，官方 `vk_device_generated_cmds` 示例跑了多年，理应有成熟实现，不该有"push 超 80B 多序列就挂死"这种弱智级 bug。因此**不确信 push 尺寸是真正根因**，可能只是某个更底层机制（execution set 内容 × 序列数 × preprocess 内部 staging？）的**共线表象**。已做的 bindless 化无论如何是无害且符合架构语义的正当改动，予以保留；但**真正的 NV DGC 挂死机理留待以后复查**（候选实验：官方示例式 PUSH_CONSTANT+真 layout 已试仍崩；显式两段 preprocess 因 VUID-renderpass 未干净测；分块 execute 规避未做）。排查工具 Aftermath 接线保留为编译期开关 `-DRGL_AFTERMATH=ON`（默认关）。

**验证**：核显 headless 截图 = 基线（建筑/草地/树/天空全对）；NV 窗口 llm_debug 截图 frame 10 = 同画面、零 error、reconcile 1571=1571、DGC 全量不崩。Aftermath ON/OFF 双态编译绿。
