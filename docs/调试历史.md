## 灰屏问题修复时间线

### 阶段一：Descriptor Heap 基础搭建

1. **替换 BDA 指针运算** — 最初使用 BDA pointer arithmetic，后改为 `[[vk::binding(N, 0)]] StructuredBuffer<T>`，最终改为 `ByteAddressBuffer`（修复 #13）。StructuredBuffer 的 stride 对齐导致静默数据损坏。

2. **创建真实 descriptor heap** — 使用 `VK_BUFFER_USAGE_DESCRIPTOR_HEAP_BIT_EXT`（`vkresources.cppm:96-114`）。

3. **写入 descriptors** — 通过 `vkWriteResourceDescriptorsEXT` 写入 heap slots 8（vertex）和 12（index），避开 heap 起始保留区域。（当时为固定编号，现已动态化为 `reservedSlots() + offset`）

4. **修复 vk-hpp wrapper 类型** — `writeResourceDescriptorsEXT` 需要 `vk::ResourceDescriptorInfoEXT` / `vk::HostAddressRangeEXT`（而非原始 `Vk*` 类型）。

5. **对齐 heapOffset 和 heapArrayStride** — 对齐到 4（`bufferDescriptorAlignment` 的倍数）。

6. **添加 Host→GPU 内存屏障** — `HostWrite` → `ShaderRead`，在 heap 绑定前插入。

7. **修复屏障位置** — `VK_PIPELINE_STAGE_2_HOST_BIT` 不能在 dynamic render pass 内使用。将 barrier + `vkCmdBindResourceHeapEXT` + `vkCmdPushDataEXT` 移至 `vkCmdBeginRendering` 之前。

### 阶段二：修复灰屏（2026-06-24）

8. **修复 heapOffset/heapArrayStride 字节不匹配**（`shader.cppm`）
   `VK_DESCRIPTOR_MAPPING_SOURCE_HEAP_WITH_CONSTANT_OFFSET_EXT` 期望的 `heapOffset` 和 `heapArrayStride` 是**字节**而非 slot 索引。
   修正：`heapOffset = 8` → `8 * descriptorSize`，`heapArrayStride = 4` → `descriptorSize`。
   **效果：** 灰屏解决，渲染输出出现。

9. **修复 MVP 矩阵**（`vkrenderer.cppm:58`）
   修正：`drawArgs_.mvp = glm::mat4(1.0f)` → `proj * view * model`。立方体开始旋转。

10. **修复 StructuredBuffer stride 不匹配**（主修复）
    HLSL `StructuredBuffer<T>` 要求元素 stride ≥16 字节对齐。C++ `Vertex` 为 24 字节（2×float3），GPU 读取 stride 32 字节 → `vertexBuffer[1]` 从 offset 32 读取，但实际数据在 offset 24 → **完全错误的顶点数据** → 几何畸变。
    临时修复：C++ `Vertex` 添加 `float _padding[2]` 填充到 32 字节。

11. **修复索引缓冲类型**（`types.slang:24`）
    `StructuredBuffer<uint>`（16字节 stride）→ `ByteAddressBuffer`，通过 `.Load(offset * 4)` 正确读取 4 字节 `uint32_t` 索引。

12. **修复 colorToDrawBarrier**（`vkrenderer.cppm:143`）
    `srcStageMask` 从 `eColorAttachmentOutput` 改为 `eTopOfPipe`（无前序访问需要同步；acquire semaphore 处理帧间同步）。

13. **彻底替换 StructuredBuffer → ByteAddressBuffer**（`shaders/types.slang:20-24`, `cube.mesh.slang:13-19`, `cube.cppm:10-14`）
    `StructuredBuffer` 的 stride 对齐是根本原因。C++ `Vertex`（24字节）与 GPU stride（32字节）不一致 → 仅 `vertexBuffer[0]` 正确，顶点 1-7 读取错位垃圾数据 → 几何畸变 + 颜色丢失。
    添加 `_padding[2]` 是临时方案 — 数据仍只有 24 字节，padding 包含垃圾值。
    **正确修复：** `ByteAddressBuffer` + 手动 `.Load3(offset)` + 字节偏移计算（`ti * 24`），精确匹配 C++ `sizeof(Vertex)`。移除 C++ `Vertex` 中的 `_padding[2]`。

### 最终状态（已验证工作正常）

- Descriptors 正确写入 heap slots 8（vertex）和 12（index），通过字节对齐的 `heapOffset` 映射
- MVP 矩阵计算后通过 `vkCmdPushDataEXT` 推送
- **顶点和索引缓冲均使用 `ByteAddressBuffer`** — vertex 通过 `.Load3(offset)` 在 `ti * 24` 处访问，index 通过 `.Load(offset * 4)` 访问。C++ `Vertex` 24 字节（无 padding）
- colorToDrawBarrier `srcStageMask` 修正为 `eTopOfPipe`
- **结果：** 立方体正确渲染，旋转正常，8 个不同顶点颜色（每顶点一色：红、绿、蓝、黄、品红、青、白、黑）

## 已解决的争议

### ~~Matrix 布局~~
Slang 面向 Vulkan/SPIR-V 时 `float4x4` 默认 column-major，与 `glm::mat4` 一致。**实验证明：添加 `glm::transpose()` 输出严重畸变** — 立方体塌陷为扁平方块。两端内存布局相同，直接透传。

### ~~Push Data Mapping~~
`[[vk::push_constant]]` 在 descriptor heap 模式下不需要显式 mapping。Spec 明确说明无需构建 pipeline layout。

### ~~StructuredBuffer vs ByteAddressBuffer~~
**Slang 面向 Vulkan 时绝不用 `StructuredBuffer<T>` 处理顶点/索引数据。** `StructuredBuffer` 强制 ≥16 字节 stride 对齐，与 C++ `sizeof` 静默偏离 → 数据损坏。**始终使用 `ByteAddressBuffer` + 手动 `.Load(offset)` — 字节偏移由你控制，始终匹配 C++ `sizeof`。** `scalarBlockLayout` 不影响 StructuredBuffer stride，只影响 UBO 布局规则。

## 维护性改进

### ~~VMA 裸指针生命周期~~（2026-08-01）

**问题：** `VmaBuffer`/`VmaImage` 存储原始 `VmaAllocator*` 指针。AGENTS.md 已记录为已知问题 — 仅在 allocator 生命周期长于所有分配时安全。若 allocator 提前析构，后续 `vmaDestroyBuffer`/`vmaDestroyImage` 调用将读悬空指针 → UB。

**方案：** 引入 `SharedAllocator = std::shared_ptr<AllocatorControlBlock>` 共享所有权。

- `AllocatorControlBlock` 包装 `VmaAllocator` 句柄
- `VmaAllocatorRAII` 在构造函数中创建 `shared_ptr`（带 `vmaDestroyAllocator` 自定义删除器）
- 所有 `createBufferWithAddress`/`createImage`/`createDescriptorHeap` 方法将 `allocatorBlock` 的副本传递给子对象
- `VmaBuffer`/`VmaImage` 析构时通过 `allocatorBlock->handle` 访问，保证 allocator 在最后一个对象析构前始终有效
- `rlstd.cppm` 添加 `using std::shared_ptr;` 以供模块间使用

**效果：** 消除了 AGENTS.md 中的已知问题 2.2。无论析构顺序如何，allocator 仅在最后一个 VMA 对象析构时才被销毁。

- `features.cppm` 缩减为 67 行，仅保留 `checkDeviceExtensions()` / `getDeviceExtensions()`，通过 `export import features_generated;` 重新导出

**效果：** `features.cppm` 从 217 行 → 67 行。添加新 feature 只需在 JSON 中新增一行。

### ~~WriteDescriptor 静默失败~~（2026-08-01）

**问题：** `vkresources.cppm` 中的 `writeDescriptors()` 在 `getSlotCpuAddress` 失败时静默 `return`，不向调用者报告错误。构造函数无法感知 descriptor 写入失败，导致渲染错误时几无提示（灰屏）。

**方案：** 将 `if (!result) return;` 改为 `throw std::runtime_error(result.error().describe())`，与 `recreateDepthImage` 等方法保持一致的错误处理模式。构造函数通过 `main.cpp` 的 `try-catch` 统一处理异常。

### ~~Trackball 相机"鬼畜旋转"~~（2026-08-22）

**问题：** Phase 1 引入 trackball 相机后，用户反馈"稍微拖动几个像素 cube 就消失"，随后是"疯狂鬼畜旋转"。

**排查（3 轮）：**

1. **误判 Wayland 巨型增量** — 最初以为是 Wayland 合并 pointer 事件下发超大 delta，加了 ±100px/帧 clamp。症状从"瞬间消失"变为"快速消失"，方向对但没到根。
2. **发现相机模型错误** — 用户指出"trackball 下相机应该绕 cube 转圈"。检查实现：cameraSystem 是**原地转朝向**（position 钉死，yaw/pitch 旋转），任何旋转都让目标立刻出视野轴。重写为真轨道：旋转 `position - target` 偏移向量（yaw 绕世界 Y、pitch 绕相机右轴），再由新位置反推 yaw/pitch 保持朝向 target，object 恒居屏中心。
3. **日志定位真根因（SDL3 API 误用）** — 限幅触发的 debug 日志显示"巨大 delta"形态异常：`(260, 367) → (255, 370)` 逐帧缓慢漂移 —— 这是**指针在窗口内的绝对位置**，不是增量。查 `SDL3/SDL_events.h:461-464`：SDL3 的 `event.motion.x/y` 是**窗口内绝对坐标**，相对增量在 **`xrel/yrel`**（SDL2 时代 x/y 即绝对坐标的习惯让人误以为 x/y 是 delta）。把 `event.motion.x/y` 当增量累加 → 相机每帧按"指针位置"旋转 ≈73°/帧 → 鬼畜。改用 `xrel/yrel` 后修复。

**教训：**

- **SDL3 鼠标事件：增量用 `motion.xrel/yrel`，`motion.x/y` 是窗口内绝对坐标，永远不要当 delta 用。**
- 相机"目标消失"类 bug 先查**相机模型**（原地转 vs 绕 target 公转），再查输入数据；日志里的 delta 形态（恒定巨大 + 缓慢漂移 = 绝对位置）是重要线索。
- 输入增量 clamp（±100px/帧，`camera.cppm`）保留作尖峰保险，与根因无关但防真异常。

## 2026-09-02：编译提速二期——2m2s → 31.1s，以及"为什么惊讶"

`just profile-fast`（clean 后全量）时间线：**137.8s**（一期起点）→ 122.0s（一期：GMF 收敛 +
依赖图解耦，commit `1a6ffce`）→ 112.2s（二期 A：11 模块接口/实现单元拆分）→ **44.5s**
（二期 B：rlvk 具名模块，`3736251`）→ **31.1s**（反射管线解耦，`4a1a661`）。
user CPU 4m33s → 1m57s（-57%）——**全项目每个模块重复解析 vulkan.hpp 就是最大的那件事**。

**惊讶记录**：B（rlvk）预估 -8~12s，实测 **-68s**，当场 WOW。复盘为什么模型错：

1. **把 3.1s/TU 当成了 B 的全部收益**。3.1s 只是纯文本解析（vkerror 对照实验的量）；hpp 在
   每个 TU 里还附带：模板隐式实例化、以及 **WriteAST 连带序列化**——模块接口导出实体凡引用
   vk:: 类型，该类型所在的 hpp 上下文被一并拖进 BMI。rlvk 后引用变 BMI ID 直连，两头都省。
2. **收益不在并行区而在串行链上复利**。链首四节点实测各降 ~6-10s：vkinstance 7.4→1.2、
   vkdevice 10.0→1.3、vkswapchain 10.5→1.4、vkresources 13.2→2.6，合计 -34s 全落在关键路径
   （墙钟 ≈ 关键链长；并行区再省也不掉墙钟）。预估时按"15 TU × 3s 均摊"，没建模"hpp 成本
   集中在链首串行节点"这一分布事实。
3. 教训：**估编译收益要按关键路径算，不按 CPU 总量算；测"头成本"要用真实消费 TU 的
   -ftime-trace（Frontend + WriteAST 两项），别拿单文件对照实验外推。**

A（接口/实现拆分）本身只值 -7s（函数体移出 BMI 的收益被新实现的 entt 头解析吃回去一半）——
它是必要铺垫（接口面收窄后 B 的 WriteAST 复利才成立），不是主角。

**二期坑档（append-only）**：

- **clang 不给 partition implementation unit 隐式 import 主接口**（[cpp.import.module] 标准
  文本两实现都该有，GCC 有、clang 无）——`module xxx:impl;` 第一行必须显式 `import xxx;`，
  症状"类名 undeclared"。
- **CMake 4.3 拒绝 FILE_SET 里的纯实现单元**（`module xxx;` "does not provide a module
  interface unit or partition"）→ 用 partition（`module xxx:impl;`）形态。
- GMF 掏空暴露 **rlstd 历史洞**：此前每 TU 靠 vulkan.hpp 传递 include 兜底 STL 自由运算符与
  全局名（`uint32_t`、`it != end`、`ifstream`、`getenv`…）；BMI 只带类本体，namespace 作用域
  自由运算符（含 `__gnu_cxx` 迭代器比较）不序列化 → 全部补进 rlstd 导出（教训已写进 AGENTS
  规范：rlstd 必须是"完整可用面"的唯一来源）。
- **vulkan.hpp 的 namespace 作用域 Flags 位运算符**（`operator&|^~`）同理必须逐个
  `export using` 进 rlvk，否则 `a | b` 无候选；`operator&=/|=` 在 vk 不存在（Flags 成员函数）。
- **本机 CMake 4.3.4 的 `file(TIMESTAMP)` 对任何存在文件恒返回空串**（Gentoo 构建异常，实测
  三路径全空）——新鲜度判定改用输入 **SHA1 清单**（`cmake/ReflectionManifest.cmake`），
  顺带比 mtime 语义更强（touch 噪声不误报、改动零漏报）。
- add_custom_target/command 的 `-DPAIRS=...` 命令行参数会被 CMake 按 `|`/`,`/`;` 拆分转义，
  复杂参数一律经 `file(GENERATE)` 落地成 .cmake 文件再 `-D*_FILE` 传入。
- 反射工具链的 custom command 若 DEPENDS 含工具 exe，clean 后 exe 缺失 → 命令必判过期 →
  产物重写 → 下游全量重编（14s 串行前缀的根因）；解法 = 产物提交 + 显式 `just reflect` +
  哈希守卫，工具链 `EXCLUDE_FROM_ALL`。

## 2026-09-02：edS3 depthClip "VVL 误报"实为真违规（深挖推翻，已修复）

**旧结论（错）**：`vkCmdSetDepthClipEnableEXT` 每帧报 VVL `VUID-…-depthClipEnable-07451`

   分管两 feature）。`device_features.cpp` 两字段分别解析自两 sType。v1.4.359/main 检查未变。
3. **vulkaninfo**：RADV `VK_EXT_depth_clip_enable: revision 1`、`depthClipEnable = true`（能开，app 漏开）。

**修复**：`features_config.json` optional 加 `depthClipBase`（探测 `VK_EXT_depth_clip_enable`）
→ `vkdevice.cppm` 条件链接其 feature struct + `features.cppm` 同启扩展 + `rlvk` 补 `vk::PhysicalDeviceDepthClipEnableFeaturesEXT`。
注：`depthClipDynamic` 门（vkrenderer）实际仍按单探测位 `optionalFeatures.depthClipEnable`（edS3）——"门 = eds3 && base"仅见于提交信息/调研 §12.3 勘误，代码未落地；RADV 两扩展同暴露故行为正确，严格兑现"缺一即不调"需把门改为 `depthClipEnable && depthClipBase`（未做）。

**教训**：VVL feature 类报错，先精确锚定 VUID 引用的**那个 sType/字段**（查 spec 锚点或 VVL
`enabled_features.X` 的 X 名），别被相似命名带偏——"某个含该子串的 struct 在链里 = TRUE" ≠
"被检查的那个 feature 启用了"。同名/近名 feature（edS3 的 extendedDynamicState3DepthClipEnable
vs 旧扩展的 depthClipEnable）是本次误诊的全部原因。

## 2026-09-08：截图回归基线跨日漂移（±1 LSB）——BIT-IDENTICAL 比对法修正

**现象**：重构清理批次 1（纯行为保持改动）验证时，新二进制 forward/deferred 截图与前一晚二进制
截图差 ~1000 像素（白树 dither 叶缘，±1/±2 LSB）。

**隔离实验**（同环境当日）：① 同一二进制连跑两次 = 位级一致（运行确定）；② `git stash` 回
HEAD 源码全量重建 vs commit-1 改动源码全量重建 = **位级一致**（改动零像素影响，实锤）；③ 两者
与前一晚二进制产物 = ±1 噪声（同源码重建也复现）。驱动（libvulkan_radeon 8/28）与工具链未更新、
`MESA_SHADER_CACHE_DISABLE` 无影响。

**结论**：噪声源 = **增量构建残留 .o vs 全量重建 codegen 微差**（C++20 modules 下 clang 内联/FMA
决策对 BMI 重建状态敏感，CPU 侧 mvp ±1ulp 放大于高频纹理边缘）。非代码 bug、非驱动 bug。

**规约修正**：BIT-IDENTICAL 验收以**同会话双构建比对**为准（stash 基线构建 vs 改动构建）；
跨日/跨构建形态比对只作目检参考，出现 ±1 LSB 叶缘级噪声不判回归。

## 2026-09-10：三驱动排查——NVIDIA DGC 黑屏根因 + DrawArgs 彻底 bindless 化（存疑未闭环）

**背景**：Phase 7b 批次 5 的 DGC 路径（`vkCmdExecuteGeneratedCommandsEXT`）此前只在 RADV 编译绿但**从未运行时实测**（RADV graphics 侧 graphicsIndirect=false → 走读回重放）。三驱动排查首次在 NVIDIA（RTX 5090 / 610.57.04 / GB202）跑通 DGC，立即黑屏。

**排查链**（Aftermath GPU crash dump + 逐层 bisect，全部证据在案）：
1. **VVL 首层违规**（应用侧真 bug，已修）：PUSH_DATA updateRange.stageFlags 须 `VK_SHADER_STAGE_ALL`（11333）；DRAW_MESH_TASKS token 须 mesh+task 双 feature 启用（11126，故 features_config 加 `taskShader`）；execution set `pInitialShaders` 须 shaderCount>0 且各元素 stage 唯一（11023，改"初始=首条目 frag+mesh + 建后 update 全 2N 槽"）；preprocess/序列/计数 buffer 补 PREPROCESS_BUFFER/INDIRECT_BUFFER/DEVICE_ADDRESS usage（bit-31 usage 走 flags2 pNext）。
2. **定性崩溃性质**：开 `VK_NV_device_diagnostics_config`（flags=15）后 Aftermath dump 显示 `Device state: Reset / Engine reset`，无 PageFaultInfo、无 active shader，最后一个 automatic checkpoint = `NotStarted`，CPU 栈落在 `Renderer::drawFrame`。结合内核 `Xid 109 CTX SWITCH TIMEOUT` = **GPU 在 DGC 命令生成阶段挂死被 watchdog 复位**，非内存错误、非 shader 死循环（shader 从未跑起）。
3. **规模定位**（bisect env 剥离，以"是否 DeviceLost"为自动判据）：单序列 DGC **像素级渲染完全正确**（截图验证）→ 基础契约全对；去 PUSH_DATA token（仅 EXECUTION_SET+DRAW）全 1591 序列**活**；含 push token 的任意组合**崩**。
4. **尺寸相关性**（初步结论，**存疑见下**）：固定 1591 序列下 push 字节数阈值 83/84；固定 100B 下序列数阈值 ~112/120。→ 推断"总 push 字节 ≈ size×count"超某内部上限即挂死。

**处置**：顺着项目 bindless 原则把 **DrawArgs 彻底瘦身至仅 `objectIndex`（4B push）**——mvp → scene data per-object MVP 表（`readObjectMvp`）、baseColor/roughnessMetallic/totalTriangles/vertexOffset → per-object 材质/几何表（`readObjectDraw`），均按 objectIndex 索引、CPU 每帧写同一份值（位级与旧 push 路径一致，无 shader 端矩阵乘法）。顺带踩坑：Slang `float4x4(c0,c1,c2,c3)` 构造按**行**填（HLSL 语义），列主序内存读成转置 → 建筑炸形（地面近似对称侥幸正常），改用 `ObjectMatrix`+列组合 `clipPos` 规避。结果：NV 全量 1591 序列 DGC 不崩、渲染正确；RADV replay 画面与基线一致。

**⚠️ 根因存疑（用户明确保留意见，未闭环）**：`push 字节数 × 序列数` 这个阈值规律**太邪门**——NV 是 DGC（EXT 由 NV 主导 promote）的最初推手，官方 `vk_device_generated_cmds` 示例跑了多年，理应有成熟实现，不该有"push 超 80B 多序列就挂死"这种弱智级 bug。因此**不确信 push 尺寸是真正根因**，可能只是某个更底层机制（execution set 内容 × 序列数 × preprocess 内部 staging？）的**共线表象**。已做的 bindless 化无论如何是无害且符合架构语义的正当改动，予以保留；但**真正的 NV DGC 挂死机理留待以后复查**（候选实验：官方示例式 PUSH_CONSTANT+真 layout 已试仍崩；显式两段 preprocess 因 VUID-renderpass 未干净测；分块 execute 规避未做）。排查工具 Aftermath 接线保留为编译期开关 `-DRGL_AFTERMATH=ON`（默认关）。

**验证**：核显 headless 截图 = 基线（建筑/草地/树/天空全对）；NV 窗口 llm_debug 截图 frame 10 = 同画面、零 error、reconcile 1571=1571、DGC 全量不崩。Aftermath ON/OFF 双态编译绿。

### 2026-09-13（续 3）：街景"墙面特定角度死黑 + 地面脏噪点"——两个独立负值/NaN 根因

用户反馈（FPS 街景视角）：① 特定角度大砖墙整面死黑；② 湿地面黑点噪声（逐像素 dither）。

**隔离**（llm_debug 截图二分）：直出 albedo 干净（非纹理）→ 输出 `isfinite(color)?正常:红`
标记——红色区域与原黑点/黑块**逐像素重合**，石锤 = NaN/负值非材质。旁路 normal map 后
散布 dither 大部分消失但右下角残留一块连续 NaN → 二分 envSpec 非有限（P/N/lod 全有限）
→ 定位 env cubemap 数据侧。

**根因 1（墙面死黑）= envBrdfFactor 手抄拟合抄错**：④a 版 `B = -(1.04r-0.04)²` 全 roughness
范围大负值（python 复算 F0=0.04：rough 0.3→-0.107 / 0.5→-0.311 / 0.74→-0.671 / 1.0→-1.204），
非金属像素被**减去**最多 1.2× 天空 radiance（env 亮部 4~18）→ 负 radiance clamp 成黑。
**修复 = 蒙特卡洛数值积分重拟合**（`tools/brdf_fit.py`：GGX height-correlated Smith +
Schlick (1-VoH)^5 分解 I=F0·A+B，H 按 GGX pdf=D·NoH 重要性采样（Jacobian dωL=4VoH → 权重
G2·VoH/(NoV·NoH)），29×29 网格 × 52 万样本/格，张量积三次 16 系数最小二乘，maxerr 0.056；
锚点：mirror→A=1/B=0、F0=0.04·rough 0.74→0.026）。坑：①VoH 必须带 φ 项（只取 NoV·cosH
镜像极限直接崩）；②Karis 形式 `0.5/(sv+sl)` 本身 = G2/(4NoVNoL) 不是 G2；③张量积设计矩阵
`Vy[:,:,None,None]*Vx[None,None,:,:]` reshape 前必须转成 [i,j,k,l] 轴序（rank 10≠16 即中招）。
scene.slang 单点替换，forward（model_pbr_ibl）与 deferred（light.frag）共用同时受益。

**根因 2（地面黑块/黑点）= env HDR 太阳 texel packHalf 溢出**：FreeImage RGBE 解码出
float32 天文值（指数 255 → ~FLT_MAX）→ RGBA16F 重投影 `glm::packHalf2x16` 溢出成 inf →
三线性/mip 混合 inf×权重 = NaN → 反射方向命中处采样 NaN → ACES NaN → 纯黑（isfinite 红标
与残留连续块吻合；dither 形态 = 掠射/法线抖动使采样在有限/inf texel 间跳变）。
**修复** = `loadEnvCubeMapHdr` 重投影处 `glm::clamp(rgb, 0, 6e4)`（天空 p50 的 ~1.4 万倍，
视觉无损）。附带：`irradianceSH` 返回补 `max(r,0)`（SH 截断振铃对高对比 HDR 可输出负辐照度，
Filament 同款钳制——本例非主犯但属正确性修复）。

**验证**：`isfinite` 红标截图**零红像素**；街景机位黑块/黑点/墙死黑全消、湿地面砖缝保留
正常高光；总览机位正常；style/doc 0 警告；reflect 已重跑（manifest 随提）。

**经验**：逐像素 dither 形态的黑点第一假设应是 **NaN**（ACES 把 NaN 吞成纯黑），一条
`isfinite`→红标 shader 即石锤，快过一切读码猜；黑块与 dither 可同源（NaN 在连续区/跳变区
两种形态）。HDR 进 half 纹理必须在转换点 clamp——float32"有限"不代表 half 域有限，
inf×0=NaN 让"数据没 NaN"的直觉失效。

### 2026-09-13（续 5）：掠射角白色椒盐噪点 = 导数 TBN 退化，改 CPU 烘切线标准 TBN + specular AA

**现象**：湿地面 / 植被表面在**掠射角**（视线近平行表面）出现逐像素跳动的白色椒盐点。

**定位**（G-buffer 通道分解，免猜）：新增 F1 相机导出快捷键固化机位 → dump G-buffer 逐通道看：
position 平滑（**排除 z-fighting**）、albedo 平滑（排除色彩图本身）、**仅 normal 通道椒盐**。
再采样白点像素确认是**中性 specular 高光**（亮点通道 max-min 中位数 11，非彩色）——即噪声来自
法线，高光只是法线噪声的显形。判据教训：**目测"随机性是否消失"才对，像素计数指标无效**（真实
高光本就应有、且随帧连续变化）。

**根因**：`applyNormalMap` 用屏幕空间导数（`ddx(P)/ddx(uv)`）解 Jacobian 造切线空间，掠射角下
`det = st1.x·st2.y − st1.y·st2.x → 0`，invDet 除法放大浮点误差 → world normal 逐像素乱跳。
这与资产、MASK/doubleSided 全无关（涉事地面材质全 OPAQUE）。

**Filament 基准**（子 agent 调研本地 filament）：lit 材质编译期强制 `TANGENTS` 顶点属性，CPU 导入
期 MikkTSpace 预烘切线，FS 只做一次 `normalize(TBN·n_ts)`，**绝不用 dFdx 造 TBN**；dFdx 唯一正当
用途 = specular AA `normalFiltering()`（Kaplanyan 2016，**刻意喂几何法线**而非着色法线，glTF 默认
variance 0.15 / threshold 0.2）。

**修复 A（CPU 烘切线 + 标准 TBN）**：assimp 三路导出（默认 / `WEBCGL_GLTF_TANGENTS` config /
via-FBX）实测均不写切线 → 切线在 `bistro_pack.py` 用 numpy **Lengyel 平滑切线**（+ Frisvad 退化
兜底）生成 glTF 2.0 核心 `TANGENT`（VEC3 float32；验证 |len-1|≤4e-8、|T·N|≤7e-7）。glTF 核心
TANGENT 不含手性 W → loader **逐三角形按 UV Jacobian det 符号推 W**（实测 bistro UV 92% det<0 =
DirectX Y-down 镜像 UV，W 硬编码 +1 会把镜像面切线翻错），无属性时 Frisvad 兜底。ModelVertex
32→48B（tangent vec4@32，改 `model_schema.lua` + `just reflect` 重生 static_assert）；mesh shader
直通 tangentOS；`applyNormalMapTBN`（Gram-Schmidt 正交化 + `cross(T,N)·w` 定手性）。

**修复 C（specular AA）**：`normalFiltering`（Kaplanyan 2016，喂几何法线 geoN）forward lighting /
deferred geometry 两 pass 接入——掠射角用粗糙度门控展平高频法线，压掉残余高光锯齿。

**验证**：白噪点**随机成分消失**（用户目测：椒盐 → 连续高光）；forward/deferred 冒烟零 error。

**D1 0→29px 定性（接受项）**：接入后总览 D1 = 29px（0.0031%，**全落在剪影边缘**：天线尖 / 屋脊
轮廓 / 树叶边缘，肉眼不可见）。隔离实验：normalFiltering 置 identity = 19px（纯 A 标准 TBN），
恢复 = +10px（C）。diff 像素处 deferred position 非零 = **几何覆盖一致、差在 specular**。查
light.frag 用共享 LINEAR sampler 采 G-buffer，但 1:1 像素映射 LINEAR 退化成 NEAREST，**排除 halo**。
最终定性 = **forward（float N）↔deferred（oct RG16_SNORM 量化 N）的固有精度差**，掠射角 Fresnel→1
时 reflect 方向对量化误差极敏感 → 剪影边缘单像素分叉。**非 A/C 新引入 bug**。

**纠偏（重要）**：本文件续 4 把"street 长期 D1 19px"记为"相机时间漂移"——**错**。本次背靠背两次
forward 截图 = 0px，证明相机确定、零漂移；那 19px 一直就是上述 oct 边缘灵敏度（street 视角剪影
边缘多故常驻，总览当时恰好落阈值内显示 0，换机位/换法线即到 29）。教训：**"相机漂移"这类甩锅
归因必须先用背靠背 run 实测漂移基线，未实测不得拿来解释残差**。

**教训**：①掠射角白噪点先 dump G-buffer 分通道（position/albedo/normal 各是不是噪的），一步区分
z-fighting / 纹理 / 法线，别读码猜；②导数 TBN 掠射退化是已知病，标准解 = CPU 烘切线（别在 FS 用
dFdx 造 TBN，dFdx 只配喂 normalFiltering）；③forward↔deferred 剪影边缘常驻少量 D1 先怀疑 oct
法线量化（掠射 Fresnel 放大），是固有精度差不是新 bug，追零需升高精度 normal G-buffer。

### 2026-09-14：植被透射 + 光源本色 shader——路灯绿光根因 + backLit=0 盲调参教训

**任务**：给植被（背光透射 SSS）/ 光源（本色）各加 forward 专属 shader，路由 per-primitive
（MASK+doubleSided=植被、emissive 非零=光源，纯数据驱动），deferred 无视 styleMap 逐位不动。
实施细节见 phase8_plan §10；本条记两个诊断。

**绿光 = 路灯变绿霓虹**：光源 shader 上后灯不再是镀铬球、但变成饱和发光的绿灯罩。数据根因
（提取纹理算均值，3 行 python）：`Emissive_StreetLight` 的 `baseColor`=纯黑、`emissiveFactor`
=[0.5,0.5,0.5] 灰、**绿色 100% 来自 emissiveTexture（绿玻璃纹理）**；`0.5×strength(4.0)=2.0`
乘绿纹理绿通道 1.47，我写的 `reflectWeight≈0`（emission 强时压制反射）让 emission 独占像素 =
纯绿霓虹。**金属球版是黑金属底把过强 emission 压暗了才藏住**——去掉金属后绿光暴露的是
strength=4 回填值过强的预存问题。修复 = emission×(1/strength) 还原 + 保留玻璃反射（暗绿玻璃）。
教训：**查颜色异常先提取纹理算均值**（baseColor 黑 / emis 绿一测即明），比读图猜快且准。

**植被透射"看不见" = backLit=0，非 bug**：用户机位 + 我拍的俯视都是顺光（主光 elevation≈50°
从上方照、透光朝正下方出射，仰视镜头 `dot(V,-L)≈-0.17<0`）。据此连调两轮 strength/thickness
**零响应**（对比图逐像素近同）——驱动项是 0，调幅度全打在零上。手算 dot 符号验算才暴露，临时
把 sun 压到镜头正逆光方向 → 树冠金黄透亮，机制证明正确。教训：**调光照参数若完全无响应，先算
驱动项（一个 dot 的符号/量级）再调幅度**——"效果不出"很可能是"条件不满足"而非"幅度不够"。

**死黑面（用户追问"树叶为什么会有死黑面"）**：标准 GGX 下 `NdotL=saturate(dot(N,L))` 让单层叶片卡
背阴面直接光**恰好为 0**，IBL 的 `irradianceSH(N)` 朝地面方向又暗，透射只补严格背光角——三层全
关零 = 纯黑剪影。真实树冠发亮靠**冠内多层叶互射**（多重散射），单层卡没有这个信息。标准解 =
**half-Lambert wrapped diffuse**（`pow(dot(N,L)·0.5+0.5, 2)`，Valve HF2 植被经典、UE vegetation 同款）
把阳光绕到晨昏线背光侧，specular 保持标准 saturate（高光不该绕）。同机位对比：黑剪影 → 橄榄/
棕色叶片纹理分明，曝光正常。教训：植被/薄壁/软对象的"死黑面"多半是 **Lambert 项太硬**，
wrapped/half-Lambert 是标配，不是调强度能解决的。

**花床"潮湿反光"+ 漏路由（红色探针一次定位）**：用户实拍绿篱花床带湿地式天空镜面。两个候选根因
（走通用 PBR = 漏路由 / 植被 shader envSpec 掠射菲涅尔）读图无法区分，临时把植被 shader 输出涂纯红

树叶物理上无锐利环境像）→ `envSpec×0.2`。真正的漏路由是判据太窄：花床 `Foliage_Paris_Flowers` 是
OPAQUE（非 MASK+DS），判据补"材质名含 `Foliage`"（loader 透出 `materialName`）。教训：**两个候选根因
读图区分不了时，构造一个"必走 A 则显红"的判别性实验（探针着色器/涂色），一张图定案**，别逐个候选

### 2026-09-15（续 9）：envBrdfFactor 拟合权重——历史记录描述与 brdf_fit.py 实际不符（外部勘误 #4，代码对文档错）

**事实**：本文件续 3（根因 1，L521-524）的 MC 权重描述——"H 按 GGX pdf=D·NoH 重要性采样（Jacobian
dωL=4VoH → 权重 G2·VoH/(NoV·NoH)）"＋"②Karis 形式 `0.5/(sv+sl)` 本身 = G2/(4NoVNoL) 不是 G2"——
作为**权重推导**字面连读，与真源 `tools/brdf_fit.py:36` `w = 2·NoL·VoH/((sv+sl)·cosH)` 不一致：
字面读法容易理解成"把某个形式的 G2 直接代入 `G2·VoH/(NoV·NoH)`"，而代码是把 1/(4NoVNoL) 已折进 G2
再与 Jacobian 合并后的形态。代码与 scene.slang 的系数本身正确——错在本 doc 的压缩记录（brdf_fit.py
docstring 倒是写了完整合并"合并为 2·NoL·VoH/((sv+sl)·NoH)"；外部独立复算的 16+16 系数与
scene.slang **逐位一致**、自报 maxerr 0.0558 = 续 3 的 0.056，自洽）。

**独立数值验证**（LCG 20 万样本，两极限对照，本文件另种子复算同量级）：

- 镜像极限（NoV=1, rough=0.05，真值 A→1 / B→0）：代码权重 A=1.0000 / B=0.0000 ✓；续 3 字面权重
  （`VoH/((sv+sl)·NoV·NoH)`）A=0.5006 ✗；把 `0.5/(sv+sl)` 当 G2（`0.5·VoH/((sv+sl)·NoV·NoH)`，
  再半之）A=0.2503 ✗——两个错误变体都过不了续 3 自设的锚"mirror→A=1"，这反证产出系数的拟合 run
  走的不是文档字面。
- 掠射（NoV=0.05, rough=0.5）：代码权重 A=0.77 有限 ✓；续 3 字面权重 A=20.3、Karis 式权重 A=10.1
  ——均发散（错误变体残留伪 `1/NoV` 因子；代码权重 NoV 已在 G2 内相消，除式只剩 NoH=cosH）。

**正确推导**（一句话）：Karis 形式 `0.5/(sv+sl)` 已把 1/(4NoVNoL) 折进 G2（= 真 G2/(4NoVNoL)），
与重要性采样 pdf=D·NoH、Jacobian dωL=4VoH 合并后权重 = `2·NoL·VoH/((sv+sl)·cosH)`，即
brdf_fit.py L36。

**结论**：`tools/brdf_fit.py` 与 `scene.slang` 的 envBrdfA/envBrdfB 系数本身**正确，未改**，本条
纯文档勘误。按本文件"只增不改"规矩，L521-524 原文保留，权重推导以本条为准。

**风险记录**：若有人照续 3 字面重写拟合工具，会得到静默劣质系数——镜像 A→0.5（镜面反射减半）、
掠射区 A→10~20 垃圾值，且全程**不崩、不 NaN、不报错**，只是 specular 略差，极难察觉。教训：
**MC 权重记录必须写成最终合并式**（可直接对码核对），把"G2 结构"与"采样修正"拆成两句 = 留解读
歧义。

**来源**：现代 Vulkan 教程侧勘误报告 #4（`../modern_vulkan_tutorial/RGL-math-audit.md`，W1
split-sum 双实现 + 独立 MC 交叉验证），2026-09-15 处置。

present 接线）过程中，以下四点均以 VVL 报错 / 驱动返回值实测定案，规范文本与 archive
调研稿（`present_timing_research.md`）都没写全：

1. **swapchain flag 的支持位不能用 `VkSwapchainFlagsSurfaceCapabilitiesEXT` 筛**。
   RADV 对 per-surface+mode 的 caps2 查询返 `swapchainSupportedFlags = 0`，而
   `presentTimingSupported = true`、`presentStageQueries = 0x5`。查 spec：约束 flags 的
   VUID-12448（"flags must be a subset of swapchainSupportedFlags"）整段包在
   `ifdef::VK_EXT_multisampled_render_to_swapchain[]` 内——只有启用那个扩展才生效，本项目
   恒不启用。若按该字段筛，present timing 在本机直接被误判为不支持。门槛改为
   `presentTimingSupported` + stage 掩码含 `QUEUE_OPERATIONS_END`。

2. **链上 `VkPresentId2KHR` 要求 swapchain 创建带 `VK_SWAPCHAIN_CREATE_PRESENT_ID_2_KHR`**。
   VVL：`pPresentInfo->pSwapchain[0] was created without VK_SWAPCHAIN_CREATE_PRESENT_ID_2_BIT_KHR`
   （只带 `..._PRESENT_TIMING_BIT_EXT` 不够）。激活时两个 flag 同置，两 feature 由设备组门
   一并启用（`present_timing + present_id2 + KHR_calibrated_timestamps` all-or-nothing）。

3. **`vk::Queue::presentKHR` 对 queue-full 抛异常而非返回码**。vk-hpp 该函数的允许结果列表
   不含 `VK_ERROR_PRESENT_TIMING_QUEUE_FULL_EXT`（此码 2026 才进 spec），命中即抛
   `PresentTimingQueueFullEXTError`——按返回码判断回退分支永远进不去（第一次实测表现为
   异常穿透到 main 报错退出）。处置 = `presentKHRTolerantQueueFull` 包装折回 Result 值。

4. **queue-full 回退重试必须同时摘掉 timing 链与 present fence、并清零 wait 信号量**。
   spec 述被拒 present 的"队列操作仍视为已入队"，实测 VVL 两条印证其后果：再提交已 SIGNALED
   的 present fence 报 `Fences must be reset before being submitted`；再 wait 同一 binary
   信号量则成同队列 wait-then-signal 死锁形态（该信号量的下一次 signal 排在更后面）。
   重试只留 image/swapchain，VVL 对"重投同一 image"不报警（acquisition 已在被拒 present
   时释放，实现侧接受）。随后 8 帧冷却不挂链，队列排空自动恢复。

**时间域形态（跨驱动需注意）**：本机 RADV 的 swapchain 只 advertise
`VK_TIME_DOMAIN_PRESENT_STAGE_LOCAL_EXT`（id=0），没有 swapchain-local 域。实现改为
"优先 swapchain-local，缺则 stage-local"，且校准的
`VkSwapchainCalibratedTimestampInfoEXT.presentStage` 在 stage-local 下必须恰为基准 stage
一位（VU-12228）。副作用：stage-local 域内不同 stage 的时间戳**历元不一致**——首条结果
log 显示 `QueueOperationsEnd = 20576.656 s` 而 `ImageFirstPixelOut = 20566.756 s`，相差
~10 s。故报告侧放弃"queue→pixel 端到端跨度"，改为基准 stage 瞬时落位（`present.stage`）；
同 stage 相邻差（IPD）不受影响，实测 FIFO IPD p50 = 6.066 ms 恰 = 驱动报的
refreshDuration 6.061 ms，校准与 CPU 轨同轴（首帧 pixel-out 落在首个 present CPU zone
后 ~5.9 ms，一帧周期内）。

**丢帧量化（⑤ 证据）**：eImmediate 6.5 min 长跑（40117 present，≈138 fps 满渲）中
**34190 条（85.2%）的 present 其基准 stage 时间恒为 0**（= spec 的"该 stage 无结果"，
被合成器丢弃/替换），FIFO 下仅 4/10090（0.04%）——即 `present_timing.drop` counter
直接给出"帧率上限必要性"的数字；对照 IPD 只有 2079 条有效样本（真到像素 stage 的那些帧）。

## 2026-09-27（同日勘误）：并行双实例污染测量——"85% 丢弃"结论作废

**错误结论**（本文上一条 9.3 条目末尾）："eImmediate 6.5 min 长跑中 85.2%（34190/40117）
的 present 其像素 stage 时间恒 0 = 满速渲染被合成器丢弃的直接证据；FIFO 下仅 0.04%"。

**成因 = 测量环境被我自己污染**：19:57:00 我后台起第一次长跑（FIFO），以为它已退出，
于是在 19:57:05 又起了第二次（eImmediate）。**两个 rgl 实例同时在屏**，两窗口互相遮挡、
KWin 需同时合成两路 surface：① 被遮窗口的 present 走合成拷贝而非 direct scanout，
`IMAGE_FIRST_PIXEL_OUT` 对多数帧不再报告（该 stage 的语义是"该 image 第一个像素出现在
显示输出上"，合成路径下被合成器接手 = 不适用于 app 的 image）；② 两进程分担 GPU/CPU，
帧率被对半压。于是"drop=85%"主要是**呈现路径形态变化**，不是"85% 的帧白渲"。

**单实例复跑（同一 build，各 25 s，窗口 1280×720 forward）**：

| | eImmediate | FIFO |
|---|---|---|
| 帧墙钟 avg/p50/p95 (ms) | 7.10 / 6.91 / 8.48 | 7.10 / 6.91 / 8.46 |
| CPU `drawFrame` mean (ms) | 7.03 | 7.03 |
| GPU `gpu.frame` mean (ms) | 2.98 | 2.98 |
| CPU `acquire` mean (ms) | 0.05 | 0.04 |
| present / IPD n / min / p50 (ms) | 1936 / 1934 / 6.063 / 6.96 | 2004 / 2002 / 6.059 / 6.97 |
| **丢帧（基准 stage 无时间戳）** | **0** | **0** |

两模式分布在噪声内一致，**drop 双零**；先前 FIFO 那组"p50 恰 = 刷新周期"同样属污染态
（彼时它才是被遮挡/被合成的一方）。**权威数据以 `docs/phase9_plan.md` §4.4 上表为准。**

**方法学教训（写进操作纪律）**：
1. **窗口测量必须单实例串行**——`nohup ... &` 起后台后，起下一个前必须确认前一个进程
   已退出（`pgrep` + 日志终值行双检），不能凭"看起来跑完了"推断；
2. **异常漂亮的数字先问环境**——"85% 白渲"这种正好印证既有假设（archive §八）的大数字，
   最该先怀疑测量条件而非立刻当作证据（确认偏误）；
3. **合成器路径本身是变量**——同一段 present timing 代码在 direct scanout 与合成拷贝两种
   形态下，stage 可得性完全不同；跨机/跨 WM 比较前，先用单实例确认基线形态；
4. 用户关窗 = 该次长跑作废（不得只取"关窗前那段"当完整样本），要复跑。

不受影响、仍然成立的结论：queue-full 回退路径（压容量到 1 强制触发 → 重试成功 + 冷却恢复、
VVL 零报警）、默认关 BIT-IDENTICAL、四处分歧契约（上一条 1–4 项）、CPU-bound 判定（§10）。

## 2026-09-28：Phase 10b 增补批（批 11b.1 中文字体 + 11b.2 HTTP RPC）排障时间线

### 一、imgui 中文显示为问号（批 11b.1）

**根因是三层叠加，缺一层都修不到点上**：

1. **压根没加载字体**——`ImGuiLayer::init` 此前只有 `StyleColorsDark()`，从不调

   不是"编码问题"也不是"字形缺失告警"，是**根本没给图集中文字体**。
2. **想用系统 CJK 字体还有一层拦路**——内建 stb_truetype 只吃 TrueType 轮廓，

**落地形状**：`kUiFontCandidates` 探测链（`configs/runtime.lua` 的 `ui_font` 前置 →
MiSans Light → MiSans Regular → Noto Sans CJK 两路径 → 文泉驿正黑 → Windows
msyh/simhei），全 miss 只 warn 并回落内建字体（中文仍问号，不崩）。

**验收方式纠偏（重要）**：计划原写"`llm_debug=true` 出含 UI 截图"，实测**做不到**——
`vkrenderer_impl.cppm` 里 `capturer.record` 在 `frameEndHook`（imgui 绘制）**之前**，
llm 截图天生不含 UI。改用窗口模式（`headless=false` + `diagnostics.imgui=true`）
+ `spectacle -b -n -o` 外部截图验收：日志
`imgui: 面板字体 /usr/share/fonts/misans/MiSans-Light.ttf @ 18px`，图内

### 二、RPC 两个真 bug（批 11b.2 验收期抓到）

1. **`set_error_handler` 覆盖自产 4xx body**：cpp-httplib 对**所有 status ≥400** 都回调
   error handler（handler 返回值只控制 `need_apply_ranges`，void lambda 被包装成
   Unhandled 也照跑）→ 我们无条件 `respondBody(res, ...)` 把自家 dispatch 写好的
   400/404/409/504 载荷全盖成 `unknown route`。修 = **只补空体**
   （`if (res.body.empty())`），空体才是 httplib 自兜的 404/405/431。
   教训：第三方框架的"错误回调"未必只在你出错时触发，先读它对 status 的判断条件。
2. **`rpcDispatch` 把 responder move 进下层 → catch 分支空句柄 → 恒 504**：
   `rpcDispatchPost(w, request, std::move(responder))` 之后，本函数 catch 里的
   `responder` 已是默认构造的空句柄，而 `RpcResponder::resolve` 对空句柄是**静默 no-op**
   → promise 永不兑现 → 传输层 2s 超时吐 504。
   **症状指纹极好认**：预构造错误（`rpcFail(400,…)`）路径全部秒回，**只有真正抛
   json 异常的请求**（`get<float>()` 撞字符串、越界取字段）才 504——一看就是"异常路径
   独有的分支坏了"。修 = 传拷贝（`shared_ptr` 拷贝廉价），并在注释里写死勿改回 move。
   复测：wrong type / 缺字段 / 坏值一律 `400 + json.exception 原文` 秒回。

两个 bug 都**不影响默认路径**（门默认关），BIT-IDENTICAL 回归不受影响。
验收纪律沿用：`checks --strict` 0 警告 + headless 冒烟 + BIT-IDENTICAL 全绿。

## 2026-09-28 · Phase 10 批 10.7：点选高亮 + 选中跳页（三处"看着对却不生效"）

起因 = 用户报「phase10 加入的点选功能似乎并没有生效，或许需要增加个 shader 来表示
点选成功，也可能是真的没能点选成功」。**结论：点选一直是通的**——headless 探针与
窗口合成左键两轮实测都打出 `回读 raw id → objectSlot → entity` 全链。真正原因是
`diagnostics.picking` 默认关，且**选中后画面零视觉反馈**（唯一反馈是面板"选中"页的
一行文字，而 Tab 默认停在"渲染"页）。

### 坑 1：pass 插图末 = 画了白画（图能编译、pass 在跑、纯视觉无效）

高亮 pass 初版按「插在最后一个 pass 之后」实现。**图编译通过、pass 确实在执行、draw
确实录了**，但零视觉输出——因为 forward 图末是 `tonemap`（`drawLight`，采 `scene_hdr`
上屏），插在它之后时 `scene_hdr` 已无人采样，高亮写进了一个死附件。

正确插入点 = **首个「采样场景色附件的消费 pass」之前**（forward/deferred = tonemap 前，
offscreen = composite blit 前），且色附件名由该 pass 的 `sampleRead` 输入反查（不硬编码
`scene_hdr`，三变体自动跟随）。

> 一般教训：动态装饰渲染图时，「追加一个 pass」不是 `push_back` 就完事——**插入点相对
> 数据流的语义位置**才决定它是否可见。编译成功 ≠ 有效果。

### 坑 2：借 depth 前须改上游 storeOp（compile 阶段即报错，good）

高亮要借 `scene depth` 做可见性测试，但 forward 图的 `transparent` 段按「depth 后续
无人用」的优化声明了 `storeOp = dontCare`。于是 compile 报：

```
attachment 'depth' written in pass 'transparent' with DontCare store but used later
```

修法 = 装饰时把上一个写 depth 的 pass 的 `storeOp` 改成 `store`。这是**门控装饰的一部分**
（门关 = 不调用 = 图逐位同），不是改默认图。

### 坑 3：alpha 混合的 rgb/a 语义写错 → 贡献退化为 rim²（实测两次都"不可见"）

高亮首版输出 `float4(HIGHLIGHT_COLOR * rim * I, rim * I)`，想着「预乘 alpha」。但混合是
标准 `SRC_ALPHA / ONE_MINUS_SRC_ALPHA`（`shader.cppm` colorBlend），合成结果 =
`dst·(1−a) + src.rgb·a`——**rgb 里再乘一次 rim，等于 rim 被乘了两次**：

| 版本 | 实际贡献 | 实测差异像素 | 最大通道差 | 肉眼 |
|---|---|---|---|---|
| v1 `power=4, I=0.6`，rgb 与 a 各乘 rim | `rim²·0.6` | 1.83% | 17/255 | 不可见 |
| v2 修正混合语义（rgb 纯色，a 承载权重） | `rim·1.6` | 1.76% | 46/255 | 仍偏弱 |
| v3 再加恒定基色权重 0.35 | `0.35+rim` | 1.82% | **112/255** | 清晰可见 |

第二个独立问题：**纯菲涅尔只勾轮廓**。建筑墙面这类**正对相机的大平面** `NdotV≈1` →
`rim≈0`，点中后正面完全无变化（v2 的 46/255 差异全落在轮廓线上）。故必须有
`HIGHLIGHT_BASE_WEIGHT` 恒定基色层做「点中即染色」，轮廓光只作强化。

> 教训：调试「效果不可见」时，先用**逐像素 diff 量化**（差异像素数 + 最大通道差 + 分布
> 区域），再据此定位——v1 的 17/255 与 v3 的 112/255 差别明确指向前者是量级问题而非
> 「没生效」。纯看图分不出「没画」和「画得太淡」。

### 顺带：312 克隆条目的构成（曾误判）

用户质疑「3-4 个 fragment shader 怎么会形成那么多组合」。实测 `pipeline entry:` 日志
统计 = 312 = 六元组去重结果，**爆炸源是贴图槽不是 shader**：

| 维度 | 不同取值数 |
|---|---|
| frag 规格（`model_pbr_ibl` 264 / `model_vegetation` 25 / `model_light` 23） | **3** |
| 顶点槽 | 30 |
| base / normal / orm 贴图槽 | 各 132 |

bistro 1591 个 primitive 按贴图组合去重成 132 组，撞出 312 个不同组合。**去重本身工作

### ② SSAO 三个坑（都靠实测才发现，写进了 shader 注释）

1. **产物语义反了**：shader 返回 occlusion（0=通透），tonemap 却当乘数
   `hdr *= lerp(1, ao, strength)` → 开阔处被乘成 0，**strength=1 整幅全黑**。
   改成返回**可见度**（1=通透）后正常。附带的 bit 级论证：`lerp(1, x, 0) ≡ 1.0`
   逐位成立，故 strength=0 的旁路在改语义前后都保 BIT-IDENTICAL（实测 sha256 相同）。
2. **导数落入非一致控制流**：strength 早退放在 `ddx/ddy` 之前 = UB（编译器无法证明
   uniform）。所有早退（天空、strength）必须排在导数之后。
3. **深度图用了共享 sampler**：共享那份是 LINEAR + mipmap LINEAR，而 D32Sfloat
   **不可过滤**（Vulkan invalid usage）→ 新增 `ensurePointSampler`（NEAREST + 无 mip）。

另外还踩了图契约的连锁反应：为了让 ao 读 depth，放宽了"depth 附件只允许 depthWrite"，
结果 `decorateHighlightPass` 把 ao 误当成"消费成片的 pass"（它也 sampleRead），
colorAtt 取到 `"depth"` 与 depthAtt 撞名 → 编译期报
`references attachment 'depth' more than once`。修法 = 消费点判定只匹配**色**附件。

### ③ 三次量错数据，第三次才对（最贵的教训）

## 2026-09-29 · Phase 11 批 11.2 阴影失效排查：四个 bug 与一条被冤枉的"最大嫌疑"

全程排查日志见 `docs/阴影失效排查.md`（交接文档，结论以本节为准）。症状：`shadow_pass=true`
时画面**零投影**（开关对拍 0.000% 逐位相同）。共修四个独立 bug，全部落地后对拍
**21.5% 像素变化、100% 变暗、0 变亮**（复现机位），树冠/建筑/灯柱投影形状正确。

### Bug 1（采样端）：级联选级把片元推进未写入的槽

未生效级的 `shadowSplits` 留 0，而 shader 选级是无条件三段比较、任何片元 `distSq > 0`
恒成立 → 生效 1 级时全场景被推到 3 号槽（矩阵从未写过 = 全零）→ `clip.w = 0` →
NaN → 阴影因子恒 0。**与机位无关**——5a-3/5a-4 的"阴影可见"判定与四组基线全部作废。
修法：未生效槽也填 `kNoFar`（`fillShadowData`），shader 侧零改动。

### Bug 2（剔除端）：拟合球平面约定混用

`frustumBoundingSphere` 的 Eberly 增量法是"≤ 0"约定，`extractFrustum`/`sphereInFrustum`
是"≥ 0"——混用把球心推向内侧深处、半径长不大（实测 r=1.25 < 远角距 2.0）。
中途"取负转约定"把半径推成 0（更糟）→ 改 8 角 AABB 法（不依赖符号约定）。
**方法论**：一个修正让结果更差时，换方法而不是继续调符号。

### Bug 3（架构）：剔除体与拟合体解耦（对照 Filament）

原"世界球 × 级联切片球"剔除漏掉比受光面高得多的投影体（楼房整批被剔 → 没人画进阴影图）。
按 Filament（`src/ShadowMap.cpp:835-839/458-501`）重做为 `ShadowVolume`：盒 XY 由切片球定
（正交投影下影子沿光向平移 XY 不变 → XY 只需覆盖受光面），**Z 覆盖全部投影体**世界 AABB
在光轴上的投影；实体遍历拆两段（循环内攒候选 → 循环后建体再逐级剔除）。

### Bug 4（根因，卡最久）：反投影乘了正向矩阵 + NDC z 值域错

Bug 2 换 AABB 法后仍半径 0，`阴影失效排查.md §3` 把最大嫌疑指向 `projWithDepthRange`
的 GLM 列主序下标——**探针实测洗清**：`out[2][2]/out[3][2]` 与 GLM `perspectiveRH_ZO`
的 `Result[2][2]/Result[3][2]` 一致，w 行未动。真根因两条叠加：

1. **8 角循环把 NDC 角点当世界点乘了正向 `viewProj`**——反投影必须乘
   `glm::inverse(viewProj)`。正向透视矩阵的 w 行恒 `(0,0,-1,0)`，远平面角 w=−1 恒负
   → `clip.w <= 0` 早退 → 半径恒 0（"退化视锥"保护成了错误构造的遮羞布）。
2. **本项目 GLM 编译为 depth zero-to-one**（`rgl/CMakeLists.txt:105`），NDC z 值域
   `[0,1]`，角点应取 {0,1} 而非 {−1,1}——只修①不修，近角 w 恰为 0 仍触发早退。

修法：`invViewProj * (±1,±1, z∈{0,1}, 1)` → 世界 AABB → 外接球。探针实测复现机位
r=2.4017 ≥ 远角距 2.0074，包住 ✓。**教训**：`阴影失效排查.md §7.3` 说同一函数栽两次
都是"凭记忆推 GLM"——这次连"最大嫌疑"本身都是记忆推出来的，探针一跑 30 秒定案。

掩盖了这条错误推理。

必须写进注释，否则"load 保邻块"的直觉推理必错；② 排查沿用 5a-5 教训——先改 shader 把中间量
（级号/强制级）直接画出来，两轮实验各自只排除一半假设，不从像素反推。

## 2026-09-29 · Phase 11 批 11.2 5a-7：阴影随视角"游动"——拟合球的姿态依赖与连续变化

尺寸随之变 → 光空间投影逐帧缩放 → 影子在地面滑移。三个叠加根源：

1. **AABB 法姿态依赖**（5a-5 引入）：世界 AABB 随 yaw 变 → r 随姿态连续变；且比精确

2. **自适应 near/far 连续变**：两机位 f=1.3813 vs 1.4345 → 即便闭式解 r 也连续变。
3. **snap 格错**：buildShadowVolume 收 `kShadowMapSize`(2048)，4 级时块边长实为 1024

- `frustumBoundingSphere(view, proj)` 改**闭式精确外接球**：8 角共球、球心在视轴
  `zc=(f²−n²+rf²−rn²)/(2(f−n))`、`r=√((f−zc)²+rf²)`；n/f 从 proj 深度行反推
  （RH_ZO：n=B/A、f=B/(1+A)），角点离轴距 = `z·tanHalf·√(aspect²+1)`。姿态无关，
  不碰任何平面符号约定。GLM 探针（probe4）验证 4 组参数 8 角距 ≡ r——**探针又抓到
  一次记忆错误**（离轴距先写成 `√(1+1/a²)`，自检"包住=NO"当场暴露）。r×1.001
  防 float32 下角点出球（剔除保守方向 = 宁大勿小）。
- `quantizeShadowDistance`（1/8 格向上取整）：CPU 建切片与 `fillShadowData` 的 splits
  **同用量化值**（两处错位 = 边界闪跳）。小幅移动落同一桶 → r/splits 完全恒定；
  跨桶跳一次 ≤12.5%（离散、低频，观感是"分辨率变"而非"影子滑"）。
- snap 格改传 `shadowTileSize(cols)`。

**验证**：用户报障的两机位 + 中点机位三图对比，井盖阴影状态一致（修复前 A 有影 B 无）；
默认机位开关对拍 6.17% 全变暗（面积比修前小——量化后 splits 外移 + 球收紧，属预期）；
D1 0.005%；0 error；on 态基线迁移 forward `b856e4a6…` / deferred `fe3693ef…`
（off 两组逐位不变）。

**方法论**：① CSM 稳定性三件套 = 姿态无关半径 + 距离量化 + 正确 snap 格，缺一即游动；
② 闭式解也要探针——"这次我推对了"的记忆同样不可信，自检断言（8 角距 ≤ r）比推导便宜。

## 2026-09-29 · Phase 11 批 11.2 5a-8：5a-7 是"修一个丢一个"——guard 反了，且验证全在垃圾数据上做

——游动的判据（一致性）反过来成了它的保护色。

   排除多级路径；4. checkout 5a-5 码同机位 → 影子完整 → 回归点钉在 5a-7 改动；
5. 临时日志数剔除（pass=42/1591，**r=0.000000**）→ 全体积退化 → guard 反了。

  （含 A=−1 除零）。探针补测三分类：正常透视/重映射子 proj 有效、正交拒绝 ✓。

## 2026-09-29 · Phase 11 批 11.2 5a-8b：旋转游动真根因——AABB 角点当光轴极值（support function 错）

用户报（5a-8 提交后）：同 position 两 target（纯转视角 ~11°）井盖阴影一个受光一个有影，
"转移视角下影子又在动了"。

### 定位链（全部实测）

1. 重写 texel 吸附为**世界锚定光空间格**（旧吸附是"中心在自己盒里的 NDC"——恒 (0,0)，
   等于没吸；旋转时切片球心绕 eye 划弧扫过 ~100 texel）。探针（probe5）验格相位跨姿态
   恒定 ✓——**但影子照旧游动**，说明吸附不是（本次的）根因，保留备用（平移分量它管）。
2. 临时日志数体积参数：两姿态 r/eyeOffset **逐位相同**、格点坐标为整数 → 体积稳定，
   排除吸附路径。
3. 二值级联可视化（`return cascade==1`）：井盖姿态 A 非 c1、姿态 B 是 c1 → **换级**；
   而 c1 图里没建筑影、c2 有 → 影子随选级边界扫过而忽明忽暗。
4. 追问"c1 为什么没建筑影"：日志里 `eyeOff = r×1.02` **恒等**暴露 tMin 永远被 `−r` 支配，
   caster AABB 项从未生效 → **`dot(casterMin−center, d)` 把"世界 AABB 最小角"当光轴
   最远点——只有 d 分量全正才成立；太阳 d.y<0 时极值角在 y 的 max（建筑顶）**。
   于是各级 Z 只盖 ±r 切片球，比球顶高的建筑被近平面裁掉不画。各级 −r 不同（0.24/0.45/
   0.70/1.24），建筑影"在不在"取决于受光片元落在哪一级 → 旋转换级 = 影子开关 = 游动。

### 修复

- `buildShadowVolume`：tMin/tMax 改用 **support function**（逐轴按 d 分量符号取 min/max
  角）。修复后实测 eyeOff = 1.86/2.13/2.40/2.93（support 项胜出）。
- texel 吸附重写为世界锚定（见定位链 1，探针判据：任意姿态盒心光坐标 = texel 整数倍）。
- 探针自坑一枚：验"吸附后盒心"时用 `view·(0,0,−eyeOff)` 重构世界点——view 是
  world→view，重构要 `inverse(view)`；错了会把 PASS 看成 FAIL。

### 验证

报障两机位井盖阴影一致（都有影）；街道机位小物件影子全在；开关对拍 6.0% 全变暗；
D1 0.005%；0 error；基线迁移 forward on `03357546…` / deferred on `86b62107…`
（off 两组不变）。

### 教训

1. **"AABB 角点 = 方向极值"是几何里最常见的隐性假设**——凡"沿某方向取盒的极值"必须
   support function 逐轴选角，或干脆用球（球对任意方向极值 = 中心 ± r·d，无角点假设）。
2. 恒等式日志（`eyeOff ≡ r×1.02`）是根因的**指纹**：两个"不该恒等"的量恒等 = 其中一个
   分支从未生效。数值日志不只要看"变不变"，还要看"哪些量死也不变、且变得不该一样"。
3. 5a-8 的"三机位一致"验的是**平移**（两机位 depth 恰好同桶同层级）；旋转是独立自由度，
   验收机位对必须**同 position 纯转向**加一组。

3. **"只在一小块区域生效"的 bug 最会骗指标**：c0 盒小，早期所有验收机位都贴着相机，
   坏路径恰好被小盒罩住。验收要专门挑"远离相机、跨越多级"的取景（本次的街道远景）。

## 2026-09-30 · Phase 12 批 12.2d：闭式解探针成立（引擎侧零改动）+ 三处「我以为的行为」被实测推翻

### 闭式解探针：像素「该是多少」可以算出来，不必比基线

`tools/analytic_ref.py` 把 `shadeDirect`（GGX + Schlick-Fresnel + 简化 Smith-Schlick G）+
`tonemap.frag.slang`（Narkowicz ACES + 两张矩阵）+ **硬件 sRGB store** 逐式独立复刻一遍，
作为着色链的第二实现，与实机截图**逐字节对拍**。

原计划要在引擎加 `diagnostics.analytic = true`（跳过 IBL/SSAO 分支并导出 ACES 前线性值）。
**实测判定：不需要动一行引擎代码。** 链上每一项都已有配置门——

| 要关掉的东西 | 配置项 | shader 侧效果 |
|---|---|---|
| IBL 漫反射 + 镜面 | `environment.intensity = 0.0` | 两路统一乘 `env.intensity` |
| 天空盒背景 | `environment.skybox = false` | 不画背景 |
| 平环境光 | `light.ambient = {0,0,0}` | `light.ambient * albedo` 项归零 |
| SSAO | `ao.strength = 0.0` | `lerp(1,ao,0)` 位级 = 1.0 |
| 曝光 | `exposure = 1.0` | ACES 前线性倍率取中性 |
| 阴影 | `diagnostics.shadowPass = false` | `sampleShadow1Tap` 恒 1.0 |

唯一没门的只剩 specular，而它在「平面 + 无纹理 + 常数 rough/metal」的探针面上是 20 行闭式。
加一个把六个旋钮打包的开关**不换来任何表达能力**，只多一条与单旋钮并行、可能各自漂移的路径，
故不做。配置模板固化在 `qa/configs/analytic/`，入口 `just analytic`。

**实测结果（本机 RADV STRIX_HALO，cornell_box，屏幕中心 (640,360)）**：

| 光向（指向光源 L） | 线性预测 | 预测字节 | 实机字节 | 差 |
|---|---|---|---|---|
| `(0,0,1)`（垂直，N≡V≡L 退化） | (0.058217, 0.058217, 3.877936) | (113,56,249) | (113,56,249) | 0 |
| `(−0.6428, 0, 0.7660)`（转 40°，NdotL=0.766） | (0.045996, 0.045996, 2.972069) | (88,43,244) | (88,43,244) | **0** |

**三通道零误差**。两件事因此得到端到端证据：① 回读链路（glTF→顶点→光栅→材质→直接光→
HDR RT→tonemap→硬件 sRGB→回读→PNG）无系统性偏移；② specular 与漫反**各自**被钉住
——纯蓝面上 R 通道只来自 specular（113），B 通道 = 1/π + specular（249）。
40° 那行是刻意加的**判别力**验证：垂直光下 D/F/G 全退化成常数，判据弱；倾斜后
H≠N、NdotL<1，BRDF 三项全展开，仍然零误差。
阴性对照：谎称 roughness=0.5 或 intensity=6，预测分别偏到 (101,61,244) / (13,16,223) → 判红。

### 推翻的三处「我以为的行为」（都写进了测试与 AGENTS.md）

1. **doctest 没有 tag 形态。** 本项目 doctest 2.5.3 只有 `TEST_CASE(name)`（单参数），
   `TEST_CASE("x", "[gpu]")` 直接编译失败。设备级用例改用 **测试套件**
   `TEST_SUITE("gpu") { … }` + `--test-suite-exclude=gpu`（一等公民过滤器）。
   「用 tag 分流」这个最初设计前提整个是错的。
2. **`resolveRgFormat` 的 fallback 只服务 `"inherit"`**，未知名返回 `eUndefined`。
   我原本以为它是通用兜底（未知名→fallback）——那样配置里的格式拼错会被静默变成
   swapchain 格式，编译不报错而通道数/位深不对。返回 `eUndefined` 才是对的方向。
3. **`decorateShadowPass` 无条件返回 `true`**（没有 `mapSize` 守卫），且它的附件 extent
   用**入参** `mapSize`、每个 pass 的分块尺寸却用**常量** `kShadowMapSize` 推。两者只在
   `mapSize == kShadowMapSize` 时自洽——传别的值不报错、不返回 false，只会得到「分块
   只盖住图集一部分」的错误布局。已写成断言钉住「canonical 调用下分块正好铺满」。

另外同批补的：`state_kit` 九段状态表并非九种形态而只有**五种**（tonemap/ao 与 light 同形、
picking 与 skybox 同形、shadow 与 opaque 同形），真正的不变量是 **`stateFor` 返回九个
不同地址**；以及 `tests/` 链接面扩到全部四层（判据换成「需不需要 VkDevice」而非
「import 没 import rlvk」），`just test` 仍无 GPU 毫秒级。

## 2026-10-01 · Phase 12 批 12.3b：黑面 bug 定案——Frisvad 切线奇点号写反（+勘误 09-30「不复现」条目）

**现象**（probe 场景 cornell_box，styles 钉 model_pbr_ibl）：正对相机的蓝后墙受光面**整面纯黑**
（(640,360) = (0,0,0)），其余面正常；shadow_rig 上同款 = 立方体前面黑、顶面亮。model_pbr 管线
逐字节正确 → 差异只在 frag；但 frag 无条件输出调试色时黑面像素仍是黑的 → **frag 根本没跑**？

**定位链**（全程 imgqa probe 逐字节判据 + 每轮 build rc 核对）：
① styles 钉死 model_pbr_ibl（此前探针一直回落 model_pbr 假绿——12.3b 抓的第一层）；
② 采样/shadowFactor/env/材质逐项 dump 全部正常（R=灯数/16 解码 = 1、GpuLight[0].color = 12×白、
   定向光 atten=1）；③ 三面 NaN 标志探针**一次定罪**：`isnan(N)=1`，geoN/P 清白 →
   NaN 诞生于 TBN。**「调试色没跑」是误读**：frag 一直在跑、输出 NaN——ACES 链的输入 3×3
   矩阵把任一 NaN 通道扩散成三通道全 NaN，tonemap 后整面 (0,0,0)；dump4（不消费 N）干净、
   dump9（dot(N,L) 消费 N）全黑，两个观测被同一机制同时解释。黑面 = **NaN 传播**，
   不是丢覆盖。

**根因**：`gltf_loader_impl.cppm::frisvadTangent` 原式写成 `a = 1/(1-n.z)`——该形态奇点在
n.z=**+1**，而 guard 处理的是 -1，方向反了。法线恰 (0,0,+1) 的顶点 → a=Inf →
**切线 = NaN** → `worldTangent` 无 guard 直接 normalize →
`applyNormalMapTBN` 的 `tlen < 1e-6` 兜底**对 NaN 恒 false**（IEEE 比较）→ `T*0+B*0+N*1` 里
0×NaN=NaN 污染整面（normalmap.slang 头注释「中性法线与切线基无关」的不动点声明**对 NaN 不成立**）
→ 着色全 NaN → tonemap 后 (0,0,0)。model_pbr 不读切线 → 免疫。**只咬法线精确 +Z 的面**——
这就是选择性黑面的全部。bistro_pack.py 的 `frisvad()` 同源同错（其注释「>0 safe」防错了端）。

**修复（含一记自我打脸，值得记）**：正确式 = `a = 1/(1+n.z)`，t=(1−n.x²a, −n.x·n.y·a, −n.x)
——构造即单位长且 ⟂ n（10⁵ 随机球面数值验证 worst |dot|=2e-14、|len−1|=7e-13，±Z 精确）。
主 agent 第一版"改回 Frisvad 原式 `a=-1/(n.z+1)`"**同样被单测打红**：该记忆公式 NaN 安全但
**正交性错**（n=(1,0,0) 处 dot=0.89）——旧代码从未暴露这点，因为 shader 端 Gram-Schmidt
一直在吸收切线垃圾，唯一藏不住的是 NaN。**「断言要照源码写不照记忆写」连修 bug 的当场公式
也不例外**：三个版本里只有数值验证过的那个是对的。loader 提为接口 inline
`export frisvadTangent` + 新增单测 tests/test_frisvad_tangent.cppm（轴向/±Z/随机三面；
**变异双向验红**：改回 ①`1/(1−n.z)` → isfinite 红 3/3；改回 ②`-1/(n.z+1)` → 正交性红 3/3）。
`applyNormalMapTBN` 的 `tlen < 1e-6` 兜底**刻意不加 NaN 兼容形态**（`!(tlen > 1e-6)`）：
NaN 渲染成显眼黑面正是探针能逐字节抓到它的前提，shader 端吞 NaN = 把数据 bug 伪装成
合理光照（沉默跳过=假绿同款）；数据正确性归 loader 单测管，头注释已写明该边界。
**验收**：probe 默认光 + `--light 0,0,1` + 两个背光负例（预测=实际=(0,0,0)）
共 4/4 逐字节 PASS；`just test` 116/116（新增 3 条全绿 + 变异双红）；switch 三项全绿域外恰 0。
