## 灰屏问题修复时间线（2026-06-24，首条管线冒烟）

首条管线（cube + descriptor heap + push data）灰屏修复史。该管线此后已大改，机械修复步骤删于 12.3d（原文见 git
history 与 `docs/DESCRIPTOR_HEAP_SPEC.md`），只留两段机制性叙事：

1. **StructuredBuffer stride 静默损坏（根因）**：HLSL `StructuredBuffer<T>` 强制元素 stride ≥16 字节对齐——C++ `Vertex`
   为 24 字节（2×float3），GPU 读 stride 32 → `vertexBuffer[1]` 从 offset 32 读取而数据在 24 → **完全错误的顶点数据**
   （顶点 1-7 读错位垃圾）→ 几何畸变 + 颜色丢失。临时修法"C++ `Vertex` 加 `float _padding[2]` 凑 32 字节"是个陷阱——
   数据仍只有 24 字节，padding 是垃圾值。**正确修复 = `ByteAddressBuffer` + 手动 `.Load3(offset)` 字节寻址**
   （`ti * 24` 精确匹配 `sizeof(Vertex)`）。现全库禁用 StructuredBuffer（tools/check_shader_deps.py 红线），
   Vertex 24B/color@12 契约由 tests/test_cube_geometry.cppm 钉住。
2. **`heapOffset`/`heapArrayStride` 的单位是字节而非 slot 索引**
   （`VK_DESCRIPTOR_MAPPING_SOURCE_HEAP_WITH_CONSTANT_OFFSET_EXT`）：传 slot 号（8/4）静默灰屏，必须写
   `8 * descriptorSize` / `descriptorSize`。现行契约钉在 `rgl/shader.cppm` 注释（负知识口径见下方沉淀地址）。

---

**沉淀地址**：TEST: tests/test_cube_geometry.cppm（Vertex 24B/color@12）；GUARD: tools/check_shader_deps.py（StructuredBuffer 全禁红线，12.3d-D）；DOC: heapOffset/heapArrayStride 字节单位契约（负知识，shader.cppm 注释钉住）

## 已解决的争议

### ~~Matrix 布局~~
Slang 面向 Vulkan/SPIR-V 时 `float4x4` 默认 column-major，与 `glm::mat4` 一致。**实验证明：添加 `glm::transpose()` 输出严重畸变** — 立方体塌陷为扁平方块。两端内存布局相同，直接透传。

### ~~Push Data Mapping~~
`[[vk::push_constant]]` 在 descriptor heap 模式下不需要显式 mapping。Spec 明确说明无需构建 pipeline layout。

### ~~StructuredBuffer vs ByteAddressBuffer~~
**Slang 面向 Vulkan 时绝不用 `StructuredBuffer<T>` 处理顶点/索引数据**——≥16 字节 stride 对齐与 C++ `sizeof` 静默偏离 → 数据损坏（根因叙事见灰屏时间线条目；全库禁用红线见 `tools/check_shader_deps.py`；`scalarBlockLayout` 不影响其 stride）。

### ~~Trackball 相机"鬼畜旋转"~~（2026-08-22）

**问题：** Phase 1 引入 trackball 相机后，用户反馈"稍微拖动几个像素 cube 就消失"，随后是"疯狂鬼畜旋转"。

**排查（3 轮）：**

1. **误判 Wayland 巨型增量** — 最初以为是 Wayland 合并 pointer 事件下发超大 delta，加了 ±100px/帧 clamp。症状从"瞬间消失"变为"快速消失"，方向对但没到根。
2. **发现相机模型错误** — 用户指出"trackball 下相机应该绕 cube 转圈"。检查实现：cameraSystem 是**原地转朝向**（position 钉死，yaw/pitch 旋转），任何旋转都让目标立刻出视野轴。重写为真轨道：旋转 `position - target` 偏移向量（yaw 绕世界 Y、pitch 绕相机右轴），再由新位置反推 yaw/pitch 保持朝向 target，object 恒居屏中心。
3. **日志定位真根因（SDL3 API 误用）** — 限幅触发的 debug 日志显示"巨大 delta"形态异常：`(260, 367) → (255, 370)` 逐帧缓慢漂移 —— 这是**指针在窗口内的绝对位置**，不是增量。查 `SDL3/SDL_events.h:461-464`：SDL3 的 `event.motion.x/y` 是**窗口内绝对坐标**，相对增量在 **`xrel/yrel`**（SDL2 时代 x/y 即绝对坐标的习惯让人误以为 x/y 是 delta）。把 `event.motion.x/y` 当增量累加 → 相机每帧按"指针位置"旋转 ≈73°/帧 → 鬼畜。改用 `xrel/yrel` 后修复。

**教训：**

- **SDL3 鼠标事件：增量用 `motion.xrel/yrel`，`motion.x/y` 是窗口内绝对坐标，永远不要当 delta 用。**
- 相机"目标消失"类 bug 先查**相机模型**（原地转 vs 绕 target 公转），再查输入数据；日志里的 delta 形态（恒定巨大 + 缓慢漂移 = 绝对位置）是重要线索。
- 输入增量 clamp（±100px/帧，`camera.cppm`）保留作尖峰保险，与根因无关但防真异常。

**沉淀地址**：GUARD: cmake/ReflectionManifest.cmake（features 单源 SHA1）；TEST: tests/test_camera.cppm（trackball 数学）；DOC: VMA 共享所有权与 expected 传播（已落地代码，生命周期性质写不出廉价断言）

## 2026-09-02：编译提速二期——2m2s → 31.1s，以及"为什么惊讶"

`just profile-fast`（clean 后全量）时间线：**137.8s**（一期起点）→ 122.0s（一期：GMF 收敛 + 依赖图解耦，commit `1a6ffce`）→ 112.2s（二期 A：11 模块接口/实现单元拆分）→ **44.5s**（二期 B：rlvk 具名模块，`3736251`）→ **31.1s**（反射管线解耦，`4a1a661`）。user CPU 4m33s → 1m57s（-57%）——**全项目每个模块重复解析 vulkan.hpp 就是最大的那件事**。

**惊讶记录**：B（rlvk）预估 -8~12s，实测 **-68s**，当场 WOW。复盘为什么模型错：

1. **把 3.1s/TU 当成了 B 的全部收益**。3.1s 只是纯文本解析（vkerror 对照实验的量）；hpp 在每个 TU 里还附带：模板隐式实例化、以及 **WriteAST 连带序列化**——模块接口导出实体凡引用 vk:: 类型，该类型所在的 hpp 上下文被一并拖进 BMI。rlvk 后引用变 BMI ID 直连，两头都省。
2. **收益不在并行区而在串行链上复利**。链首四节点实测各降 ~6-10s：vkinstance 7.4→1.2、vkdevice 10.0→1.3、vkswapchain 10.5→1.4、vkresources 13.2→2.6，合计 -34s 全落在关键路径（墙钟 ≈ 关键链长；并行区再省也不掉墙钟）。预估时按"15 TU × 3s 均摊"，没建模"hpp 成本集中在链首串行节点"这一分布事实。
3. 教训：**估编译收益要按关键路径算，不按 CPU 总量算；测"头成本"要用真实消费 TU 的 -ftime-trace（Frontend + WriteAST 两项），别拿单文件对照实验外推。**

A（接口/实现拆分）本身只值 -7s（函数体移出 BMI 的收益被新实现的 entt 头解析吃回去一半）——它是必要铺垫（接口面收窄后 B 的 WriteAST 复利才成立），不是主角。

**二期坑档（append-only）**：

（partition 须显式 `import 主接口` / CMake 4.3 拒绝 FILE_SET 里的纯实现单元须用 partition 形态 / GMF 掏空暴露 rlstd 历史洞——此三条已机制化：rgl-new-module skill 三条坑 + tools/checks/rules_text.py partition 规则 + rlstd“完整可用面”规范，原文删于 12.3d。）
- **vulkan.hpp 的 namespace 作用域 Flags 位运算符**（`operator&|^~`）同理必须逐个 `export using` 进 rlvk，否则 `a | b` 无候选；`operator&=/|=` 在 vk 不存在（Flags 成员函数）。
- add_custom_target/command 的 `-DPAIRS=...` 命令行参数会被 CMake 按 `|`/`,`/`;` 拆分转义，复杂参数一律经 `file(GENERATE)` 落地成 .cmake 文件再 `-D*_FILE` 传入。
- 反射工具链的 custom command 若 DEPENDS 含工具 exe，clean 后 exe 缺失 → 命令必判过期 → 产物重写 → 下游全量重编（14s 串行前缀的根因）；解法 = 产物提交 + 显式 `just reflect` + 哈希守卫，工具链 `EXCLUDE_FROM_ALL`。

**沉淀地址**：GUARD: tools/checks/rules_text.py（partition 显式 import 规则）+ ReflectionManifest（SHA1 新鲜度口径）；DOC: CMake 外部约束、rlstd 完整可用面史（编译器兜底）

## 2026-09-02：edS3 depthClip "VVL 误报"实为真违规（深挖推翻，已修复）

**旧结论（错）**：`vkCmdSetDepthClipEnableEXT` 每帧报 VVL `VUID-…-depthClipEnable-07451`
"feature was not enabled"，此前（同日 §12.3）定性为"VVL 1.4.357 gap、app 无 bug、非致命噪声、
保留现状"。本会话开头复述并"自证"过一次——逻辑（"报错说明调用了命令、说明 feature 探测位
为真"）看似闭环，实则错。

**推翻过程（三源交叉）**：
1. **本地 Vulkan-Docs v1.4.360** `vertexpostproc.adoc:1060`：07451 说"The `depthClipEnable`
   feature must be enabled"，锚点 `features-depthClipEnable` 定义在 `VkPhysicalDevice-
   DepthClipEnableFeaturesEXT` 节——属**独立旧扩展 `VK_EXT_depth_clip_enable`**，非 edS3。
2. **VVL v1.4.357 源码** `cc_cmd_buffer_dynamic.cpp:2361`：`if (!enabled_features.depthClipEnable)`——查的就是旧扩展 feature；上面 09423 才查 `extendedDynamicState3DepthClipEnable`（两 VUID 分管两 feature）。`device_features.cpp` 两字段分别解析自两 sType。v1.4.359/main 检查未变。
3. **vulkaninfo**：RADV `VK_EXT_depth_clip_enable: revision 1`、`depthClipEnable = true`（能开，app 漏开）。

**根因**：两个 feature 名都含 "depthClipEnable" 子串，此前只 grep 到自己启用的 edS3 `extendedDynamicState3DepthClipEnable=TRUE` 就误判"已启用、VVL 记错了"。edS3 只是把旧扩展的 depth-clip 管线状态"动态化"，底座 feature 仍须同时开——VVL 完全正确，RADV 宽容执行才没崩。

**修复** = `features_config.json` optional 加 `depthClipBase`（探测 `VK_EXT_depth_clip_enable`）+ 条件链接 feature struct + 同启扩展；现状 = `depthClipDynamicSupported`（edS3 && base）双条件门已落在 features.cppm（"门未落地"的过渡期注记删于 12.3d，以代码就范收口）+ 真值表 tests/test_features_gates.cppm。headless 冒烟 `was not enabled` 报错归零、命令仍实调（底座补齐而非退化成 no-op）。

**教训**：VVL feature 类报错，先精确锚定 VUID 引用的**那个 sType/字段**（查 spec 锚点或 VVL
`enabled_features.X` 的 X 名），别被相似命名带偏——"某个含该子串的 struct 在链里 = TRUE" ≠
"被检查的那个 feature 启用了"。同名/近名 feature（edS3 的 extendedDynamicState3DepthClipEnable
vs 旧扩展的 depthClipEnable）是本次误诊的全部原因。

**沉淀地址**：GUARD+TEST: rgl/features.cppm `depthClipDynamicSupported`（双条件门**已落地**，issue_history L25 声称与代码的矛盾以代码就范收口）+ tests/test_features_gates.cppm（真值表，12.3d-A）

## 2026-09-10：三驱动排查——NVIDIA DGC 黑屏根因 + DrawArgs 彻底 bindless 化（存疑未闭环）

**背景**：Phase 7b 批次 5 的 DGC 路径（`vkCmdExecuteGeneratedCommandsEXT`）此前只在 RADV 编译绿但**从未运行时实测**；三驱动排查首次在 NVIDIA（RTX 5090 / 610.57.04）跑通 DGC，立即黑屏。**排查链**（Aftermath GPU crash dump + 逐层 bisect）：VVL 首层违规（PUSH_DATA stageFlags 须 ALL / DRAW_MESH_TASKS 须 mesh+task 双 feature / pInitialShaders 唯一性 / 三 buffer usage 位）均为应用侧真 bug、逐条修复（清单删于 12.3d）。**定性方法**：开 `VK_NV_device_diagnostics_config`（flags=15）后 Aftermath dump 显示 `Engine reset`、无 PageFaultInfo、无 active shader，最后一个 checkpoint = `NotStarted`，结合内核 `Xid 109 CTX SWITCH TIMEOUT` = **GPU 在 DGC 命令生成阶段挂死被 watchdog 复位**，非内存错误、非 shader 死循环（shader 从未跑起）。**规模定位**（以“是否 DeviceLost”为自动判据）：单序列 DGC **像素级完全正确**（基础契约全对）；去 PUSH_DATA token（仅 EXECUTION_SET+DRAW）全 1591 序列**活**；含 push token 的任意组合**崩**；尺寸相关性：固定 1591 序列下 push 字节数阈值 83/84、固定 100B 下序列数阈值 ~112/120。

**处置**：顺着项目 bindless 原则把 **DrawArgs 彻底瘦身至仅 `objectIndex`（4B push）**——mvp → scene data per-object MVP 表（`readObjectMvp`）、baseColor/roughnessMetallic/totalTriangles/vertexOffset → per-object 材质/几何表（`readObjectDraw`），均按 objectIndex 索引、CPU 每帧写同一份值（位级与旧 push 路径一致，无 shader 端矩阵乘法）。顺带踩坑：Slang `float4x4(c0,c1,c2,c3)` 构造按**行**填（HLSL 语义），列主序内存读成转置 → 建筑炸形（地面近似对称侥幸正常），改用 `ObjectMatrix`+列组合 `clipPos` 规避。结果：NV 全量 1591 序列 DGC 不崩、渲染正确；RADV replay 画面与基线一致。

**⚠️ 根因存疑（用户明确保留意见，未闭环）**：`push 字节数 × 序列数`这个阈值规律**太邪门**——NV 是 DGC 的最初推手（EXT 由 NV 主导 promote）、官方 `vk_device_generated_cmds` 示例跑了多年，理应有成熟实现，不该有“push 超 80B 多序列就挂死”这种弱智级 bug，因此**不确信 push 尺寸是真正根因**，可能只是某个更底层机制（execution set 内容 × 序列数 × preprocess 内部 staging？）的**共线表象**。已做的 bindless 化无害且符合架构语义，予以保留；但**真正的 NV DGC 挂死机理留待以后复查**（候选实验清单删于 12.3d，见 git history）。排查工具 Aftermath 接线保留为编译期开关 `-DRGL_AFTERMATH=ON`（默认关）。

### 2026-09-13（续 3）：街景"墙面特定角度死黑 + 地面脏噪点"——两个独立负值/NaN 根因

用户反馈（FPS 街景视角）：① 特定角度大砖墙整面死黑；② 湿地面黑点噪声（逐像素 dither）。

**隔离**（llm_debug 截图二分）：直出 albedo 干净（非纹理）→ 输出 `isfinite(color)?正常:红` 标记——红色区域与原黑点/黑块**逐像素重合**，石锤 = NaN/负值非材质。旁路 normal map 后散布 dither 大部分消失但右下角残留一块连续 NaN → 二分 envSpec 非有限（P/N/lod 全有限）→ 定位 env cubemap 数据侧。

**根因 1（墙面死黑）= envBrdfFactor 手抄拟合抄错**：④a 版 `B = -(1.04r-0.04)²` 全 roughness 范围大负值，非金属像素被**减去**最多 1.2× 天空 radiance（env 亮部 4~18）→ 负 radiance clamp 成黑。**修复 = 蒙特卡洛数值积分重拟合**（`tools/brdf_fit.py`，原记录：H 按 GGX pdf=D·NoH 重要性采样（Jacobian dωL=4VoH → 权重 G2·VoH/(NoV·NoH)），52 万样本/格张量积三次 16 系数最小二乘；积分定义/锚点见 docstring，拟合踩坑（VoH 必须带 φ 项、Karis 形式 `0.5/(sv+sl)` 本身 = G2/(4NoVNoL) 不是 G2）见代码；上述权重句字面连读有歧义，**勘误见续 9 条目**。scene.slang 单点替换，forward（model_pbr_ibl）与 deferred（light.frag）共用同时受益。

**根因 2（地面黑块/黑点）= env HDR 太阳 texel packHalf 溢出**：FreeImage RGBE 解码出 float32 天文值 → RGBA16F 重投影 `glm::packHalf2x16` 溢出成 inf → 三线性/mip 混合 inf×权重 = NaN → 反射方向采样 NaN → ACES NaN → 纯黑（isfinite 红标与（isfinite 红标与残留连续块吻合；dither 形态 = 掠射/法线抖动使采样在有限/inf texel 间跳变）。**修复** = 重投影处 `glm::clamp(rgb, 0, 6e4)`（视觉无损）。附带：`irradianceSH` 返回补 `max(r,0)`（SH 截断振铃对高对比 HDR 可输出负辐照度，Filament 同款钳制——本例非主犯但属正确性修复）。

**经验**：逐像素 dither 形态的黑点第一假设应是 **NaN**（ACES 把 NaN 吞成纯黑），一条 `isfinite`→红标 shader 即石锤，快过一切读码猜；黑块与 dither 可同源（NaN 在连续区/跳变区两种形态）。HDR 进 half 纹理必须在转换点 clamp——float32"有限"不代表 half 域有限，inf×0=NaN 让"数据没 NaN"的直觉失效。

### 2026-09-13（续 4）：deferred emissive + 植被 MASK/双面接入——揪出两个 deferred 天空预存 bug

**任务**：Phase 8 剩余批次 A/B/C（emissive_strength loader / deferred 第 5 G-buffer emissive /

### 2026-09-13（续 5）：掠射角白色椒盐噪点 = 导数 TBN 退化，改 CPU 烘切线标准 TBN + specular AA

**现象**：湿地面 / 植被表面在**掠射角**（视线近平行表面）出现逐像素跳动的白色椒盐点。

**定位**（G-buffer 通道分解，免猜）：新增 F1 相机导出快捷键固化机位 → dump G-buffer 逐通道看：position 平滑（**排除 z-fighting**）、albedo 平滑（排除色彩图本身）、**仅 normal 通道椒盐**。再采样白点像素确认是**中性 specular 高光**（亮点通道 max-min 中位数 11，非彩色）——即噪声来自法线，高光只是法线噪声的显形。判据教训：**目测“随机性是否消失”才对，像素计数指标无效**（真实高光本就应有、且随帧连续变化）。

**根因**：`applyNormalMap` 用屏幕空间导数（`ddx(P)/ddx(uv)`）解 Jacobian 造切线空间，掠射角下 `det = st1.x·st2.y − st1.y·st2.x → 0`，invDet 除法放大浮点误差 → world normal 逐像素乱跳。这与资产、MASK/doubleSided 全无关（涉事地面材质全 OPAQUE）。

**修复 A + C（实施细节删于 12.3d，契约由 tests 钉住）**：assimp 三路导出实测均不写切线 → 切线在 `bistro_pack.py` 用 numpy **Lengyel 平滑切线**（+ Frisvad 退化兜底）生成 glTF 核心 `TANGENT`；核心格式不含手性 W → loader **逐三角形按 UV Jacobian det 符号推 W**（实测 bistro UV 92% det<0 = DirectX Y-down 镜像 UV，W 硬编码 +1 会把镜像面切线翻错——又一枚地雷）。ModelVertex 32→48B + `applyNormalMapTBN`（布局契约 tests/test_reflection_layout.cppm，兜底数学 tests/test_frisvad_tangent.cppm）；specular AA（`normalFiltering` Kaplanyan 2016、喂几何法线）forward/deferred 两 pass 接入。

**D1 0→29px 定性（接受项）**：接入后总览 D1 = 29px（0.0031%，**全落在剪影边缘**：天线尖/屋脊轮廓/树叶边缘，肉眼不可见）。
隔离：normalFiltering 置 identity = 19px（纯标准 TBN），恢复 C = +10px；diff 像素处 deferred position 非零 = 几何覆盖一致、
差在 specular；LINEAR 1:1 映射退化 NEAREST，排除 halo。最终定性 = **forward（float N）↔ deferred（oct RG16_SNORM 量化 N）
的固有精度差**，掠射角 Fresnel→1 时 reflect 方向对量化误差极敏感 → 剪影边缘单像素分叉。**非 A/C 新引入 bug**。

**纠偏（重要）**：本文件续 4 把"street 长期 D1 19px"记为"相机时间漂移"——**错**。本次背靠背两次 forward 截图 = 0px，
证明相机确定、零漂移；那 19px 一直就是上述 oct 边缘灵敏度。教训：**"相机漂移"这类甩锅归因必须先用背靠背 run 实测
漂移基线，未实测不得拿来解释残差**。

**教训**：①掠射角白噪点先 dump G-buffer 分通道（position/albedo/normal 各是不是噪的），一步区分
z-fighting / 纹理 / 法线，别读码猜；②导数 TBN 掠射退化是已知病，标准解 = CPU 烘切线（别在 FS 用
dFdx 造 TBN，dFdx 只配喂 normalFiltering）；③forward↔deferred 剪影边缘常驻少量 D1 先怀疑 oct
法线量化（掠射 Fresnel 放大），是固有精度差不是新 bug，追零需升高精度 normal G-buffer。

### 2026-09-14：植被透射 + 光源本色 shader——路灯绿光根因 + backLit=0 盲调参教训

**任务**：给植被（背光透射 SSS）/ 光源（本色）各加 forward 专属 shader，路由 per-primitive（纯数据驱动），deferred 无视 styleMap 逐位不动。实施细节见 phase8_plan §10；本条记诊断。

**绿光 = 路灯变绿霓虹**：光源 shader 上后灯不再是镀铬球、变成饱和发光的绿灯罩。数据根因（提取纹理算均值，3 行 python）：`Emissive_StreetLight` 的 baseColor=纯黑、emissiveFactor 灰、**绿色 100% 来自 emissiveTexture（绿玻璃纹理）**，`0.5×strength(4.0)=2.0` 乘绿纹理绿通道——**金属球版是黑金属底把过强 emission 压暗了才藏住**，去掉金属暴露的是 strength=4 回填值过强的预存问题。修复 = emission×(1/strength) 还原 + 保留玻璃反射。教训：**查颜色异常先提取纹理算均值**（baseColor 黑 / emis 绿一测即明），比读图猜快且准。

**植被透射“看不见” = backLit=0，非 bug**：用户机位与我拍的俯视都是顺光（透光朝正下方出射，仰视镜头 `dot(V,-L)<0`）。据此连调两轮 strength/thickness **零响应**（对比图逐像素近同）——驱动项是 0，调幅度全打在零上，手算 dot 符号验算才暴露。教训：**调光照参数若完全无响应，先算驱动项（一个 dot 的符号/量级）再调幅度**——“效果不出”很可能是“条件不满足”而非“幅度不够”。

**死黑面（“树叶为什么会有死黑面”）**：标准 GGX 的 `NdotL=saturate(dot(N,L))` 让单层叶片卡背阴面直接光**恰好为 0**、IBL 的 `irradianceSH(N)` 朝地面方向又暗、透射只补严格背光角——三层全关零 = 纯黑剪影。真实树冠发亮靠**冠内多层叶互射**（多重散射），单层卡没有这个信息。标准解 = **half-Lambert wrapped diffuse**（Valve HF2/UE 植被同款）把阳光绕到晨昏线背光侧，specular 保持标准 saturate。教训：植被/薄壁/软对象的“死黑面”多半是 **Lambert 项太硬**，wrapped/half-Lambert 是标配，不是调强度能解决的。

**花床“潮湿反光” + 漏路由（红色探针一次定位）**：用户实拍绿篱花床带湿地式天空镜面，两个候选根因（走通用 PBR = 漏路由 / 植被 shader envSpec 掠射菲涅尔）读图无法区分——临时把植被 shader 输出涂纯红跑一张：**花床已经全红 = 本就走植被 shader**，潮湿感即植被 envSpec 本身（掠射角 F→1 拉天空镜像）→ `envSpec×0.2`。真正的漏路由是判据太窄（花床是 OPAQUE 非 MASK+DS），判据补“材质名含 `Foliage`”。教训：**两个候选根因读图区分不了时，构造一个“必走 A 则显红”的判别性实验（探针着色器/涂色），一张图定案**，别逐个候选改一遍看效果。

**批次 F 两个坑（D1 口径误读 + python 截断）**：

① **严格 diff 计数会撒谎——先看幅度直方图**：批次 F 合并后 D1 严格 diff = 149,752 px（16%），初判“合并失败/大回归”。拉幅度直方图才发现：149,601 px 全 @1LSB（deferred G-buffer 8-bit 量化固有底噪，历史 baseline 同谱系 batch1 23k → batch4a 186k，此前“D1=29px”是阈值口径而非严格 diff），真实信号只有 18 个 @81–217 剪影像素。教训：**跨路线像素对拍先画幅度直方图再下结论**——量化底噪与着色分叉的量级在严格 diff 计数下会混成一个数。② **python `open(p,'w').write(re.sub(..., open(p).read()))` 一行式 = 清空文件**：`open(p,'w')` 在参数求值时先截断，再 `read()` 读到的已是空串 → render_graph.lua 被清 0 行，run Aborted；且“背靠背对比”拷到的是上一次的旧截图，对比数字（恰好 149,752 与路线间相同）极具误导性。教训：**改文件先 read 到变量再 write；截图对比前确认目标 run 真的成功（rc + 截图 mtime）**。

### 2026-09-15（续 9）：envBrdfFactor 拟合权重——历史记录描述与 brdf_fit.py 实际不符（外部勘误 #4，代码对文档错）

**事实**：本文件续 3（根因 1）的 MC 权重描述——“H 按 GGX pdf=D·NoH 重要性采样（Jacobian dωL=4VoH → 权重 G2·VoH/(NoV·NoH)）”＋“②Karis 形式 `0.5/(sv+sl)` 本身 = G2/(4NoVNoL) 不是 G2”——作为**权重推导**字面连读，与真源 `tools/brdf_fit.py:36` `w = 2·NoL·VoH/((sv+sl)·cosH)` 不一致：
容易理解成"把某个形式的 G2 直接代入 `G2·VoH/(NoV·NoH)`"，而代码是把 1/(4NoVNoL) 已折进 G2 再与 Jacobian
合并后的形态。代码与 scene.slang 的系数本身正确——错在本 doc 的压缩记录（brdf_fit.py docstring 写了完整合并式；
外部独立复算的 16+16 系数与 scene.slang **逐位一致**、自报 maxerr 与续 3 的 0.056 自洽）。

**独立数值验证**（LCG 20 万样本，两极限对照）：镜像极限（NoV=1, rough=0.05，真值 A→1/B→0）——代码权重 A=1.0000 ✓；续 3 字面权重 A=0.5006 ✗；把 `0.5/(sv+sl)` 当 G2 的变体 A=0.2503 ✗——两个错误变体都过不了续 3 自设的锚“mirror→A=1”，反证产出系数的拟合 run 走的不是文档字面。掠射（NoV=0.05）：代码权重 A=0.77 有限 ✓；字面权重 A=20.3、Karis 式权重 A=10.1 均发散——错误变体残留伪 `1/NoV` 因子，代码权重的 NoV 已在 G2 内相消。

**正确推导**（一句话）：Karis 形式 `0.5/(sv+sl)` 已把 1/(4NoVNoL) 折进 G2（= 真 G2/(4NoVNoL)），与重要性采样 pdf=D·NoH、Jacobian dωL=4VoH 合并后权重 = `2·NoL·VoH/((sv+sl)·cosH)`，即 brdf_fit.py L36。

**结论**：`tools/brdf_fit.py` 与 `scene.slang` 的 envBrdfA/envBrdfB 系数本身**正确，未改**，本条纯文档勘误。按本文件“只增不改”规矩，续 3 的权重原句仍保留（MC 数值细节删于 12.3d，见 git history），权重推导以本条为准。

**风险记录**：若有人照续 3 字面重写拟合工具，会得到静默劣质系数——镜像 A→0.5（镜面反射减半）、掠射区 A→10~20 垃圾值，且全程**不崩、不 NaN、不报错**，只是 specular 略差，极难察觉。教训：**MC 权重记录必须写成最终合并式**（可直接对码核对），把“G2 结构”与“采样修正”拆成两句 = 留解读歧义。

## 2026-09-27：批 9.3 `VK_EXT_present_timing` 落地——四处"文档没说、实测才知"的契约

本机 = Mesa 26.2.3 RADV（STRIX_HALO）+ KWin Wayland。9.3b 实现（`present_timing.cppm(/_impl)` + swapchain 探测 + frame_session present 接线）过程中，以下四点均以 VVL 报错 / 驱动返回值实测定案——规范文本与 archive 调研稿都没写全：

1. **swapchain flag 的支持位不能用 `VkSwapchainFlagsSurfaceCapabilitiesEXT` 筛**。RADV 对 per-surface+mode 的 caps2 查询返
   `swapchainSupportedFlags = 0`，而 `presentTimingSupported = true`。查 spec：约束 flags 的 VUID-12448 整段包在
   `ifdef::VK_EXT_multisampled_render_to_swapchain[]` 内（只有启用那个扩展才生效，本项目恒不启用）——按该字段筛会把
   present timing 在本机误判为不支持。门槛改为 `presentTimingSupported` + stage 掩码含 `QUEUE_OPERATIONS_END`。

2. **链上 `VkPresentId2KHR` 要求 swapchain 创建带 `VK_SWAPCHAIN_CREATE_PRESENT_ID_2_KHR`**（只带 `..._PRESENT_TIMING_BIT_EXT` 不够，VVL 直接报）。激活时两 flag 同置，两 feature 由设备组门 all-or-nothing 一并启用。

3. **`vk::Queue::presentKHR` 对 queue-full 抛异常而非返回码**。vk-hpp 该函数的允许结果列表不含 `VK_ERROR_PRESENT_TIMING_QUEUE_FULL_EXT`（此码 2026 才进 spec），命中即抛——按返回码判断的回退分支永远进不去（第一次实测表现为异常穿透到 main 报错退出）。处置 = `presentKHRTolerantQueueFull` 包装折回 Result 值。

4. **queue-full 回退重试必须同时摘掉 timing 链与 present fence、并清零 wait 信号量**。spec 述被拒 present 的“队列操作仍视为已入队”，VVL 两条印证其后果：再提交已 SIGNALED 的 present fence 报 `Fences must be reset before being submitted`；再 wait 同一 binary 信号量 = 同队列 wait-then-signal 死锁形态。重试只留 image/swapchain（acquisition 已在被拒 present 时释放，VVL 对重投同一 image 不报警），随后 8 帧冷却不挂链，队列排空自动恢复。

**时间域形态（跨驱动需注意）**：本机 RADV 的 swapchain 只 advertise
`VK_TIME_DOMAIN_PRESENT_STAGE_LOCAL_EXT`（id=0），没有 swapchain-local 域。实现改为
"优先 swapchain-local，缺则 stage-local"，且校准的
`VkSwapchainCalibratedTimestampInfoEXT.presentStage` 在 stage-local 下必须恰为基准 stage
一位（VU-12228）。副作用：stage-local 域内不同 stage 的时间戳**历元不一致**——首条结果
log 显示 `QueueOperationsEnd = 20576.656 s` 而 `ImageFirstPixelOut = 20566.756 s`，相差
~10 s。故报告侧放弃"queue→pixel 端到端跨度"，改为基准 stage 瞬时落位（`present.stage`）；
同 stage 相邻差（IPD）不受影响，实测 FIFO IPD p50 = 6.066 ms 恰 = 驱动报的
refreshDuration 6.061 ms，校准与 CPU 轨同轴（首帧 pixel-out 落在首个 present CPU zone
后 ~5.9 ms，一帧周期内）。

## 2026-09-27（同日勘误）：并行双实例污染测量——"85% 丢弃"结论作废

**错误结论**（本文上一条 9.3 条目末尾）："eImmediate 6.5 min 长跑中 85.2%（34190/40117）的 present 其像素 stage 时间恒 0 = 满速渲染被合成器丢弃的直接证据；FIFO 下仅 0.04%"。

**成因 = 测量环境被我自己污染**：19:57:00 我后台起第一次长跑（FIFO），以为它已退出，于是在 19:57:05 又起了第二次（eImmediate）。**两个 rgl 实例同时在屏**，两窗口互相遮挡、KWin 需同时合成两路 surface：① 被遮窗口的 present 走合成拷贝而非 direct scanout，`IMAGE_FIRST_PIXEL_OUT` 对多数帧不再报告（该 stage 的语义是「该 image 第一个像素出现在显示输出上」，合成路径下被合成器接手 = 不适用于 app 的 image）；② 两进程分担 GPU/CPU，帧率被对半压。于是“drop=85%”主要是**呈现路径形态变化**，不是“85% 的帧白渲”。

**单实例复跑**（同一 build，各 25 s，1280×720 forward）：两模式分布在噪声内一致，**drop 双零**；先前 FIFO 那组“p50 恰 = 刷新周期”同样属污染态（彼时它才是被遮挡/被合成的一方）。**权威数据以 `docs/phase9_plan.md` §4.4 单实例复跑表为准。**

**方法学教训（写进操作纪律）**：
1. **窗口测量必须单实例串行**——`nohup ... &` 起后台后，起下一个前必须确认前一个进程已退出（`pgrep` + 日志终值行双检），不能凭"看起来跑完了"推断；
2. **异常漂亮的数字先问环境**——"85% 白渲"这种正好印证既有假设（archive §八）的大数字，最该先怀疑测量条件而非立刻当作证据（确认偏误）；
3. **合成器路径本身是变量**——同一段 present timing 代码在 direct scanout 与合成拷贝两种形态下，stage 可得性完全不同；跨机/跨 WM 比较前，先用单实例确认基线形态；
4. 用户关窗 = 该次长跑作废（不得只取"关窗前那段"当完整样本），要复跑。

不受影响、仍然成立的结论：queue-full 回退路径（压容量到 1 强制触发 → 重试成功 + 冷却恢复、VVL 零报警）、默认关 BIT-IDENTICAL、四处分歧契约（上一条 1–4 项）、CPU-bound 判定（§10）。

## 2026-09-28：Phase 10b 增补批（批 11b.1 中文字体 + 11b.2 HTTP RPC）排障时间线

### 一、imgui 中文显示为问号（批 11b.1）

**根因是三层叠加，缺一层都修不到点上**：

2. **想用系统 CJK 字体还有一层拦路**——内建 stb_truetype 只吃 TrueType 轮廓，

   **无需也不能再指定 glyph ranges**（D4）；缺文件会走 `IM_ASSERT_USER_ERROR`

### 二、RPC 两个真 bug（批 11b.2 验收期抓到）

1. **`set_error_handler` 覆盖自产 4xx body**：cpp-httplib 对**所有 status ≥400** 都回调
   error handler（handler 返回值只控制 `need_apply_ranges`，void lambda 被包装成
   Unhandled 也照跑）→ 我们无条件 `respondBody(res, ...)` 把自家 dispatch 写好的
   400/404/409/504 载荷全盖成 `unknown route`。修 = **只补空体**
   （`if (res.body.empty())`），空体才是 httplib 自兜的 404/405/431。
   教训：第三方框架的"错误回调"未必只在你出错时触发，先读它对 status 的判断条件。
2. **`rpcDispatch` 把 responder move 进下层 → catch 分支空句柄 → 恒 504**：
   `rpcDispatchPost(w, request, std::move(responder))` 之后，本函数 catch 里的
   `responder` 已是默认构造的空句柄，而 `RpcResponder::resolve` 对空句柄是**静默 no-op**
   → promise 永不兑现 → 传输层 2s 超时吐 504。
   **症状指纹极好认**：预构造错误（`rpcFail(400,…)`）路径全部秒回，**只有真正抛
   json 异常的请求**（`get<float>()` 撞字符串、越界取字段）才 504——一看就是"异常路径
   独有的分支坏了"。修 = 传拷贝（`shared_ptr` 拷贝廉价），并在注释里写死勿改回 move。
   复测：wrong type / 缺字段 / 坏值一律 `400 + json.exception 原文` 秒回。

两个 bug 都**不影响默认路径**（门默认关），BIT-IDENTICAL 回归不受影响。

起因 = 用户报「phase10 加入的点选功能似乎并没有生效，或许需要增加个 shader 来表示点选成功，也可能是真的没能点选成功」。**结论：点选一直是通的**——headless 探针与窗口合成左键两轮实测都打出 `回读 raw id → objectSlot → entity` 全链。真正原因是 `diagnostics.picking` 默认关，且**选中后画面零视觉反馈**（唯一反馈是面板“选中”页的一行文字，而 Tab 默认停在“渲染”页）。

### 坑 1：pass 插图末 = 画了白画（图能编译、pass 在跑、纯视觉无效）

高亮 pass 初版按「插在最后一个 pass 之后」实现。**图编译通过、pass 确实在执行、draw
确实录了**，但零视觉输出——因为 forward 图末是 `tonemap`（`drawLight`，采 `scene_hdr`
上屏），插在它之后时 `scene_hdr` 已无人采样，高亮写进了一个死附件。

正确插入点 = **首个「采样场景色附件的消费 pass」之前**（forward/deferred = tonemap 前，
offscreen = composite blit 前），且色附件名由该 pass 的 `sampleRead` 输入反查（不硬编码
`scene_hdr`，三变体自动跟随）。

> 一般教训：动态装饰渲染图时，「追加一个 pass」不是 `push_back` 就完事——**插入点相对
> 数据流的语义位置**才决定它是否可见。编译成功 ≠ 有效果。

### 坑 2：借 depth 前须改上游 storeOp（compile 阶段即报错，good）

forward 图的 `transparent` 段按“depth 后续无人用”优化声明了 `storeOp = dontCare`，高亮借 depth 做可见性测试 → compile 报 `attachment 'depth' … DontCare store but used later`。修法 = 装饰时把上一个写 depth 的 pass 的 `storeOp` 改成 `store`——**门控装饰的一部分**（门关 = 不调用 = 图逐位同），不是改默认图。tests/test_render_graph.cppm 钉住。

### 坑 3：alpha 混合的 rgb/a 语义写错 → 贡献退化为 rim²（实测两次都"不可见"）

混合是标准 `SRC_ALPHA / ONE_MINUS_SRC_ALPHA`（`shader.cppm` colorBlend），合成 = `dst·(1−a) + src.rgb·a`——首版“预乘”把 rgb 又乘了一次 rim，**rim 被乘了两次**：v1（`rim²·0.6`）实测差异像素 1.83%、最大通道差仅 17/255，不可见；到 v3（再加恒定基色权重 0.35，`0.35+rim`）才 112/255 清晰可见。第二个独立问题：**纯菲涅尔只勾轮廓**——正对相机的大平面 `NdotV≈1 → rim≈0`，点中后正面完全无变化，故必须有 `HIGHLIGHT_BASE_WEIGHT` 恒定基色层做“点中即染色”，轮廓光只作强化。

> 教训：调试"效果不可见"时，先用**逐像素 diff 量化**（差异像素数 + 最大通道差 + 分布区域）再定位——
> v1 的 17/255 与 v3 的 112/255 明确指向前者是量级问题而非"没生效"。纯看图分不出"没画"和"画得太淡"。

### 顺带：312 克隆条目的构成（曾误判）

实测 `pipeline entry:` 日志统计 = 312 = 六元组去重结果，**爆炸源是贴图槽不是 shader**：frag 规格只有 3 种、base/normal/orm 贴图槽各 132——bistro 1591 个 primitive 按贴图组合去重成 132 组。**去重本身工作正常**；根因是 `shader.cppm` 用 `HEAP_WITH_CONSTANT_OFFSET` 每管线烘焙不同槽偏移——mapping 进 shader object 身份，故同 SPIR-V 也无法共享编译产物（成本账本见 `docs/shader_object_组合成本与优化预留.md`）。开高亮后克隆 312 → **624**（实测）。

## 2026-09-29 · Phase 11 批 11.0/11.4：Bistro 外景三问题收口（含一次 GPU 卡死误判 + 三次量错数据）

### ① "GPU 卡死只能重启" = 误判，真凶是我自己 OOM

长程会话中途用户报「你这个修改百分百引发 GPU 卡死了，只能重启」——核查：机器确实重启过，但无任何校验层报错、RAM 无 swap 压力，用户随后澄清是 **opencode 自身 OOM**，不是 GPU。真 bug 是启动即报的确定性错误（VVL 不报——它不是校验问题而是**图契约违规**）：forward lua 图的 transparent 段仍按“depth 后续无人用”的旧优化声明 `store="dontCare"`，而新加的 ao pass 之后要 `sampleRead` 读 depth → 撞上编译器“后续使用的写必须 store”的校验。**之前没暴露是因为 `picking` 门开着**：picking pass 声明了 store，把这条掩盖了。

> **教训**：诊断 pass 装饰类改动时，**先把其它调试门全关掉再冒烟**。多个门互相掩盖契约错误时，“能跑”不等于“图是对的”。

### ② SSAO 三个坑（都靠实测才发现，写进了 shader 注释）

1. **产物语义反了**：shader 返回 occlusion（0=通透），tonemap 却当乘数 → 开阔处被乘成 0、strength=1 整幅全黑。改成返回**可见度**（1=通透）后正常。（strength=0 旁路的位级论证 `lerp(1, x, 0) ≡ 1.0` 已记入 AGENTS。）
2. **导数落入非一致控制流**：strength 早退放在 `ddx/ddy` 之前 = UB（编译器无法证明 uniform）——所有早退（天空、strength）必须排在导数之后。
3. **深度图用了共享 sampler**：共享那份是 LINEAR + mipmap LINEAR，而 D32Sfloat **不可过滤**（Vulkan invalid usage）→ 新增 `ensurePointSampler`（NEAREST + 无 mip）。另外踩了图契约连锁反应：为让 ao 读 depth 放宽了“depth 附件只允许 depthWrite”，`decorateHighlightPass` 把 ao 误当成“消费成片的 pass”（它也 sampleRead）→ colorAtt 取到 `"depth"` 与 depthAtt 撞名 → 编译期报 `references attachment 'depth' more than once`。修法 = 消费点判定只匹配**色**附件。

### ③ 三次量错数据，第三次才对（最贵的教训）

- **扫描跑在错误机位**：重启实例后没重新 `aim`，32 组光照配比整轮量的是默认视角。
- **坐标约定搞反**：`[560:700, 300:850]` 是 numpy `[rows, cols]`，按 `[x, y]` 读 → “背光墙”实际量到屋顶上的微缩模型。
- **材质定位用错闪色通道**：baseColor 是**乘法**，纹理本身就暗的表面 ×红色后变化 < 阈值 → 画面里最大的那批暗面被整体漏判“无变化”；改用 **emissive 加法**闪色（与 albedo 亮度无关）才定位成功。

## 2026-09-29 · Phase 11 批 11.2 阴影失效排查：四个 bug 与一条被冤枉的"最大嫌疑"

全程排查日志见 `docs/archive/阴影失效排查.md`（交接文档，结论以本节为准）。症状：`shadow_pass=true` 时画面**零投影**（开关对拍 0.000% 逐位相同）。共修四个独立 bug，全部落地后对拍 **21.5% 像素变化、100% 变暗、0 变亮**（复现机位），树冠/建筑/灯柱投影形状正确。

### Bug 1（采样端）：级联选级把片元推进未写入的槽

未生效级的 `shadowSplits` 留 0，而 shader 选级是无条件三段比较、任何片元 `distSq > 0`
恒成立 → 生效 1 级时全场景被推到 3 号槽（矩阵从未写过 = 全零）→ `clip.w = 0` →
NaN → 阴影因子恒 0。**与机位无关**——5a-3/5a-4 的"阴影可见"判定与四组基线全部作废。
修法：未生效槽也填 `kNoFar`（`fillShadowData`），shader 侧零改动。

### Bug 2（剔除端）：拟合球平面约定混用

`frustumBoundingSphere` 的 Eberly 增量法是"≤ 0"约定，`extractFrustum`/`sphereInFrustum`
是"≥ 0"——混用把球心推向内侧深处、半径长不大（实测 r=1.25 < 远角距 2.0）。
中途"取负转约定"把半径推成 0（更糟）→ 改 8 角 AABB 法（不依赖符号约定）。
**方法论**：一个修正让结果更差时，换方法而不是继续调符号。

### Bug 3（架构）：剔除体与拟合体解耦（对照 Filament）

原"世界球 × 级联切片球"剔除漏掉比受光面高得多的投影体（楼房整批被剔 → 没人画进阴影图）。按 Filament（`ShadowMap.cpp`）重做为 `ShadowVolume`：盒 XY 由切片球定（影子沿光向平移、正交投影下 XY 不变 → XY 只需覆盖受光面），**Z 覆盖全部投影体**的世界 AABB 在光轴上的投影；实体遍历拆两段（循环内攒候选 → 循环后建体再逐级剔除）。

### Bug 4（根因，卡最久）：反投影乘了正向矩阵 + NDC z 值域错

Bug 2 换 AABB 法后仍半径 0，`archive/阴影失效排查.md §3` 把最大嫌疑指向 `projWithDepthRange`
的 GLM 列主序下标——**探针实测洗清**：`out[2][2]/out[3][2]` 与 GLM `perspectiveRH_ZO`

1. **"AABB 角点 = 方向极值"是几何里最常见的隐性假设**——凡"沿某方向取盒的极值"必须

## 2026-10-01 · Phase 12 批 12.3b：黑面 bug 定案——Frisvad 切线奇点号写反（+勘误 09-30「不复现」条目）

**现象**（probe 场景 cornell_box，styles 钉 model_pbr_ibl）：正对相机的蓝后墙受光面**整面纯黑**
（(640,360) = (0,0,0)），其余面正常；shadow_rig 上同款 = 立方体前面黑、顶面亮。model_pbr 管线

① styles 钉死 model_pbr_ibl（此前探针一直回落 model_pbr 假绿——12.3b 抓的第一层）；
② 采样/shadowFactor/env/材质逐项 dump 全部正常（R=灯数/16 解码 = 1、GpuLight[0].color = 12×白、
   定向光 atten=1）；③ 三面 NaN 标志探针**一次定罪**：`isnan(N)=1`，geoN/P 清白 →
   NaN 诞生于 TBN。**「调试色没跑」是误读**：frag 一直在跑、输出 NaN——ACES 链的输入 3×3
   矩阵把任一 NaN 通道扩散成三通道全 NaN，tonemap 后整面 (0,0,0)；dump4（不消费 N）干净、
   dump9（dot(N,L) 消费 N）全黑，两个观测被同一机制同时解释。黑面 = **NaN 传播**，
   不是丢覆盖。

**根因**：`gltf_loader_impl.cppm::frisvadTangent` 原式写成 `a = 1/(1-n.z)`——该形态奇点在
n.z=**+1**，而 guard 处理的是 -1，方向反了。法线恰 (0,0,+1) 的顶点 → a=Inf →
**切线 = NaN** → `worldTangent` 无 guard 直接 normalize →
`applyNormalMapTBN` 的 `tlen < 1e-6` 兜底**对 NaN 恒 false**（IEEE 比较）→ `T*0+B*0+N*1` 里
0×NaN=NaN 污染整面（normalmap.slang 头注释「中性法线与切线基无关」的不动点声明**对 NaN 不成立**）
→ 着色全 NaN → tonemap 后 (0,0,0)。model_pbr 不读切线 → 免疫。**只咬法线精确 +Z 的面**——
这就是选择性黑面的全部。bistro_pack.py 的 `frisvad()` 同源同错（其注释「>0 safe」防错了端）。

**修复（含一记自我打脸，值得记）**：正确式 = `a = 1/(1+n.z)`，t=(1−n.x²a, −n.x·n.y·a, −n.x)
——构造即单位长且 ⟂ n（10⁵ 随机球面数值验证 worst |dot|=2e-14、|len−1|=7e-13，±Z 精确）。
主 agent 第一版"改回 Frisvad 原式 `a=-1/(n.z+1)`"**同样被单测打红**：该记忆公式 NaN 安全但
**正交性错**（n=(1,0,0) 处 dot=0.89）——旧代码从未暴露这点，因为 shader 端 Gram-Schmidt
一直在吸收切线垃圾，唯一藏不住的是 NaN。**「断言要照源码写不照记忆写」连修 bug 的当场公式

`export frisvadTangent` + 新增单测 tests/test_frisvad_tangent.cppm（轴向/±Z/随机三面；
**变异双向验红**：改回 ①`1/(1−n.z)` → isfinite 红 3/3；改回 ②`-1/(n.z+1)` → 正交性红 3/3）。

## 2026-10-01 · 批 11.3-1c：IZB 原子链表首跑三重坑——ByteAddressBuffer 的"字节语义"与"分量乘"

3. **`l3 * w`（float4×float4）= 分量乘**：齐次列组合 `m·v` 的第四列要写 `l3 * w.w`；

## 2026-10-03 · 批 12.6 T4 续：`/shot` 逐张拍不出结论 → 新增 `/shotburst`（连续性必须由帧循环担保）

**症状**：同日上一条收账时，时域判据不可复现——同一配置只把 warm 从 32 改到 64，
S1/S2 就从 1.58× 跳到 0.95×。

**根因**：`/shot` 是「帧首收单、本帧回读」，而引擎**自由跑帧**，两次 HTTP 之间跨了几帧
看墙钟时序 ⟹ 相邻两张根本不是相邻两帧，「逐帧差」退化成随机相位窗。最硬的一条旁证不是
mask 漂移，而是 **S1 自己动了**：S1 = `feedback=1` ⇒ 输出 = 本帧、完全无历史，它逻辑上只
可能依赖抖动相位，却在 warm 32→64 时从 0.0207 变到 0.0152。

**修法**：新增 RPC `POST /shotburst {dir, n, prefix?, gbuf?}`。机制只有一句：第一张在
drain 里登记，**之后每张由帧首结算钩子自己登记下一张**——该钩子先于 `drawFrame`，于是采集
落在连续的第 N、N+1、N+2… 帧上，连续性由帧循环担保，与 HTTP 时序彻底解耦。应答在最后一张
写盘后才兑现（运输层超时另开 120s 一档；路由要在 `debug_rpc_impl` 的 httplib 白名单里
**也**登记，只加 dispatch 会得到一个不带路径的 `"unknown route"` 404——第一次就踩了）。

**修后实测（可复现性验收）**：warm 32 vs 64 → S1 差 0.03%、S2 差 0.4%，比值 1.18× / 1.17×。
「随预热长度差 3 倍」的病灶消失 ⟹ 判据第一次可以被相信。

**由此得到的真实结论**：TAA 时域累积目前只把逐帧差压到 **1.17×**（判据下限 3.0×，闭式
白噪声 ≈11× / 周期输入 ≈4–8×）。它确实在干活（中间调 0→2.8% = 空间上真的把边缘摊开了），
但远不到闭式。候选成因按优先级：① 历史用**双线性**重采样，静止机位下 prevUv = p +
(δ_t − δ_{t+1}) 是每帧随机变的 ≤1px 偏移，每帧重采样一次就把边缘位置误差重新引入一次
（= plan §7 第 5 条记债的 Lanczos-2 输入重建，Filament 默认开）；② box5 邻域裁剪偏保守；
③ 未做 YCoCg 亮度加权 AABB（`taa.frag.slang` 头注释已记债）。

**教训**：① **采集通道的时序语义是判据的一部分**——「拍 N 张图」听起来等价，实际一个担保
连续性一个不担保，而差分判据的全部信息量就在连续性上；② 判据不可复现时，先去找一个
**逻辑上只可能依赖单一因素**的量当探针（本轮 = 无历史的 S1），它比任何解释都便宜地指认了
「变量没被控制住」；③ 加 HTTP 端点要连运输层白名单一起加，dispatch 通过 ≠ 路由存在。

**沉淀地址**：GUARD: `imgqa temporal` 本身即护栏（三条硬判据 + 窗口对齐抖动周期 + 少交一张
立刻抛），可复现性以 warm 32/64 对拍为准；DOC: `rgl/debug_rpc_exec_impl.cppm` `/shotburst`
头注释（连续性机制 = 帧首结算钩子自登记）+ `rgl/debug_rpc_impl.cppm` 超时分档注释 +

## 2026-10-03 · 批 12.6 T4 续二：抑制比判据二次推翻——病根在度量算子（L1 对模糊守恒），不在激励

|---|---|---|---|
